# R13.7 -- the message that waits, and the claim that was not a claim

## Outcome

A message authored on a paired device now lands on a running conversation's next
request, as a marked `user` turn, exactly once, visible locally before it lands,
and off by default. See [[Joined Session]].

Demonstrated end to end against a **plain HTTP client** rather than Claude Code —
which is the point of ADR-0007 §3b's harness-agnostic claim, and is the half of
the gate that could otherwise have been asserted instead of shown. The second
harness needed no launch flag, no channel and no knowledge of Golem: it spoke
`POST /v1/messages` at the proxy and the message arrived.

The path exercised by `tests/integration/join-injection-proxy.test.ts` is the
real one at both ends: a real client certificate through R13.4's mutual-TLS write
surface into the queue, and the real `GolemProxy` and pipeline out to a recording
upstream, so every assertion is about bytes that were actually forwarded.

## Key lessons

**A rename is not a claim — measured, not assumed.** The queue's exactly-once
guarantee was first built on the reflex that a rename is atomic, so the loser of
a race gets `ENOENT`. On Windows, two *concurrent* `fs.rename` calls on the same
source **both resolve successfully** (Node 24.13.1, NTFS; verification-notes
§148), and the two-claimer test duly showed every message delivered twice. The
primitive that actually refuses the second caller is exclusive create —
`writeFile(path, data, { flag: "wx" })` — which returns one `fulfilled` and the
rest `EEXIST` under the same concurrency. Sequential probing would have "proved"
the rename correct: the second rename *does* fail when it happens afterwards. The
race only appears when both calls are in flight, which is exactly the shape two
processes make.

**Anything in this repo using rename as a cross-process mutex is now suspect.**
Atomic *replacement* (write temp → rename over target) is unaffected and stays
correct; that is a different property from exclusive *acquisition*.

**The test that caught it was the one that modelled the real topology.** The
write surface and the proxy are separate OS processes, so the test used two
independent queue objects claiming concurrently rather than one. A single-object
test would have passed against the broken implementation.

**"Sent" is the feature's central lie, so the status is a third value.** The
transport's contract note says an acknowledgement means *delivered*, and a joined
session cannot honour that — the proxy speaks only when the harness speaks to it.
Rather than relax the note, `SessionMessageResponse.status` gained `queued`,
carrying the *condition* in the words a user reads ("this session is idle (14
minutes since its last request); nothing will be delivered until it runs again"),
plus the alternative that would actually work — a [[Hosted Session]].

**Off by default was made structural, not conditional.** The pipeline is handed a
queue only when `security.join_injection` is on. With it off there is no branch
to reach and no queue to read, so byte-faithfulness at compression ≤ 1 is a
property of the wiring rather than of a flag being checked correctly — which is
what ADR-0007 invariant 6 and CLAUDE.md's hard rule actually want. Two
recorded-shape tests assert the same object reference comes back out.

**Injection goes in BEFORE redaction, deliberately.** The queue already redacts
on the way in (its contract's binding note), but placing the stage ahead of
redaction means there is no path by which text reaches an upstream without
passing the stage CLAUDE.md's hard rule puts first. The one consequence to
handle: a local answer would short-circuit a request that had just consumed a
queued message, so that stage is skipped outright when something was injected.

**Appending a turn beats editing one, and the API rule was checked.** Consecutive
same-role messages are legal — the Messages API combines them (verification-notes
§148) — so the injected message is its own `user` turn. Every earlier message
stays byte-identical, the cached prefix survives, and the model can tell who is
speaking. Editing the last message would have moved the cache divergence one
message *earlier* for no benefit. The mid-conversation `system` message was
considered and rejected twice over: it is the *operator* channel, which is the
opposite of what a human's words should claim, and it 400s on Sonnet 5 while
Golem proxies for whatever model the client chose.

**§99's collision needed a mechanism, not a caveat.** Conversation identity is a
hash of the first message, so two conversations that open identically share a
key. The registry separates the distinct *instances* under one key by
message-chain continuity — a chain that extends or rewinds another is the same
conversation; one that diverges mid-chain is a second — and refuses to deliver to
an ambiguous key at all, in both processes. It becomes addressable again once one
of the two goes idle, so the refusal is a state rather than a life sentence.

## What this did NOT do

- **Anthropic's channels as a delivery adapter** (§3b's optional half). §136's
  five objections were re-read and all still stand — flag-gated per session, off
  the curated allowlist, unacknowledged, explicitly unstable. The task brief
  permitted concluding "not yet", and that is the conclusion.
- **A joined session's replies on the device.** Delivery is this task; reading
  the conversation back and picking a target from the phone is R13.8. The device
  can list addressable conversations and see its own queue, which is what
  delivery needs and no more.
- **Any change to who may answer a permission prompt.** Gate-map item 3 is
  untouched and stays off by default; this task only carries messages, and the
  tool calls they lead to are gated exactly as a locally-typed turn's are
  ([[Autonomy Gate]]).
