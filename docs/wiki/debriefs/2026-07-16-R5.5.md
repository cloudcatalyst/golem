# R5.5 — Writing-style adaptation & prompt translation (WS-F7 / spec 20g)

The most research-shaped, lowest-priority R5 task. Per the memo: **spike-first +
a demand check before any real investment.** Shipped as an honest spike, not a
committed feature.

## What shipped (`src/prompt/`)

- **`translatePrompt(raw, {inference, examples})`** — rewrites a raw note into a
  clearer prompt using the LOCAL model, grounded few-shot in the user's own
  accepted examples. The spec's hard constraints are enforced by construction:
  - **Never silently alters intent** — the system prompt forbids adding scope; it
    ALWAYS returns a *suggestion object*, never an action.
  - **Off the proxy path, fully inspectable, disableable** — it only runs when
    explicitly invoked; there is no automatic rewrite anywhere. An empty model
    rewrite yields `translated: null` (never fabricated); an unavailable model
    degrades to `null` + error.
- **`style-store.ts`** — a tiny local example store
  (`.golem/prompt-style/examples.jsonl` + a `last.json` scratch) so accepted
  translations become few-shot grounding over time. Local-only, best-effort.
- **CLI:** `golem prompt translate <note>` prints the suggestion with an explicit
  "Golem never sends this" notice; `golem prompt accept` records the last
  suggestion as a style example.

## Verification

- +6 unit tests (suggestion-not-action, few-shot grounding, unavailable-model
  degradation, empty-rewrite → null, style-store round-trip). Full suite **1018
  green**; tsc + biome clean.
- Driven end-to-end against the real local model: "make the watch thing refresh
  faster and dont break on weird data" → "Optimize the watch functionality to
  refresh more quickly and ensure stability with unusual data inputs." Shown for
  inspection; `accept` recorded it.

## Demand-check gate (before any further investment)

This is deliberately minimal. The spec's open questions — how to score
interactions (explicit vs inferred), avoiding a feedback loop that optimizes the
wrong signal, proving it never distorts intent — are **not** answered here and
should NOT be built speculatively. Gate for going further:

1. **Use it.** Does `golem prompt translate` actually get reached for, or is
   writing the prompt directly just as fast? (The memo's own doubt.)
2. Only if yes: add the inferred-outcome scoring (retries/edits/acceptance) into
   telemetry as additive fields, and measure whether accepted-example grounding
   improves accept-rate. Until there's demand, the scoring loop stays unbuilt.

## Guidance-as-rules model (follow-up, same day — final)

Guidance went through a few iterations the same day and landed here (user
decisions): **Golem guidance is a set of Claude Code project rules, not CLAUDE.md
content.** See `src/hooks/guidance.ts`.

- Each working practice is a named feature written to a rule file —
  `.claude/rules/golem-<name>.md` (committed, team-wide) or
  `.claude/rules/golem-<name>.local.md` (gitignored, personal). Claude Code
  auto-loads `.claude/rules/*.md` every session, so **Golem never edits the
  user's `CLAUDE.md`.**
- **Presence of a rule file is the toggle** — there is no config flag. (The
  short-lived `prompt.translation_enabled` setting was removed.)
- `golem init` **seeds the default features once** (ccr-refs, wiki-kb-first,
  local-coder), guarded by a `.golem/state/guidance.json` sentinel, then leaves
  them user-owned — `golem guidance disable <feature>` sticks across re-inits.
  Opt-in features (prompt-translation, durable-tasks) aren't seeded.
- **`golem guidance list | show | enable [--user] | disable [--user]`** manages
  the rule files; `uninit` removes them + the sentinel. Personal (`--user`) rules
  and `CLAUDE.local.md` stay gitignored (`.claude/rules/golem-*.local.md`).

No frozen interface touched; consumes the frozen `InferenceService`.
