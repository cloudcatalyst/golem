# R11.7 — proving your own innocence

Shipped 2026-08-21, from an incident rather than a plan: a live
`API Error: Connection lost mid-response`, one occurrence in 130 sessions, with
Golem sitting in the path.

## Outcome

- Every daemon line is stamped ISO-8601 UTC, from one sink in `src/shared/`.
- One line per request records target, status, duration, bytes and SSE event
  count, across six outcome kinds.
- A stream that ends without `message_stop` — and without an `error` event to
  explain why — is named **TRUNCATED**, with the event it stopped on.

```
2026-08-21T03:45:46.755Z golem proxy: POST /v1/messages → anthropic 200 — OK in 3.9s, 1.3 KB, 36 SSE events
```

## Key lessons

**The diagnosis was fine. The records were the problem.** Golem was cleared
honestly — same pid throughout, no error lines, a 600s idle timeout against a
7.8s gap, byte-faithful relay on a caching upstream — but every one of those
facts came from *outside* the proxy: the client's transcript, the Windows process
table, the settings file. For a project whose pillar is honest observability,
being unable to answer "was it us?" from our own records is the defect, whatever
the answer turned out to be.

**A log with no timestamps is not a log.** 11,655 lines of
`routed to "anthropic" — inference.default_target`, none of which could be placed
in time, so the file contributed nothing to an investigation of an event that
happened *while it was being written*. Correlating against a client transcript
also decided the format: ISO-8601 **UTC**, because that is what the transcripts
use and what sorts lexicographically.

**Log the END, not just the intent.** The one line per request was written
*before* forwarding — a decision, not an outcome. So a request that died was
byte-for-byte indistinguishable in the log from one that succeeded. Anything that
records "about to do X" and never "X finished, thus" can only ever tell you what
was attempted.

**The truncation signal was already in the building.** `UsageSniffer` reads SSE
event names to find `usage`; whether `message_stop` went past was one boolean
away from a scan already running. A second `Transform` would have been the
obvious shape and the wrong one — every streaming response would pay a copy to
learn what the first hop already knew. Look for the observer you already have
before adding another.

**Silent returns are where outcomes go missing.** Wiring the report exposed two
paths that previously returned with no record at all: a client hanging up
mid-stream, and a translated stream breaking mid-flight. Neither was a bug in
itself; both were invisible. Enumerating a function's terminal paths is a cheap
audit with a good hit rate.

**Answer the follow-up question before it is asked.** The task said measure before
deciding about rotation, so: 181 bytes per request against 65, 2.8×, ~2.0 MB per
11,655 requests. No rotation needed. Both lines are kept deliberately — the
routing line is the "started" record, so a request that *never finishes* still
leaves a trace, which is exactly the case an outcome line cannot cover.
