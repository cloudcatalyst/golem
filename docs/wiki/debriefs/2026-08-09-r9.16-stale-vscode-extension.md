# R9.16 — the status bar was right about a model nobody was using (2026-08-09)

Related: [[R9.5 — two opposite bugs, one missing question]], [[R9.15 — spending the subscription without borrowing its token]]

## Outcome

Reported in one line: *"ive restarted but the vs code status line shows
qwen2.5"*. The config was right. The CLI was right —
`✎ claude-sonnet-5 · ◆ claude-opus-5`. The **deployed** extension was three
releases behind.

Its `render.js` read the worker list from `st.local_model.workers`; the CLI had
since moved `workers` to the top level of `status --json`. Finding none, the
stale renderer fell back to the implicit coder row and filled it with
`localCoderModel` — `qwen2.5-coder:7b`. A surface stating, confidently, a model
that was not in use: the R8.32 / R9.4 failure class, arriving through a door
nobody had checked.

`golem init` now refreshes a stale deployment instead of skipping it, and
`golem status` names one before anybody has to notice a wrong model.

## Key lessons

**"The directory exists" is not "the right bytes are in it."** The whole bug:

```ts
if (await pathExists(target)) {
  return { kind: "skip", detail: "already installed" };
}
```

That directory is named for the extension *version*. Ship a renderer fix without
bumping the version and every subsequent `golem init` is a silent no-op — for as
long as the version holds still. R9.5 diagnosed precisely this shape for
`.claude/rules/*.md` ("seed-once, sentinel-gated → an improved rule never reaches
an existing project") and fixed it there. The same bug was sitting one level up,
in the artifact R9.5 did not think of as a managed file, and survived R9.5 by
being in a different directory.

**The identity check has to be content, not a name.** A version string is a
*promise* about content, and promises drift. Hashing the files costs a few
milliseconds on a command that already probes the network, and it cannot be
wrong in the direction that matters.

**Not every managed file needs R9.5's ownership question.** R9.5 refuses to
overwrite a file that differs from what Golem last wrote, because a user may
have edited it. That care would be theatre here: the deployed extension is a
build artifact in VS Code's own directory, and nobody hand-edits `render.js`
there. So "differs from what we ship" means stale, full stop, and the refresh is
unconditional. Deciding this deliberately — and writing down why the two
managed-file mechanisms disagree — matters more than the code, because the next
reader will otherwise assume one of them is wrong.

**The test suite was green the entire time, and could not have been otherwise.**
`vscode-extension/render.test.js` tests the **repo** copy of the renderer — the
copy that was correct. No amount of coverage on a source file can detect that a
*different* copy is running. The gap was not "untested behaviour", it was
"untested artifact", which is a category that does not show up in a coverage
report. The new tests build a fake extensions directory and assert on
shipped-vs-deployed drift, which is the only place the bug was ever visible.

**Status names it; only `init` fixes it.** R9.13 drew that line for settings
files — a read-only diagnostic that silently rewrites an install is its own
surprise — and it holds here for the same reason. The warning names the files
that differ and the command that repairs them, because "the extension is stale"
invites "says who?", and a warning nobody can act on is the same as no warning
(R9.6).

## Verification

`tsc`, `biome`, `verify:deps`, full suite green — **2520 passed**, +10 (9 drift
tests plus one `init` integration test pinning that a stale deployment is
`modify`, not `skip`).

Live on the machine that reported it, end to end:

```
state: current | id: golem-run.golem-vscode-0.11.0 | stale: []

# deliberately append a line to the deployed render.js
state: stale | stale: ["render.js"]

golem status →
  - the installed VS Code extension is older than the one this Golem ships
    (render.js differ). … run `golem init`, then reload the VS Code window.

golem init →
  modify   ~/.vscode/extensions/golem-run.golem-vscode-0.11.0
           — refreshed render.js — reload the VS Code window

state: current | stale: []      # and the warning is gone
```

The original symptom is also fixed: the deployed renderer, run against live
`status --json`, now produces
`⬢ Golem · Aggressive → ✎ claude-sonnet-5 · ◆ anthropic (claude-opus-5) · ✂ full`.
