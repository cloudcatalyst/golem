# R12.12 -- the gate moved one event earlier, where a decision can actually resolve the request

## Outcome

Golem now registers a `PermissionRequest` hook that returns
`hookSpecificOutput.decision.behavior: "deny"` for `destructive` and `outward`
actions, at every autonomy level, carrying the same reason text the old `ask`
carried. `PreToolUse`'s `ask` is **kept** underneath it. The class line in
[[Autonomy Gate]] is unchanged; only the layer that enforces it moved.

## The gap this closes

R12.11 found that `src/autonomy/gate.ts` never emitted `deny` for the two
never-auto classes — it emitted `ask`, on `PreToolUse`, at every level.

**`ask` forces a question; it does not answer one.** Per the channels reference,
a connected permission-relay-capable channel is notified *"when a permission
dialog opens"* — the relay's trigger condition is the dialog existing at all,
and nothing in the hooks or channels reference exempts a particular call from
the relay once one has opened. A hook-forced dialog on `rm -rf` was, on that
reading, no different from any other dialog a phone could answer.

`PermissionRequest` is the event that can stand in for the dialog instead of
deferring to it. The hooks reference is explicit that it *"Runs when Claude Code
is about to ask you for permission"* and that *"Only the decision object can
grant or deny the request."* A `deny` there means no dialog is shown, and by
construction nothing for a relay to be notified of.

## Key lessons

- **A hook that forces a prompt has not made a decision — it has scheduled one.**
  The whole defect was reading `ask` as enforcement. It is the opposite: it
  guarantees the question reaches whoever is answering questions, and R12.11's
  point was that "whoever" had quietly become "any paired device".
- **The two events do not share a decision shape, and the wrong one is a silent
  no-op.** `PreToolUse` takes a flat `permissionDecision`; `PermissionRequest`
  nests `decision.behavior`, with `message` (not `permissionDecisionReason`) and
  only on deny. Emitting `PreToolUse`'s shape at `PermissionRequest` fails open
  with no error anywhere. A recorded-shape test asserts the *absence* of
  `permissionDecision` for exactly that reason.
- **Fail-closed means make the human decide, not decide for them one event
  earlier.** `unknown` at `outcome` level still only earns an `ask`.
  `decidePermissionRequest` is deliberately narrower than `decideGate`.
- **Adding the earlier layer without removing the later one is what kept the
  audit trail.** `appendActionLog` and `recordPending` both hang off the
  `PreToolUse` pass. The new handler writes **nothing** — so it cannot
  double-count a call its sibling already logged, and it has no I/O to fail on
  at the moment a human is waiting.
- **The documented auto-deny fallback is not a new risk.** *"If no hook returns
  a decision, it denies the tool call"* applies to sessions that cannot show a
  prompt. Deferring (exit 0, no stdout) is byte-for-byte what a project with no
  `PermissionRequest` hook registered already does, so the deferral paths change
  nothing.
- **A gate wired half-way is not a gate.** `golem autonomy wire`/`unwire` now
  install and remove both hooks together, and `wireHooks`/`unwireHooks` stayed
  exact inverses — the rule that file's own header states.

## What this could NOT prove

That the `deny` actually pre-empts a connected channel's `permission_request`
notification **in a live interactive session**. Headless `-p` is structurally
unable to open a dialog at all (§141: four live runs, `ask` resolved to a
synchronous denial with no dialog and no channel notification), so it cannot
exercise the path regardless of which hook is registered. That needs a real
terminal and a real connected channel, and is filed as **R12.13**
(`owner: user`). ADR-0006's R12.11 block now says so in those terms.
