# R11.2 — what the index was quietly spending

Shipped 2026-08-21. Three fixes to one cost: keeping the [[Knowledge Base]] fresh
burns GPU time, at session start, on the user's machine. The full measurements
live in [[Auto-Index Cost]]; this is what we learned finding them.

## Outcome

- `knowledge.auto_index_max_files` (default `50`, `0` disables) bounds the
  **automatic** session-start sync. Past the cap nothing is embedded, the manifest
  is untouched, and the log names the remedy: `golem index`.
- The incremental sync checkpoints its manifest every 20 files, deletions first.
- `canonicalProjectId` collapses every Windows spelling of a project path to one
  collection.

`golem index` passes no cap and is unchanged — it *is* the explicit ask the capped
path defers to.

## Key lessons

**The expensive bug was repetition, not size.** ~10 minutes to embed 114 changed
files is a real cost, but a bounded one. The manifest being written only after the
*last* file was the fault that compounded: any session shorter than the sync
recorded nothing, so the next session redid the identical work — a GPU spike on
every session start with no file having changed. A long job that cannot bank
partial progress is a job that may never finish once.

**"Changed files" is not a proxy for "work the user caused".** A branch switch
rewrites mtimes wholesale, so an ordinary `git checkout` queued hundreds of files.
Any automatic trigger keyed on mtime needs a ceiling, because the routine case and
the pathological case look identical to it.

**Cap the automatic caller, not the operation.** The cap lives in
`EnsureIndexedOptions`, passed by `golem mcp serve` and deliberately not by
`golem index`. Putting it in the operation would have made the explicit ask
refuse too — the shape to copy whenever one code path serves both a background
trigger and a human command.

**Check the cap before the incremental/rebuild fork.** The fallback path is a
*full* rebuild — the most expensive outcome available. A guard placed after the
fork would have let the automatic caller reach it by surprise, which is the exact
thing being prevented.

**Identity bugs bill you silently.** `canonicalProjectId` folded drive-letter case
only, so `d:/repo`, `D:\repo` and `D:\repo\` hashed three different ways and each
re-embedded the tree independently. This repo had **three collections, 231 MB, two
unreachable** — no error, no warning, just triple the work and stale answers from
whichever one won. Path canonicalization is platform-specific and must stay so:
`\` is a legal filename character on POSIX, so folding it there would merge two
genuinely different directories.

**The suite caught the close-out, not the code.** The only red test was
`plan-tasks-roadmap` — filing two new task docs without regenerating
`ROADMAP.md`. That check earns its place: the generated index cannot drift from
the documents it indexes.
