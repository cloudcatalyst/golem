# R13.13 — two target surfaces that stated the opposite of the truth while the logic behind them was right

## Outcome

Two display-layer defects fixed, +3 tests, suite green. Both were found not by
auditing the display code but by **answering a user's question and noticing the
tool's own output contradicted the source**.

Neither was a logic bug. In both cases the underlying behaviour was correct and
the message describing it was wrong — which is the worse failure, because there
is nothing to notice unless you already know the answer.

## Bug 1 — `key MISSING` for a provider reached without a key

`golem target list` rendered:

```
    llama:qwen3-coder-30b   llamacpp http://127.0.0.1:8080/v1 model=qwen3-coder-30b
        trust=local account=llama key MISSING (from gateway)
```

Nothing was missing. `llama-server` serves unauthenticated unless started with
`--api-key`.

The interesting part is that **the codebase already knew this**. The warning
logic thirty lines above the renderer has said so since R10.8, with a comment
that states the principle outright:

> "It is not that a missing key is tolerable there — it is that a key is not part
> of how you reach it, so reporting its absence as a defect and telling the user
> to run `gateway login` is advice their server would ignore. Keyless is the
> CORRECT state for these, not a degraded one."

So the warning list stayed correctly silent while the table beside it called the
same target broken. **Two surfaces, two answers, about one target.**

The cause was that they keyed off *different facts*: the warning asked about the
**provider** (`isKeylessProvider`), the renderer asked only whether an **account
id** was present. Those coincide right up until a keyless provider is reached
through a gateway — which is the normal way to configure one.

**Fix:** compute the fact once, in the collector, where `provider` is still a
strongly-typed `UpstreamProvider`, and carry `keyless` on `TargetRow`. The
renderer consumes it instead of re-deriving anything. Ask it *before* the
account-id branch, because "this provider needs no credential" outranks "this
target names an account".

## Bug 2 — "the model will be IGNORED" on a provider that pins the model

`golem gateway add` printed:

> `warning: provider "claude-cli" is byte-faithful (it forwards the client's own model id unchanged), so model(s) "claude-sonnet-5" will be IGNORED on the wire — they are recorded for display only.`

Both halves false. A spawn provider forwards nothing — there is no wire — and
`claudeCliArgs` pins the model as an explicit argument:

```ts
return ["--print", "--model", model, "--output-format", "text", …];
```

Worse than cosmetic: that model id is also what the dispatcher's
"don't draft on the model you are already using" guard compares against, so a
user who believed the warning and left the model off would get a target that
could not dispatch at all.

The condition was `!isTranslatingProvider(provider)`, borrowed as a stand-in for
"forwards the client's model id". For every provider that existed when it was
written, the two coincided. `claude-cli` is neither translating *nor*
forwarding, and that is where they came apart.

**Fix:** ask both questions — `!isTranslatingProvider && !isSpawnProvider`.

## Key lessons

1. **A predicate borrowed as a proxy for a related question will eventually be
   asked about a case where the two come apart.** `!isTranslatingProvider` meant
   "byte-faithful forwarder" only by coincidence of the provider set at the time.
   When adding a provider that answers an existing predicate unusually, grep for
   every use of that predicate — not just the ones that look relevant.
2. **A display branch that re-derives a fact the collector already knows will
   eventually disagree with it.** The fix was not a better condition in the
   renderer; it was moving the question to where it is answered once. If two
   surfaces must agree, they must read the same field.
3. **The prose is part of the behaviour.** Bug 2 misled a real user into
   believing a capability did not exist. A wrong warning is not a lesser class of
   defect than a wrong branch — it changes what people do.
4. **Correct logic plus wrong message is harder to find than a plain bug.**
   Nothing failed, nothing threw, no test caught it, and the warning list and the
   table disagreed in plain sight for weeks. Both of these were caught only
   because someone read the output and the source in the same sitting.

## Deliberately done this way

- Bug 1's tests are written against `llamacpp` and `openai`, **not**
  `claude-cli`, so the coverage survives R13.12 removing the `claude-cli`
  provider entirely.
- Bug 2's fix was kept even though R13.12 removes its only current trigger: the
  condition is wrong *in principle*, and leaving `!isTranslatingProvider` as the
  sole test would re-create the defect for the next non-translating,
  non-forwarding provider.
