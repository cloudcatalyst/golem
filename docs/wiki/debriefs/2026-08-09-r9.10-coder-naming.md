# R9.10 — the coder stopped being "local" (2026-08-09)

Related: [[R9.6 — a renamed setting no longer stops working in silence]], [[R9.5 — two opposite bugs, one missing question]], [[Configuration Surfaces]]

## Outcome

R9.3/R9.4 made `coder` dispatch to any declared target. The naming never
followed, and pointing `coder` at a `claude-sonnet-5` target made the
contradiction visible inside a single object:

```json
"local_model": {
  "coder_model": "qwen2.5-coder:7b",
  "workers": [{ "worker": "coder", "model": "claude-sonnet-5" }]
}
```

Now: `inference.coder_enabled` (named for the tool, migrated from
`local_coder_enabled`), `workers` promoted to top level with a `local` flag per
row, `local_model` describing only the local backend, `golem local status`
naming any worker that does not run on it, and a guidance rule whose stated
reason survives the target being a paid model.

## Key lessons

**The rename was the easy half.** Registering the migration and sweeping the
identifier took minutes. What took the work was everything the old name had been
propping up: a status block whose shape encoded the assumption, a command whose
description claimed the wrong scope, and a guidance rule whose *argument* —
"drafting locally leaves the paid model's tokens for judgment" — inverts the
moment `coder` points at a vendor model. Renaming an identifier is a sweep;
retiring a **concept** means finding every place that reasoned from it.

**Running the migration on our own repo found the bug the tests didn't.** R9.6's
`config set` writes the live key and reports the redirect — correct, and tested.
But `writeSetting` only ever *adds*, so following the deprecation notice left the
file holding both names, with the shadowed-key warning firing forever and no way
out but a hand edit. No unit test caught it because each half was individually
right. Dogfooding the rename on `.golem/settings.json` caught it in one command.
`setConfig` now deletes the retired key from the same file, via a helper that
deliberately bypasses migration resolution — `writeSetting` resolves retired
names, so using it to delete one would have deleted the replacement.

**A shape can lie even when every field is true.** `local_model.workers[0].model`
was accurate; `local_model.coder_model` was accurate; the *containment* was the
falsehood. Moving `workers` out was the fix, not renaming anything inside it.
Same for `golem local status`: "Local model: ACTIVE" above a worker routed to
api.anthropic.com is a true sentence arranged to mislead, so it now carries an
explicit line saying which workers that backend does not serve.

**Sequencing was load-bearing, exactly as scoped.** R9.6 supplied the migration,
so no existing settings file broke — verified on this repo's own, which still
named the old key. R9.5 supplied managed-file refresh, so the corrected guidance
rationale actually reaches projects that already ran `golem init`; without it the
rewrite would have been invisible to every existing user. Doing R9.10 first would
have *demonstrated* both bugs rather than fixing them.

**Optional fields are how a rename ships without a flag day.** `workers.local`,
the top-level `workers` block, and `non_local_workers` are all optional, and the
VS Code renderer reads the new key with a fallback to the old one — so a stale
extension degrades to incomplete rather than breaking. Same discipline as R9.4's
status additions.

## Verification

Full suite green (2472 passed, +10), `tsc`, `biome`, `verify:deps`, `wiki check`
all 0. Verified live on this repo: the old key in `.golem/settings.json` still
loaded (with a warning naming the file and the key to edit), `local_model` no
longer contained the vendor model, `golem local status` disclosed the routed
worker, and `config set` on the old name left the file holding only the new one —
after which the warning was gone.
