# R8.13 — the verdict that was 98% wrong about a marker

**Verdict: fixed, and §99's own leading hypothesis was wrong.** `golem stats --cache`
reported 142 `bust` / 3 `first` / **0 `append`** beside a billed **98.4% hit rate**.
§99 blamed the conversation key and proposed removing it. The key was fine. Golem was
hashing `cache_control` — a *breakpoint marker* — as though it were cached content.

One line of hashing. The task was sized **M**; the diagnosis was the work.

## What it looked like

Every turn, without exception:

| request | verdict | component | bust index | messages | billed read | billed write |
|---|---|---|--:|--:|--:|--:|
| n | `first` | — | — | 41 | 77,240 | 313 |
| n+1 | `bust` | messages | **40** | 43 | 77,553 | 483 |
| n+2 | `bust` | messages | **42** | 45 | 78,036 | 235 |

The bust index is always `prevCount - 1` — the previous request's **final** message —
while the bill says the cache read 99% of its input. A colliding conversation key
cannot produce that: it would give incoherent chains and repeated `first`s, and the
index would land wherever the two threads happened to diverge. This lands on the same
place every time.

**Cause:** Claude Code moves its `cache_control` breakpoint to the newest block each
turn, so the previously-final block *loses* a key it used to carry. Its JSON hash
changes. `classifyPrefixChange` called that an edit to already-sent history.

Anthropic's docs settle it in one sentence, about exactly this case:

> blocks that were previously marked with a `cache_control` block are later not
> marked with this, but they will still be considered a cache hit (and also a cache
> refresh!) if they are hit within 5 minutes.

The cache key is a cumulative hash of prefix *content*. Breakpoint placement is not
on the documented invalidation list. So the fingerprint now excludes `cache_control`
at any depth — via a `JSON.stringify` replacer, so nothing is deep-cloned on the
request path.

## The gate

| | before (§99) | after |
|---|--:|--:|
| append | 0 | **8** |
| bust (all `messages`, all tail) | 142 | 3 |
| append share | **0%** | **73%** |
| billed hit rate | 98.4% | 99.0% |

The surviving busts are **real**, and they now predict a billed difference — which is
the entire job of a predictor:

- mean billed cache **write on bust turns: 2,951** tokens (n=3)
- mean billed cache **write on append turns: 892** tokens (n=11)

**3.3×.** Before the fix the verdict predicted nothing, because everything was a bust.

## A bust was never one thing

The second half of the fix is that a bust now reports *how much it cost*. A change at
message 2 of 180 re-prefills everything; one at 179 of 180 costs the tail. Under one
counter those are indistinguishable — which is precisely how a 98%-bust report
coexisted with a 98.4% hit rate for a day without anyone able to say which was wrong.

The report names the deepest one, and across the entire pre-fix history it reads:

```
deepest history bust: message 40 of 43 — 3 message(s) (7.0% of history) re-prefilled
```

Even the *worst* of those 850 busts re-prefilled 7% of history. Visible at a glance
now; invisible before.

## A second, real miss found in the same doc

Re-reading the caching page for the marker question turned up a mechanism Golem did
not model: **the lookback window is 20 blocks.** A read walks backward at most 20
block positions from a breakpoint hunting for a prior write, so a turn that appends
20+ blocks at once steps over a prefix that is still byte-identical and still live.

That is now a fourth bust component, `lookback` — a bust where **nothing changed**,
and the remedy is an extra breakpoint rather than fewer edits. It is suppressed when a
request carries ≥2 breakpoints, since a second window would find the write; Claude
Code uses several, so it should be rare. Modelled and tested rather than assumed.

## What generalises

1. **Instrument before redesigning.** §99's candidate A would have torn out the
   conversation key — real machinery, in exchange for nothing. Recording *one more
   number* (the bust index) and reading three requests settled it instead. The
   telemetry field cost less than the redesign's first commit would have.
2. **A hypothesis in a notes entry is still a hypothesis.** §99 was careful, honest,
   and wrong about the cause. It was right about the *severity* and right to refuse to
   fix it on reasoning alone — the task document it produced demanded reproduction
   first, and that is what caught it.
3. **Hash content, not directives.** Any field that tells the *upstream* what to do
   with a request — as opposed to what the request says — does not belong in a
   content fingerprint. `cache_control` was the first; a future one will look the same.
4. **The two-signal rule earned its keep twice.** Keeping billed and predicted apart
   (R8.1's central call) made the contradiction visible on day one, and the
   disagreement warning is kept *after* the fix as a standing consistency check on the
   predictor — not retired with the bug it caught.
