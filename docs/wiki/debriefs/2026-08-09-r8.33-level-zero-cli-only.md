# R8.33 — level 0 becomes CLI-only (2026-08-09)

Related: [[Redaction Stage]], [[Configuration Surfaces]],
[[R8.31 — stopping the proxy meant a dead port, and unwiring alone could not fix it]].

## The gap

`LEVEL_TABLE[0].redaction === false` — level 0 is a real full bypass, per Decision 30, and
that is not in question. **Who can make that choice** was.

Before this task the `level` MCP tool accepted `0`, called `sliderStore.set()` directly, and
the write **persisted across sessions**. The only guardrail was a warning string in the
tool's *response* — emitted after the write had already landed. So any content reaching the
model's context (a poisoned tool result, a hostile file, a crafted page) could persistently
disable the project's most important hard rule, and the user's only signal was a line in a
tool result they may never read.

A warning after a persisted write is not a control. It is a receipt.

## The precedent already existed, one ADR over

ADR-0002 settled this exact question for the **autonomy** level (threat item 4, "Level
tampering / injection"):

> The level cannot be set from within a tool call (no MCP surface writes it) — only the
> explicit `golem autonomy` CLI.

…and, in the same item, an invalid value resolves to the **most restrictive** setting.

The slider did the opposite of both halves: writable from a tool call, and the writable
range included the least-safe setting in the product. Nothing new had to be invented here —
the rule had been written down, applied once, and not carried across.

## Not a walk-back of Decision 8

Decision 8 put the slider on MCP so the model could *request more context fidelity
mid-task*. That intent survives intact: the model keeps 1–3, so it can still raise fidelity
or dial compression at will. The single capability removed is **turning redaction off**,
which was never what Decision 8 was for. Level 0 itself is untouched — still supported,
still reachable, still `golem slider 0`.

## Two gates, because the schema is not the boundary

`sliderLevelInput` narrows to `min(1)` with the refusal text as its message, so an MCP
`level: 0` never reaches the handler (SDK 1.29.0 surfaces it as an `isError` result carrying
InvalidParams — verification-notes §18). The handler *also* refuses `0` before
`sliderStore.set()`.

The second gate looks redundant and is not: the schema is a description, the write is the
boundary. Anything that later loosens the schema — a legacy remap, a new caller, a
generated client — would otherwise silently restore the hole. The test asserts the property
that matters rather than the mechanism: **a `level: 0` call leaves the persisted value
untouched** (set to 2, call with 0, still 2).

## The prose was half the vulnerability

Three surfaces actively *instructed* the agent to do the thing now blocked: the `slider`
prompt ("it accepts integers 0–3"), the `bypass` prompt ("only use 0 for a deliberate full
bypass"), and both skills ("Call the `level` MCP tool with the chosen level"). All now route
a true full bypass to the user's own terminal.

Worth pinning: `.claude/skills/golem/**/SKILL.md` is **generated** from `src/cli/skills.ts`.
Editing the installed copy alone looks correct, passes review, and is erased by the next
`golem init`. Both were changed.

## What did not change, deliberately

A level-0 state set via the CLI must still round-trip through the surfaces that *read* it.
Narrowing the input schema must not narrow reporting — `stats` still reports
`slider_level: 0 / passthrough`, pinned by its own test, and `status`, the statusline and
the VS Code surfaces keep surfacing it loudly. This task narrows **who can set it**, not how
visibly it is shown.

## Verification

`tsc --noEmit`, `biome check` (446 files), full suite green: **2300 tests**, +2.

## Lesson

R8.31 already established that the cheap passthrough forwards *unredacted*, and refused to
build the Stop button on it for exactly that reason. The same fact was sitting one module
away in a tool the model calls, reachable by anything that can write text into a context —
and the mitigation there was a warning printed after the fact.

The narrower version: **a guardrail that runs after the write is documentation.** If the
irreversible part has already happened, the string you return is describing the breach, not
preventing it.

And: when an ADR settles "who may set this", the answer is about the *class* of setting, not
the one field that prompted it. ADR-0002's threat item 4 was right the first time; it just
never got applied to the second dial.
