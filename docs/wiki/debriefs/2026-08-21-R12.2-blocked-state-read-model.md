# R12.2 — the blocked state became a read model

**Outcome.** `{ blocked, reason?, sessionId?, ts }` is now a documented,
versioned read model that answers which project, which session, blocked on what,
and since when — redacted before it is written, and rendered identically by the
status line, the VS Code status bar and panel, and the dashboard. No listener
binds anywhere new; nothing gained write access. Full model:
[[Blocked State Read Model]].

## What shipped

- `SessionState` v2: `project`, `kind` (`permission`/`question`/`idle`), `tool`
  (`name`/`argument`/`actionClass`), `lastEvent`, and `v` itself. A v1 file is
  upgraded on read.
- `resolveBlock()` — one shared classifier with four statuses, replacing per-
  renderer staleness arithmetic. **`abandoned` is the new one**: blocked, stale,
  nobody ever wrote again.
- `blockedView()` — one snake_case projection shared by `/api/state` and
  `golem status --json`, so the two JSON surfaces cannot drift.
- Redaction as an unconditional, fail-closed choke point inside the write path.
- Blocked fixtures in `statusline-parity.test.ts`, and the VS Code status bar
  finally has the indicator the CLI has had since Decision 21b.

## Key lessons

**1. The payload you need is not in the payload you get.** Claude Code's
`Notification` hook carries a generic `"Claude needs your permission"` and names
no tool (verified 2026-08-21 against the live hooks reference). The tool and its
argument had to come from `PreToolUse`, stashed as a pending call and correlated
by session + age when the notification arrives ~6 s later. Any design that assumed
the notification would name the tool was dead on arrival, and only reading the
live docs surfaced that — the repo's own `verification-notes` §65 had the common
fields but not this event's.

**2. A parity test only pins the states its fixtures visit.** R11.8 wrote that
lesson down for the brevity dial. It was still true, unheeded, for the blocked
indicator: `golem statusline` printed `⏸ waiting` and the VS Code status bar
printed nothing, an inch apart, and nine parity assertions never noticed because
not one fixture was blocked. The lesson is not "write parity tests" — those
existed — it is **"enumerate the states, then check each has a fixture."**

**3. Writing the test found the design bug.** The first pending-record
implementation recorded only on the gate's *silent* path, on the theory that
silence means "the human will be prompted". A test using `rm -rf ./build` failed
because the gate emits a forced `ask` for a destructive step — and `ask` prompts
the human too. The highest-stakes prompt Golem can produce was the one case the
implementation skipped. Fixed to "record anything that is not `allow`".

**4. Put the choke point where it cannot be forgotten.** Redaction went into
`writeSessionState` as a recursive walk over every string, not into the callers
field by field, so the field someone adds in R12.5 is covered by construction. The
lazy import keeps the read path — which runs on every prompt — from paying for the
compression graph, and a load failure abandons the write rather than falling back
to plaintext.

**5. Redacting everything has a visible cost, and that is the right trade.** The
entropy sweep hits `project.dir` too, so a worktree named
`agent-ad466baadab001983` renders as a placeholder. Documented rather than
special-cased: ADR-0006 §1 says "no new exception", and an exception carved for
cosmetics is how redaction rules erode.

## Not done, and why

- **The live-block verification in the gate** — "trigger a real permission prompt
  and read the file" — needs an interactive session. The hook handlers are
  exercised end-to-end against real files with real redaction in
  `tests/unit/hooks/blocked-read-model.test.ts`, but a human should still confirm
  once against a genuine prompt, then read `.golem/state/session.json`.
- **No `SessionEnd` hook.** A session that dies mid-prompt resolves to
  `abandoned` with its age, which answers the brief's question without a new event
  surface to wire, uninstall and test.
