# LE5 embed-path fixes + Decision 33 semantic re-review

Started as PRE_R6_BATCH **LE1** — the fair re-review of [Decision 33][d33]'s
local-answer sub-mode on a *semantic* index — and turned up why the semantic
knowledge base had **never built end-to-end on this repo**. The lexical hashing
embedder (no token limit, fixed dim) had masked three separate embed-path bugs.
See `docs/plan/verification-notes.md` §69/§69b/§69c for the full record.

## The three embed-path bugs (LE5, all fixed + tested)

1. **Oversized input** — the chunker's `MAX_CHUNK_CHARS` is a *soft* cap, so a
   dense unsplittable block became a ~4096-token chunk; stock `bge-m3`'s physical
   batch is 2048, so the embed errored and crashed the runner. Fixed by bounding
   each input (`MAX_EMBED_INPUT_CHARS`) in `src/inference/ollama-client.ts`.
2. **Whole corpus in one request** — `#embedAndStore` embedded every chunk in a
   single `/v1/embeddings` call; Ollama opened a localhost connection per input
   and exhausted Windows ephemeral ports mid-build (not a crash/OOM — the tell was
   a *different* ephemeral port in each failure with 7 GB VRAM free). Fixed by
   sequential `EMBED_BATCH_SIZE` batches.
3. **Reindex never cleared on embedder change** — `golem index` re-ingested into
   the pre-existing collection, so a lexical→semantic reindex stranded old-dim
   chunks under the new signature; [§67][s67]'s `EmbedderMismatchError` (shipped
   the same morning) caught it loudly instead of returning garbage — which is how
   it was found. Fixed by resetting the collection on a dimension change in
   `FileVectorDriver.upsert`.

Lesson: a default that silently degrades (lexical fallback) can hide that the
*real* path was never exercised. `EmbedderMismatchError` earned its keep by
failing loud.

## Decision 33 re-review + the finding-#2 fix

On a clean `semantic:bge-m3` index, prose (wiki/spec) genuinely won several
questions — a real improvement over lexical — but dense-token **code/test** chunks
still out-ranked prose for definitional queries (e.g. a `const LEVEL_0 = …` test
line served *above* the correct "slider level 0 = passthrough" prose). Serving a
wrong answer is worse than declining, so Decision 33 stayed PROPOSED.

Fixed in `src/knowledge/local-answer.ts` (finding #2): the extractive local-answer
path now serves only from **durable prose** — `isProseSource` keeps `.md`/docs and
excludes code, tests, *and* working/planning docs (`docs/plan/`), over a wider
candidate fetch so prose isn't crowded out. Post-fix the sample serves **zero
wrong answers**; 5 of 6 served answers come from the wiki.

## The wiki-first payoff

The two remaining weak spots — "slider level 0" (declines) and "compression"
(served a thin VS Code README blurb) — turned out to be a wiki **coverage gap**,
not a ranking bug: no concept page existed for either topic. This makes the
wiki-first design (Decision 28) concrete: **local-answer quality is bounded by
wiki coverage**, so the fix is to write the page, not loosen the filter. Added
[[Slider Levels]] and [[Compression]] as the authoritative prose those questions
should serve.

## Status / open

Decision 33 stays **PROPOSED**: the "no wrong answer served" bar is met, so the
remaining flip-to-ACCEPTED is a human judgment call (are extractive prose answers
good enough given the "verify independently" label + off-by-default posture?),
deliberately not made unilaterally. Full suite green (1036) throughout.
