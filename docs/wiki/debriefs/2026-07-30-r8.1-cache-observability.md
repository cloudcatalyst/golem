R8a's first task, and the instrument the rest of R8 was supposed to be measured
with. Concept page: [[Cache Observability]].

## What shipped

- `src/proxy/cache-prefix.ts` — prefix fingerprinting (hashes, never content) and
  a bounded `CachePrefixObserver` that classifies each request against the
  previous one of the same conversation: `first` / `append` / `bust`, naming the
  component and, for `messages`, the first changed turn.
- Pipeline wiring: the verdict is computed on the **final forwarded body** and
  emitted on the pipeline event. Two new optional `PipelineEvent` /
  `TelemetryEvent` fields.
- `src/telemetry/cache-report.ts` — `aggregateCacheStats` + `renderCacheReport`,
  behind `golem stats --cache [--json] [--project]`.
- 44 tests.

## The finding, which cost the feature its own priority

Run against this repo's telemetry the moment it built (§93): **98.4% hit rate**
over 7,874 responses. Uncached input: **0.06%** of billed input.

The R8 memo had ranked cache-bust detection first, reasoning that busts were an
invisible and recoverable cost. On this project's evidence that reasoning is
wrong — there is essentially nothing to recover. Weighted by rate, **~83% of input
cost is re-reading an already-cached context**, turn after turn: cheap per token,
on a 2.04-billion-token base.

So the bust detector is a **guard rail, not a savings lever**, and the ranked work
is now the levers that shrink what sits in context — R8.2 dedup, R8.5's repo map
and oversized-`Read` swap, R8.4's ledger to aim the pruning. Recorded rather than
quietly re-sequenced, because the instrument arguing against its own author's
priority is the best evidence it is honest.

Worth stating plainly: 98.4% is a measurement of *this* setup (one project, Claude
Code as client, slider 3), not a claim about Golem's users. Claude Code is unusually
disciplined about prefix stability. The value shipped is that anyone can now measure
their own instead of assuming.

## Three design calls

**1. Two signals, never merged.** Billed cache tokens are authoritative but silent
about cause; the prefix verdict explains but is a prediction. They print side by
side. A blended "cache health score" was considered and rejected — it would hide
the exact distinction that makes either number actionable.

**2. `null`, not `0`, for no data.** `hitRate` is `null` when there are no samples,
and the renderer says "no usage samples yet" rather than "0.0%". Same instinct as
Decision 49: a display that simplifies past the truth is worse than a verbose one.

**3. An unobserved request is never a hit.** A byte-faithful request emits no
event (the convention shared with the semantic and context-substitution stages),
so it carries no verdict. Those are counted as `unobserved` and disclosed in the
report. The very first live run proved the point: it read "verdicts: none
recorded" over 14,776 events, correctly, because the running proxy predated the
build.

## Rejected

- **Emitting an event for unchanged requests** to close the coverage gap. It would
  have broken the established no-event-on-early-return convention (asserted in
  four existing stage tests) and changed what `requests` means in every existing
  aggregation. The gap is disclosed instead.
- **A `golem status` line.** `status --json` is polled by the VS Code extension;
  adding a telemetry-file read to it for a number nobody watches per-second is the
  wrong trade. `stats --cache` is the surface.

## Follow-ups

| Item | Note |
|---|---|
| In-process verdict counters to cover byte-faithful requests | would close the coverage gap without changing event semantics |
| Correlate a verdict with the *same* request's billed usage | needs a request id across the pipeline/sniffer split |
| Re-measure the bust rate after a week of real verdicts | the number that decides whether the guard rail ever pays |
