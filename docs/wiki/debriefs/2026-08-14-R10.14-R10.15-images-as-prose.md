# R10.14/R10.15 — a screenshot became 125k tokens of prose, and the model answered with nothing

**Date:** 2026-08-14
**Tasks:** R10.14 (done), R10.15 (done), R10.16 (filed, not built)
**Outcome:** the exact conversation that had returned nothing since 2026-08-13T06:23 answers in 4.4s. 467,764 → 30,817 tokens (**93.4%**). `count_tokens` returns a count instead of a billed completion.

## The symptom

A duoop session on `openrouter:deepseek/deepseek-v4-flash-0731` stopped
answering. Not an error — HTTP 200, `stop_reason: end_turn`,
`output_tokens: 0`, **zero content**. Claude Code injects
`[Your previous response had no visible output…]` and loops forever.

Everything healthy-looking was healthy: proxy up, gateway key set, routing
logged on every request, streaming/tools/`thinking`/`stop_sequences` all fine in
isolation, 2 MB text bodies fine, 1M context real.

## The cause

`Read` on a `.png` returns an **image block inside a `tool_result`**.
`toolResultText` flattened content blocks to a string and sent anything
non-text through `JSON.stringify`:

```ts
if (bb.type === "text" && typeof bb.text === "string") parts.push(bb.text);
else parts.push(JSON.stringify(b));
```

So each screenshot reached the model as base64 **prose**, in a `role:"tool"`
message. Three of them:

| tool_result | tool | bytes |
|---|---|---|
| idx 180 | `Read` | 501,802 |
| idx 199 | `Read` | 576,342 |
| idx 217 | `Read` | 624,112 |

~1.7 MB of a 1.87 MB conversation — **420k of its 468k tokens** — of base64.
deepseek-v4-flash has no vision, and fed that, it returned an empty completion.

## What made it hard, and the lesson

**The stringify is what made it silent.** Sent as real image blocks, the same
model gives a perfect error in 4.4 seconds:

```
{"error":{"message":"No endpoints found that support image input","code":404}}
```

The translation layer converted a clean, actionable 404 into 130 seconds of
nothing. That is the generalisable lesson: **a lossy fallback that "can't fail"
converts a diagnosable error into an undiagnosable one.** `JSON.stringify` as a
default branch always produces *something*, so nothing ever raised.

**Bisection had to be on the real transcript.** Every synthetic reproduction
passed — including 507k tokens of synthetic text, which answered fine. Only
replaying the user's actual conversation from
`~/.claude/projects/…/b926139c….jsonl` reproduced it. Content cleanups
(thinking blocks, empty turns, nudges) changed nothing; removing any one
screenshot fixed it instantly. **Replay the real artifact before theorising.**

**Two plausible causes were wrong.** Context limit (the model is genuinely 1M)
and thinking-only assistant turns translating to `{content:null}` (real, 22 of
them, but tolerated). Both were killed by measurement, not argument.

## What shipped

**R10.14 — vision-aware translation.** `modalities.input` from models.dev,
already cached by R8.8, became `ModelCatalogEntry.inputModalities`. Resolved
once at proxy start into a `VisionLookup`, threaded to the translator.

- vision → images hoisted out of the `tool_result` (OpenAI tool messages carry
  text only) into a following `role:"user"` turn, after every tool message so
  the call/reply pairing survives
- no vision → a one-line placeholder naming media type and size
- **unknown → pass through, unchanged.** Guessing "no vision" silently blinds a
  model that can see; forwarding to one that cannot returns the 404 above. A
  wrong guess that fails loudly beats a wrong guess that fails silently.

Also: an assistant turn with no text and no `tool_calls` now emits `""`, not
`null`.

**R10.15 — `count_tokens` answered locally.** There was no handler anywhere in
`src/`, so the path was rewritten to `/v1/chat/completions` and answered with
prose — and billed. Now `{"input_tokens": N}`, no upstream call. The number is
an **estimate** (`estimateTokens`, ~4 chars/token); images get a flat nominal
1,600 rather than their base64 length, which would overstate one screenshot by
~100k.

## Filed, not built

**R10.16 — the stall.** `message_start` is lazy and nothing emits `ping`, so a
translated stream sends **zero bytes** during prefill: 124–152s of dead socket,
measured. Worse, `bodyTimeoutMs`'s own comment sizes the idle budget on
"Anthropic SSE streams emit `ping` events well within this" — a cadence the
OpenAI path never has.

Deliberately not bundled: fixing it alone would have made this bug *more*
confusing — a stream that pings for two minutes and then returns nothing.
