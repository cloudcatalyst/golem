# R8.11 — the plugin surface, and admitting there is no sandbox

Third-party **pipeline stages**, **MCP tools** and **redaction rules** without
forking Golem. See [[Plugin Seams]] for the standing description; this is what
building it taught.

## Outcome

`src/plugins/` (contract, loader, init), an append-only extension point in the
redaction table, a plugin stage in the pipeline, plugin MCP tool registration,
`golem plugin [--verbose|--json]`, and a `plugins` settings section that defaults
to loading nothing. **ADR-0005** came first and is the real deliverable. +53
tests; full gate green (2857 passed), `wiki check` clean.

Verified live: a real plugin file on disk, loaded through the actual
resolve-and-import path on Windows (file-URL conversion included), registering all
three seams; the failure path (a missing specifier reported as a problem, not an
error); `plugins.enabled: false`; and `--verbose` / `--json`.

## Key lessons

**1. The task said "if it needs a sandbox to be safe, say so in the ADR rather
than shipping". It does, there isn't one, and saying so was the work.** Every
option was checked before writing that down (§134): `node:vm` is not a security
boundary and its own docs say so; `worker_threads` isolates *state*, not
*authority*, and a redaction rule has to run synchronously inside the pass to be
part of it; `--permission` is process-wide and set at launch. A separate OS process
*is* a real boundary — and Golem already has that surface, which is `golem pkg`.

So the ADR says, in the words a user would use: *loading a Golem plugin is exactly
as dangerous as adding a dependency to your own `package.json` and importing it.
It is not less dangerous.* That sentence is also in the CLI output and the settings
help. **A control that looks like containment is worse than an honest absence of
one** — it converts an explicit trust decision into a false sense of one.

**2. The comparison that makes the decision defensible is the status quo, not
zero.** "Is loading third-party code risky?" is the wrong question. Before this
seam, extending redaction meant *editing Golem*, and the realistic outcomes were:
the org forks and drifts out of date with fixes to the redaction stage itself; or
gives up and their private key format flows upstream **unredacted**; or does not
adopt Golem. None of those is safe. Framing the ADR against those three, rather
than against an imaginary risk-free baseline, is what turned "should we do this at
all" into a decision with an answer.

**3. When containment is impossible, every mitigation must be structural.** The
threat-model table was written so that **every "yes" is a property of the seam and
every "no" is a property of the runtime**. No row is mitigated by "we reviewed the
plugin". Concretely:

- Built-ins always run first, plugin rules are a suffix, `REDACTION_RULES` is
  never handed out, and there is **no remove/replace/reorder function to call**.
  A plugin can only ever redact *more*.
- Rule kinds are namespaced `<plugin>/<rule>`, so a plugin cannot impersonate a
  built-in placeholder kind in telemetry.
- A plugin MCP tool name colliding with a built-in is rejected at load, with a
  two-way drift test against the tools the server actually advertises.

And two rows are deliberately **"No", with no mitigation at all**: a plugin can
exfiltrate what it sees, and a pathological regex can hang the proxy (JS regex
execution is synchronous and uninterruptible). Writing those down is the feature.

**4. The best answer to "can a stage weaken redaction" was to redact again.** The
instinct is to audit what a stage returns. Instead: a plugin stage receives
already-redacted content, and **redaction re-runs over whatever it returns**.
Redaction is idempotent — placeholders contain `[`, `]` and `:`, which no rule's
charset matches — so the second pass renumbers nothing and costs one pass only
when a stage actually changed something. What it buys is a property rather than a
promise: a stage cannot introduce unredacted content, however it obtained it. The
extra pass is attributed separately (`redaction-after-plugins`) so a stage that
keeps doing it is visible rather than folded into stage 1.

**5. "Register once" turned out to be a caching requirement, not tidiness.**
Redaction must be a pure function of its input for prompt-cache prefix stability
(§14). A rule table that could change mid-process would break the cached prefix
for every later request — so a **second** registration is *refused with a reason*
rather than merged. The API shape follows from a caching constraint, which is not
where you would look for it.

**6. A plugin that throws half way through `setup()` gets nothing installed.**
Registrations are buffered per plugin and only committed if `setup()` returns.
Keeping the half a plugin managed before failing would mean installing a redaction
rule from a plugin that never finished saying what it wanted — and the tool-name
reservation it took has to be released too, or a later plugin is refused a name
nobody holds.

**7. A throwing third-party validator is "not a secret", not a crash.** A built-in
validator returning false means "matched the pattern but is not actually a
secret". A third-party one that throws has told us nothing, so the safe reading is
the same verdict — and crucially it must not abort a pass that still has built-ins
to run. The loader wraps it; the test proves it by registering *what the loader
produced* rather than hand-rolling the wrapper.

**8. Two test fixtures nearly passed vacuously.** The AWS key fixture was
`AKIA` + 15 chars, one short of the 20 the built-in rule requires — so the "a
built-in still wins over a greedy plugin rule" test was actually observing the
plugin rule matching a string no built-in ever would. And a first attempt at the
throwing-validator test asserted `.toThrow()` in the middle of the case it was
supposed to be proving. Both found by the assertions failing for the *right*
reason, which is the argument for asserting the placeholder kind and not merely
"the secret is gone".

## Deliberately not built

- **No install verb.** Installing third-party code is npm's job; offering
  `golem plugin install` would imply a vetting Golem does not perform. `golem pkg`
  can consent-gate an install precisely because a subprocess is a real boundary.
- **No discovery.** No `node_modules` scan, no naming convention, no registry, no
  download. A plugin loads because a human wrote its specifier, and for no other
  reason.
- **No capability declarations or per-plugin permission prompts.** They would be
  theatre: the plugin can do the thing regardless of what it declared.
- **No frozen interface.** The contract lives in non-frozen
  `src/plugins/types.ts` on purpose — promoting it later is cheaper than freezing
  a first draft now.

## Successors (recorded, not gaps)

- **Declarative pattern-only rules** — a pattern file, no code loading, no ADR
  needed. Covers the majority case ("our key prefix is `ACME-`"), strictly safer
  and strictly less capable. Probably the right default for most users.
- **WASM-compiled rules** — a genuine sandbox for the *pure* seam. A pattern
  matcher has no business touching the filesystem.
