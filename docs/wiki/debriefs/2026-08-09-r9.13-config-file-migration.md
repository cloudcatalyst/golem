# R9.13 — a project that upgrades Golem fixes its own settings files (2026-08-09)

Related: [[Configuration Surfaces]], [[R9.6 — a renamed setting no longer stops working in silence]], [[R9.5 — two opposite bugs, one missing question]]

## Outcome

Asked directly: *how does a project using Golem know its config needs migrating,
and how does it happen automatically?* Reading the code gave a half-answer.
R9.6's table makes a retired key keep **working** — the loader redirects it and
warns — but nothing ever fixed the file, so adoption was manual and the warning
was permanent.

A project now records the Golem version it last ran (`.golem/state/version.json`,
beside R9.5's `managed-files.json`). On the first run under a new version it
rewrites retired setting names to live ones across **all three scopes**: user,
project, and local. `golem config migrate` is the manual door, check-mode by
default; the automatic path runs from `golem proxy` and `golem init`.

## Key lessons

**The version stamp is not load-bearing, and saying so is the design.** The
trigger for a rewrite is the *presence of a retired key*. The stamp only decides
when to bother looking. That makes every failure mode of the stamp benign — a
missing, stale, corrupt or wrong stamp degrades to "scanned more or less often
than needed", never to a bad rewrite. Without that sentence in the module header
the next reader would guard the stamp as if a migration's correctness depended
on it, and would be defending the wrong thing.

**Key order is a user-visible property, because the file is committed.** The
obvious rename is `delete` + assign, which moves the key to the end of its
section, because JSON key order is insertion order. That turns a one-line diff
into a whole-section one in a file the user has in version control. Renaming *in
position* is a five-line helper whose entire purpose is the shape of somebody
else's `git diff`. The posture chosen here — rewrite a committed file without
asking — is only defensible if the diff it produces is small and explained.

**Where the backup goes is part of the safety, not an afterthought.** The
obvious `settings.json.bak` beside the original would appear as an untracked
file in the user's repository — a safety net that creates repo noise reads as a
mess, not as care. `.golem/state/config-backups/<scope>-<version>.json` is
already covered by the `**/.golem/state/**` rule `golem init` writes, so the net
is invisible until wanted.

**Reuse the loader's existing decisions rather than inventing parallel ones.**
Three behaviours were taken directly from code that already had to decide: a
file holding both the retired and live key drops the retired one (the loader's
shadowed-key branch already ignored it), a malformed file is reported and left
untouched (`readExisting`'s stance in `write-setting.ts`), and writes go through
temp + rename (`writeSetting`). A sweep that disagreed with the loader about
which key wins would be a second source of truth about the same question.

**Not every surface should be a write surface.** The sweep runs from `golem
proxy` — before `loadConfig`, so the R9.6 warnings printed underneath describe
what is *still* wrong rather than what was just fixed — and from `golem init`,
which is what people actually run after an upgrade. Deliberately **not** from
`golem status`: a read-only diagnostic that silently rewrites files is its own
surprise, and the point of this work is to remove surprises.

## Verification

`tsc --noEmit`, `biome check`, `verify:deps` all exit 0. Full suite green:
**2489 passed**, +15 from the new `tests/unit/config-migrate-files.test.ts`. One
failure en route was the plan-index test, correctly reporting that `ROADMAP.md`
was stale after `R9.13.md` was added — regenerated with `golem task index
--write`.

Smoke-tested against the built CLI with a temp project whose `settings.json`
named both retired keys. Check mode listed both renames and left the file
byte-identical; `--write` produced:

```json
{
  "proxy": {
    "port": 4477,
    "default_target": "my-target",
    "request_timeout_ms": 600000
  },
  "inference": {
    "coder_enabled": true
  }
}
```

`default_target` sits exactly where `active_account` was, between `port` and
`request_timeout_ms` — the in-position rename, observed rather than asserted.
The backup landed at `.golem/state/config-backups/project-0.11.0.json`, and a
second run reported "Every settings file uses current setting names." The
automatic path was exercised separately against the built module: first run
migrated and stamped `0.11.0`, second run at the same version did nothing.

## Aside — the `coder` tool is currently broken on this machine

Drafting this work with `coder` failed: the tool is routed to target `sonnet-5`,
which returns **401 Unauthorized**, and `openrouter-qwen3` returns 401 as well.
Ollama itself is healthy (`qwen2.5-coder:7b`, `localhost:11434` reachable) —
`golem local status` says in as many words that `coder` runs on target
`sonnet-5`, **not** on the local backend. Worth noting that this is exactly the
class of honest-surface work R9.4 and R9.10 did: the status output told the
truth, and the truth was that the credentials, not the routing, are the problem.
