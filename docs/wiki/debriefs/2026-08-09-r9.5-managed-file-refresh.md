# R9.5 — two opposite bugs, one missing question (2026-08-09)

Related: [[R9.6 — a renamed setting no longer stops working in silence]], [[Configuration Surfaces]]

## Outcome

Golem writes two kinds of file into a user's project and treated them inversely
wrong: a re-init **overwrote** a hand-edited skill (silent data loss), and
**never refreshed** a guidance rule (every guidance improvement invisible to
anyone who had already run `golem init`).

Both now go through one mechanism that records the hash of what Golem last
wrote, so a managed file is *current*, *absent*, *stale* (safe to refresh) or
*owned* (the user's — reported, kept). New `conflict` action kind; record lives
in `.golem/state/managed-files.json`, gitignored, removed by `uninit`.

## Key lessons

**They looked like opposite bugs and were the same bug.** Both surfaces asked
*does this file differ from what Golem ships?* That question cannot separate
"Golem's text moved on" from "the user edited it", so each surface picked one
interpretation and was wrong half the time — skills assumed drift meant staleness
(and clobbered), guidance assumed drift meant ownership (and froze). Adding the
missing question dissolved both. Worth generalising: when two subsystems have
opposite-looking defects, check whether they are answering the same
under-determined question differently.

**When you cannot prove it, don't destroy it.** A project initialized before
this mechanism has no hashes. Classifying those files as *owned* means the first
post-upgrade init reports conflicts on drifted files rather than refreshing
them — slightly noisy, and correct. The opposite default would have been the
original data-loss bug wearing a new mechanism. Same reasoning for a corrupt
record: it degrades to *keep the user's file*, never to overwrite. **The
conservative direction is the one where being wrong is recoverable.**

**A mechanism that removes a bug can also remove a safeguard — check.** The
guidance sentinel was doing two jobs under one flag: "don't undo the user's
`disable`" (intended) and "never refresh the text" (accidental). Splitting them
is the whole feature, and it would have been very easy to split them by simply
deleting the sentinel check — which resurrects every rule the user turned off.
That is a *worse* bug than the one being fixed, because it overrides an explicit
choice rather than an implicit one. It has its own test.

**The distinction has to live in the vocabulary, not the wording.** "Refreshing
stale text" and "replacing your edit" cannot both render as `modify` — and it is
not enough to say so in the detail string, because actions are rendered
generically in several places (two `padEnd` renderers, the VS Code panel,
`--dry-run`). It needed a new `ActionKind`. The detail string then carries the
instruction, since a refusal with no way forward is just an unexplained stop.

**This repo's own safety net nearly hid the severity.** `.claude/skills/` is
git-tracked here, so a clobber was always recoverable *locally* — and permanent
in a user's project that doesn't commit it. The task brief flagged this
explicitly, and it is a good reminder that "I'd have noticed" is a property of
this working copy, not of the software.

## Verification

Full suite green (2462 passed, +17), `tsc`, `biome`, all 0. Smoke-tested against
the built CLI: `golem init` in a temp project, append a line to
`.claude/skills/golem/ship/SKILL.md`, `golem init` again → reports `conflict …
kept your version …` and the edit survives. Before this change the same sequence
destroyed it and reported only `modify`.
