# R9.9 — `golem config set` learns to write objects (2026-08-09)

Related: [[Configuration Surfaces]], [[R9.8 — marker-free by default, and the warning nobody could read]]

## Outcome

`golem config set <key> <value>` coerced the raw CLI string to the leaf's zod type for
booleans, numbers and arrays — and for nothing else. An object-valued leaf
(`z.record`, `z.object`) got the raw string, which failed validation with
`Expected object, received string`:

```
$ golem config set compression.headroom_config '{"compress_user_messages":false}' --scope local
golem: invalid value for "compression.headroom_config": Expected object, received string
```

So the Decision 53(h) passthrough bag — the whole point of which is to be *settable* —
could only be written by hand-editing `.golem/settings.local.json`. A config command that
sends you to a text editor is not a config command.

Object leaves now parse as JSON through the same seam the array path already used.
`--value-file <path>` and `--value-file -` (stdin) were added as the quoting-proof route.

## Key lessons

**The bug was in the *shape* of the coercion table, not in one missing branch.** The
tempting fix is `if (target instanceof z.ZodRecord)` beside the others and move on. The
gate that got written instead is a test that **enumerates every object/record leaf in
`SETTINGS_LEAVES` and asserts each one is settable**. That is what makes the fix
non-special-cased: the next `z.record` leaf someone adds is covered on the day it lands,
and the test fails loudly rather than the CLI failing quietly.

**An error message that describes the symptom hides the cause.**
`Expected object, received string` is *true* and useless — it describes what zod saw,
not what the user did wrong. The replacement names the cause and, critically, the way
out: `invalid JSON for "<key>": Expected property name or '}' … — got "{protect_recent:6}".
If your shell is eating the quotes, use --value-file <path> or --value-file - (stdin).`
A parse failure and valid-JSON-of-the-wrong-shape are now different messages, because
they are different mistakes.

**JSON on a command line is a shell fight, and the user loses it differently on every
platform.** PowerShell, `cmd.exe` and POSIX shells each quote embedded `"` their own
way, and the failure mode is indistinguishable from a genuine syntax error. Documenting
three invocations is necessary but not sufficient — the escape hatch is what actually
removes the problem, so the value can come from a file or stdin and never touch the
shell's quoting rules at all. It strips a UTF-8 BOM, because Windows editors add one and
`JSON.parse` rejects it.

**Refusing ambiguity beats picking a winner.** Passing both a positional value and
`--value-file` is an error. Silently preferring one would write a value the user did not
intend, and they would have no way to tell.

**A latent bug fell out of the feature.** `setConfig` decided "was this write overridden
by a higher layer?" with `effective.value !== value` — a *reference* comparison. Scalars
were fine; every object write reported itself overridden by a layer that had overridden
nothing. Fixed with a structural compare. Worth noting that this bug was unreachable
until objects became writable, and would have shipped as a confusing warning on day one.

## Verification

`tsc --noEmit`, `biome check`, `vitest run` all exit 0; the gate command was smoke-tested
against the built CLI in PowerShell for all four paths (positional JSON, malformed JSON,
`--value-file`, stdin, and the both-sources refusal).
