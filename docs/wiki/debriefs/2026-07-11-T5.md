# T5 — graph-first search lookup

Spec Decision 28 / proposal `wiki-knowledge-pivot.md` §2 wanted the `search`
MCP tool to try the wiki's title/wikilink graph before falling back to vector
search. Only the boost (W1c, rank wiki-dir hits above equal-scoring non-wiki
hits) existed; there was no title/graph lookup ahead of it.

## What changed

- `src/interfaces/wiki.ts` (frozen contract, **change flagged**): added
  `listPages(): Promise<readonly WikiPage[]>` to `WikiReader`. `search` needed
  a title table it could build once per call without duplicating the
  directory-scan logic that `readPage`/`resolveLink`/`backlinks` each already
  ran independently.
- `src/wiki/file-wiki-store.ts`: `FileWikiStore.listPages()` made public — no
  behavior change, it already did the full scan.
- `tests/contract/wiki-contract.ts`: new `listPages` case in the shared
  `WikiStore` contract.
- `src/mcp/server.ts`: `graphFirstWikiHits(query, wiki, wikiDir, projectId)` —
  exact/case-insensitive title match, then a 1-hop expansion along that page's
  outgoing wikilinks (`extractWikilinks`, already exported from
  `src/wiki/frontmatter.ts`). Matches become synthetic `Hit`s via `pageToHit`
  (`chunkId = wiki:<relPath>`, `sourcePath = <wikiDir>/<relPath>` — the same
  convention vector-ingested wiki chunks use, so `boostWikiHits` and
  de-duplication both work unmodified) scored above any vector hit
  (`GRAPH_TITLE_MATCH_SCORE = 2`, `GRAPH_LINKED_PAGE_SCORE = 1.6`, both well
  clear of a vector hit's `1 * WIKI_RANK_BOOST` ceiling).
  - `registerKnowledgeTools` now takes an optional `wiki: WikiReader` param,
    threaded from `deps.wiki`.
  - `search`'s handler runs graph lookup and vector search every call, merges
    graph hits first, drops any vector hit whose `sourcePath` duplicates a
    graph hit's, then boosts/sorts/slices to `k`. Degrades to vector-only when
    `wiki`/`wikiDir` is absent — no branch removed, just an empty graph-hit
    list.
  - `fetch` resolves a `wiki:<relPath>` chunk id straight from the `WikiStore`
    (`wiki.readPage`) instead of `knowledge.getChunk`, since graph-first hits
    were never vector-ingested and `getChunk` would 404 on them.

## Verification

- `tests/unit/mcp/server.test.ts`: 7 new tests for `graphFirstWikiHits` /
  `pageToHit` against a fake `WikiReader` (empty wiki, no match, exact
  case-insensitive match, 1-hop expansion scored lower than the exact match,
  unresolved/duplicate wikilinks skipped, self-link doesn't self-duplicate).
- `tests/integration/mcp-knowledge.test.ts`: 4 new tests over a real
  `FileWikiStore` — exact-title-plus-1-hop ranks above a vector hit; `fetch`
  on a `wiki:` id reads the wiki, not the vector store; a vector hit sharing
  a graph hit's `sourcePath` is dropped; degrades to vector-only with no wiki
  injected.
- Full gate: `tsc --noEmit`, `npm run lint`, `npm run format:check`, `npm test`
  (72 files / 692 tests) all clean. Rebuilt and restarted the proxy; confirmed
  `.golem/settings.json` still has `"level": 5`.
