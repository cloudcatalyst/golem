# R13.4 -- two claims, one gate, and a dead subsystem replaced rather than repaired

## Outcome

A paired device presenting a valid client certificate **and** a live user factor
can use the write surface; either one missing is refused with a 401 that names
which. Revocation bites on the next request. Enrolment cannot be started except
locally. An unpaired browser still gets the read-only dashboard. See
[[Device Authentication]].

## The thing worth writing down

**~1,180 lines of this task were already merged on `main`, and none of it ran.**

An earlier attempt had landed `src/security/{device-catalog,device-cert-builder,device-credentials,user-factor}.ts`,
`src/cli/commands/devices-auth.ts` and `src/proxy/mount-mtls.ts`. It looked
finished. It was not reachable:

- `devices-auth.ts` was never registered in `program.ts` — `golem device` did not
  exist as a command;
- `mount-mtls.ts` was imported by nothing;
- `requestCert` appeared nowhere in the repository, so no server ever asked a
  client for a certificate — the mTLS could not have worked even if the
  middleware had been mounted;
- the only `devices` test in the tree was about Ollama model slots;
- and `user-factor.ts` carried the line *"Passkey/WebAuthn measured on this
  platform (verification-notes §143)"* — a section that is about R13.2's
  conversation store. **The measurement did not exist.**

There was also a latent trap: `isWriteSurface()` returned true for any POST,
which on the proxy is every Anthropic API request. Had it ever been mounted, the
developer's own Claude Code traffic would have demanded a device certificate and
a passcode.

USER decision 2026-08-29: **replace, don't repair.** The whole subsystem was
deleted and rewritten.

## Key lessons

- **"Merged" is not "wired".** Nothing in a green build, a green test suite or a
  clean lint distinguishes a working security subsystem from an unreferenced one.
  The check that would have caught it costs one line — `grep -rn "mount-mtls"`
  returning nothing — and it is worth running on any module whose failure mode is
  silence. A commit on `main` had already removed *dead imports* from this code
  without anyone asking why the code was dead.
- **A fabricated citation is worse than no citation.** "§143 says passkeys are
  impossible" reads as settled and stops the next person looking. The right
  answer was reachable in one fetch — and the *reason* in the fabricated version
  was wrong in a way that mattered: it blamed secure contexts, which are
  solvable, instead of the RP-ID naming rule, which is not. A gate that says
  MEASURED means a dated note with quotes, not a comment that sounds like one.
- **The blocker was naming, not transport.** WebAuthn's `rp.id` "needs to equal
  the origin's effective domain, or a domain suffix thereof". A LAN origin's
  effective domain is an IP literal, which is not a domain. Installing the CA on
  the phone — the fix everyone reaches for — changes nothing. The passcode is the
  mechanism, not the fallback, until R13.10 brings a real domain.
- **`rejectUnauthorized: false` was the right call, for a UX reason with a
  security consequence.** With it on, a bad client certificate dies in the
  handshake and the phone shows "cannot connect" — indistinguishable from Golem
  being off. Turning it off moves the decision into the guard, which answers 401
  *device:revoked* or *user:locked*. The certificate is not trusted any less: it
  is verified explicitly, per request, including the `clientAuth` EKU, because a
  chain proves who signed a key and not what the key may do.
- **No cache is the feature.** "Revocation takes effect on the next request" is
  guaranteed by reading the catalog every time and never caching it. Any cache
  would be an optimisation bought with the one property the gate names.
- **Check the device claim before the user claim.** An unknown caller then learns
  nothing about whether this project has a passcode.
- **Two CAs, not one.** The loopback CA is installed in a trust store so clients
  trust *our server*; the device CA is installed nowhere and identifies *a
  client*. One key for both would put a client-identity signer into the file the
  user is told to trust for server identities.
- **Ship the runnable command.** `golem device serve` exists specifically so this
  subsystem is not what it replaced. It refuses to start without a device CA
  rather than minting one — a trust root should never appear as a side effect of
  starting a server.

## What is deliberately NOT here

The write **application**. R13.4 builds the gate and one authenticated route
(`/api/whoami`) that demonstrates it; the session host that lives behind the
guard is R13.3/R13.5. `startWriteServer` takes an injected `handler` for exactly
that.

## Gate

`tsc --noEmit`, `npm run lint`, `npm run format:check`, `npm run verify:deps`,
`golem wiki check` all exit 0. `npx vitest run`: **3181 passed / 2 skipped /
0 failed**. +31 unit tests, +13 integration tests over real TLS handshakes.
Verified live from a built `dist/`: `device serve` refuses without a CA, starts
with one, answers an uncertificated GET with `device:no-certificate` and a bad
pairing code with `wrong-code`.
