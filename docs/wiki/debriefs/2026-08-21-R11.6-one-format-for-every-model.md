# R11.6 — one format for every model, and what the drop taught us

Shipped 2026-08-21, from a user reading their own status bar an hour after
[[Two status lines, one truth]] landed. In the same session a live
request died mid-stream, and answering *why* turned out to be the more
interesting finding.

## Outcome

```
⬢ Golem → ◆ anthropic (claude-opus-5) + ✎ openrouter (qwen/qwen3.7-flash) · 🗜 lossless · ✂ full
```

Every model segment wears `<gateway> (<model>)`; `+` joins models, `·` separates
kinds. Identical on both surfaces, pinned by the parity test.

## Key lessons

**The parity test earned its keep on the first change after it shipped.** Two
renderers, no shared module, and one instruction touching both. The test failed
on exactly the literal that had gone stale and passed everything else — so the
question "did I change both?" was answered in a second rather than by reading two
files in two languages. R10.24's real product was not the rendering fix; it was
this.

**A worker had no gateway to print, and nobody had noticed.**
`collectGolemState` was passing the raw `accountId` as a worker's "gateway", so a
target with no account rendered gateway-less while the chat segment happily said
"ollama" for the identical provider. The status JSON the VS Code extension reads
had no `gateway` field on a worker row at all. The formatting request could not be
satisfied without fixing the data first — a display asking for a field is a good
way to discover the field was never really there.

**A deliberate decision looks exactly like a bug until you find its test.**
Chasing the format, the brevity dial turned out to diverge too: the CLI prints
`✂ off`, the status bar omits the segment. It reads as an oversight — and one
edit away from "fixed" — but `render.test.js` pins it: *"statusBarText shows
brevity only while it is on"*. That is Decision 52's wording, written on purpose.
The change was reverted and the question handed back. Every parity fixture used
`brevity: "full"`, which is why R10.24 never compared the off case: **a parity
test only pins the states its fixtures visit.**

## The stream that died, and what Golem could not say

`API Error: Connection lost mid-response`, once in 130 sessions. The diagnosis —
an upstream/network drop on a 356k-token-context request, not Golem — came from
the client's transcript, the process table, and the settings file. Almost none of
it came from Golem.

- `proxy.log`: **no timestamps.** 11,655 `routed to "anthropic"` lines that cannot
  be placed in time.
- **Nothing is logged when a request ends** — only the routing decision, taken
  before forwarding. A request that dies looks exactly like one that succeeded.
- Telemetry records savings, not outcomes, so a failed request writes nothing.

The lesson is the uncomfortable one for a project whose pillar is honest
observability: **we could not prove our own innocence.** The ruling-out was real
(same pid throughout, no error lines, a 600s idle timeout against a 7.8s gap) but
every one of those facts came from outside the proxy.

And there is a signal only Golem can see: a native SSE stream that ends without
`message_stop` **was** truncated, and the proxy is holding both sockets when it
happens. R10.23 taught it to relay an explicit `error` frame; the no-frame case is
R11.7 — filed, not built.
