# T7 — entropy sweep eating repo paths

Fixed the false-positive documented in verification-notes §49: the high-entropy
backstop's candidate regex includes `/`, `-`, `_` in its charset (needed, since
real base64/base64url secrets legitimately contain them), which let a whole
repo path or a versioned/ADR-style filename form one candidate token and clear
the Shannon-entropy threshold on the strength of its mixed case and digits.

Fix: `isPathLikeToken` in `src/pipeline/redaction-rules.ts` — split the
candidate on `/-_`, require every chunk to be purely alphabetic or purely
numeric. Real secret material drawn from a 64-symbol alphabet essentially never
lands every chunk in one character class, so this doesn't reopen under-redaction;
proven by a regression case (dash-delimited token with mixed letter/digit
chunks still redacts). Full writeup and the other known false-positive classes
(§31 integrity hashes, §37 unbounded length) are now in
[[Redaction Stage]] rather than restated here.

Verification: `tsc --noEmit` clean, `npm run lint` clean, `npm run format:check`
clean, full `npm test` — 70 files / 666 tests passing, including 3 new cases in
`tests/unit/pipeline/redaction-audit.test.ts` (two negative: path, slugged
filename; one positive regression: mixed-chunk secret still redacts).

## Notable while debugging: false alarm from the pipeline itself

Per user instruction this task ran at slider level 5. Partway through, a Read
of the very file just edited appeared to show a path replaced with
`[REDACTED:high-entropy:N]`, and a Grep appeared to show forward-slashes
mangled to backslashes — looked like a novel corruption bug beyond T7's scope.
Ground-truth check (slider dropped to 0, literal-string `grep -c` counts, and
ultimately just trusting the vitest run over any visual tool-output diff)
showed the disk file was untouched throughout: what I was looking at was a
live, harmless repro of the exact bug T7 targets, happening to my own view of
a Read result at level 5, plus one of my own diagnostic mistakes (a bad grep
escape pattern) layered on top. No corruption occurred; nothing needed fixing
beyond the T7 change itself.

Lesson for future debugging at high slider levels: don't trust a repeated
near-identical Read/Grep diff as ground truth if the pipeline itself is a
suspect — drop to level 0 or shell out to a process-level check (test runner,
`grep -c`, direct byte count) instead.

## Discovered but out of scope

The credit-card rule's Luhn gate accepts unbounded space/dash-separated digit
runs before the 13-19-digit length check, so a long run of small
space-separated numbers can coincidentally contain a window that passes Luhn
and gets wrongly redacted as `[REDACTED:credit-card:n]`. Not fixed here, not
yet in verification-notes.md — flagged for a future task.
