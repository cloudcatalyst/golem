# R12.7 — the channel that appeared

Written answer, no code. The task was to re-verify — not restate — Decision 37's
"a phone cannot resume a session" and ADR-0006's capability-3 row ("Structurally
unavailable"), against the *current* Claude Code rather than the one measured in
2026-07. Full evidence, with quotes, dates and URLs, is
`docs/plan/verification-notes.md` §136. See [[Architecture]] for where the
companion app sits.

## Outcome

**The outcome the brief predicted, for none of the reasons it predicted.** There is
still no continue button, and R12.5 still ships a sentence where one might have
gone. But "structurally impossible" is dead: measured against the installed client
`2.1.235`, Claude Code now has three supported ways to put a turn into a running
session, and the material one is an **MCP server**.

- **Channels** (research preview): "a channel is an MCP server that pushes events
  into your running Claude Code session." Declare
  `capabilities.experimental['claude/channel']`, emit `notifications/claude/channel`
  with `content` and `meta` over stdio, and the event reaches the model as
  `<channel source="…">`. Golem is already an MCP server, so this seam is reachable
  in principle with no new dependency.
- **Remote Control** (`claude --rc`, `claude remote-control`): the Claude app or
  claude.ai drives your live local session, with Anthropic's own push when Claude
  needs a decision.
- **Cross-session messaging** (v2.1.224+, macOS/Linux only): `SendMessage`, and the
  sentence that settles the idle question — "when the receiving session is idle,
  Claude Code starts a new turn with the message."

Decision 37 was two claims wearing one sentence. The **architectural** half still
holds verbatim — the proxy sits below Claude Code, `/resume` is a client-side slash
command it never sees, nothing was added to the request path. The **product** half
("no IPC into an already-running interactive session", "the only techniques that
reach a live TUI are tmux `send-keys` / keystroke injection") is now false. So
ADR-0006's capability-3 row and spec Decision 59(g) are superseded **on their
reason, not their outcome**, and both got dated pointers to §136 rather than an
agent's silent rewrite. The Decision 59(g) amendment is the user's to make.

## Key lessons

**A re-verification that can only confirm is not a re-verification.** This task
existed because someone suspected the answer had aged, and it had — after five
weeks. The brief's own framing ("Decision 37 settled it… the reasoning transfers
whole") was the thing under test, and treating it as the premise would have
produced a confident, well-cited, wrong note. The habit that saved it was cheap:
read the current CLI reference end to end before quoting a decision about the CLI.

**"We cannot" and "we will not" are different sentences, and only one of them
rots.** Decision 37 wrote a capability claim where a discipline claim was the
durable one. Discipline survives a vendor release; impossibility does not. Every
place Golem says "structurally" is a place to check the date.

**Five weeks is long enough to invalidate a load-bearing fact about a dependency
that ships daily.** The client moved from "no reverse channel" to a documented
channel protocol, a permission-relay extension, background sessions, `attach`,
`respawn`, and a first-party remote-control product — the same ground ADR-0006 was
accepted to cover.

**The objection that survived was not technical.** Four of the five reasons not to
build it are contingent (research preview, allowlist, unstable contract, no
delivery ack — all could be fixed by Anthropic next week). The fifth is not:
**authoring a turn is a larger authority than answering one.** ADR-0002's class
line constrains tool calls the model *proposes*; injected free text can propose
anything, so it routes around the line rather than sitting behind it. That is why
this is a user decision (**R12.10**) and not a UI affordance.

**No delivery acknowledgement is a UI fact, not a plumbing detail.** "Claude Code
doesn't acknowledge notifications… drops the events silently and returns no error
to your server." A button that cannot learn whether its message landed can only
lie. ADR-0006 answers ambiguity with "silence denies", but silence on a *send* has
no safe reading, because nothing was held open to deny.

**Approve/deny is a different kind of thing, and the client agrees.** Anthropic's
own permission relay (`notifications/claude/channel/permission_request`) holds the
local dialog open in parallel and applies whichever answer arrives first —
independently converging on R12.3's design. The channel exists there because the
question already exists. "Continue" has to invent one.

## What R12.5 shows instead

> **There is no prompt box — this screen can answer what the agent is already
> asking, but nothing here can start a turn.**

Scoped to *this screen* deliberately: "no phone can steer a session" would now be
false, since Remote Control does exactly that. The sentence claims only what is
true of Golem's surface and names the reason a reader can act on — the hook holds a
question open, and that is the only thing there is to answer. Same register as
R12.6's *"Alerts are off — this screen only updates while it is open."*

## The honest substitute, and its naming rules

**Enqueue, do not inject.** R5.1's durable queue is real (`golem task
add|list|show|resume|cancel`, `notBefore`, `isResumable`, headless
`claude --resume <id> -p …` — §65), and it is the only path where a phone changes
what happens next without pretending work has begun. Decided here: **not in
R12.5.** A phone that can enqueue a prompt can enqueue any prompt, which the next
headless resume runs with the local session's permissions — capability 2's blast
radius without capability 2's held-open hook. If it is ever surfaced (R12.10), it
is labelled **"Add a task for later"** with **"Nothing runs until your laptop picks
it up."**, never grouped with Approve/Deny, and with no spinner: the only thing that
happened is that a file was written. The word "continue" is banned outright.

## Consistency with R12.6

No conflict, and not reopened. §135's push must be laptop-originated because the
blocked laptop is awake by definition; the same fact is why an enqueued task has
something local that *could* pick it up. Awake is not willing-to-begin-a-turn, and
nothing in the push path creates one.
