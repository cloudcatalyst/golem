# R10.2 — the flaky suite was paying for a delete per test, and hiding a real corruption bug

Related: [[R10.1 (part 1) — the first pancake was not burnt, it was just big]]

**Date:** 2026-08-13
**Task:** R10.2 (done)
**Outcome:** ten consecutive full-suite runs green — 2554 passed / 2 skipped / 204 files, zero failures. Before: 3–4 failures per run.

## The symptom

`npx vitest run` was intermittently red on a clean tree: 0–3 failures per run, a
different test each time, all passing in isolation. Five runs of one commit gave
5, 0, 3, 0, 3 failures.

## Three wrong turns worth recording

**1. "Timeouts are flake, assertions are real" is false here.** Most failures
were `Test timed out in 20000ms`, but one presented as
`AssertionError: expected true to be false` — a backoff test that waits 400ms for
a worker dying at 300ms, where under load the exit event misses the margin. Any
timing-margin assertion over a real subprocess fails this way. **Re-running the
file in isolation is the only reliable classifier.**

**2. The first diagnosis was wrong.** The task originally recorded *process-spawn
starvation*. Measurement killed it: only 7 test files spawn a subprocess at all,
and two of the three usual failures spawn nothing.

**3. The obvious expensive thing wasn't expensive.** `ensureLoopbackCert` looked
like the culprit until I checked: it uses EC (`prime256v1`), not RSA. About a
millisecond.

Each wrong turn cost minutes; acting on any of them would have cost a day of
building the wrong fix.

## The actual cause — already written down, never connected

`tests/helpers/tmp.ts` explained the mechanism in its own doc comment: on Windows
a recursive delete of a just-written tree races the indexer and the virus
scanner, which is why `rmTemp` carries `maxRetries: 5, retryDelay: 50`. **A
delete that loses the race sleeps and retries while holding the test open.**

82 files were paying one create-and-delete cycle *per test* — thousands per run,
every one retry-prone. `cli-init.test.ts` alone makes 36 `golemInit()` calls,
each writing ~20 files into its own tree.

Two independent pieces of evidence that this was known but never linked to the
timeouts: the 20s `testTimeout` had been raised from 5s with a comment describing
these exact symptoms ("timing out intermittently, on a different one each run"),
and `checkpoint-ledger.test.ts` carries a local `testTimeout: 90_000` whose
comment says "raise the ceiling rather than lose the file to flakes."

**The lesson: the codebase had already diagnosed this twice and treated the
symptom both times.** Two workarounds in two places, neither connected to the
other. When you find a local workaround for flakiness, check whether it is the
third one.

## The fix

`useTempDirs(prefix)`: one temp root per FILE, a fresh `mkdtemp` subdirectory per
test, one recursive delete per file. **Isolation is unchanged** — every test
still gets a directory nobody else can see. Only the reclaim point moved. 67
files converted.

## The bug that fell out of it

Under load, `golem init` started failing with `settings.json is not valid JSON`
— against a file it had written itself, seconds earlier, in a fresh temp dir.

That is not a flake shape, so it got investigated rather than re-run.
`cli/json-file.ts` wrote with a plain `writeFile`, leaving a window in which the
file exists holding a *prefix* of the new content — and `.claude/settings.json`
is read back several times during a single `golem init`. The fix is
temp-file-then-rename, exactly the durability `config/file-io.ts` already gave
`.golem/settings*.json`.

**The same window would corrupt a user's real settings if the process died
mid-write.** The load didn't cause the bug; it widened a window that was always
there.

It lived in a *fourth* copy of `readJsonObject`/`writeJsonObject`, in
`hooks/settings-extras.ts`, differing from the others only in an error message.
That is now the second time in this batch that consolidating duplicate JSON
helpers exposed a data-loss bug — the first was `golem proxy wire` clobbering a
malformed settings file.

## Where a timeout increase IS defensible

After both structural fixes, what remained was pure contention. The task had
ruled out "raising `testTimeout`" *unless a measurement said why* — so the
measurement got made: **`golemInit` costs 298ms on an idle machine** (10 calls in
2981ms). A test doing one or two of them and tripping 20s is a **66× slowdown of
work that is small and real** — not a hung test, not a slow code path. ~15 vitest
workers doing filesystem work on Windows, where every file creation is a
virus-scanner event.

So two files — `cli-init.test.ts` and `golem-init-smoke.test.ts` — set
`testTimeout: 90_000` locally with that measurement recorded inline. The 20s
default still guards the other 202. That is the distinction between a targeted
ceiling and the blanket increase the task forbade: **the blanket version hides
future regressions everywhere; the local one hides nothing that was ever
guarded.**

The ordering matters and is the transferable part: **structural fixes first,
measure what is left, and only then decide whether the remainder is real work
that needs more room.** Raising the timeout first would have "fixed" it and left
both the delete churn and the corruption bug in place — which is exactly what
happened the last two times.
