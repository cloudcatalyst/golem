# R8.M1 — three upstream-switch UI defects (2026-08-01)

Found by live debugging, not by a proposal: *"the VS Code status bar says Poolside but
that isn't the upstream we're using."* One report, three independent defects. Only the
first produced the reported symptom; the other two were sitting next to it.

Related: [[Configuration Surfaces]], [[Dogfooding Golem]].

## 1. The status banner read a leaf the proxy no longer routes by

`resolvePort` in [src/cli/program.ts](../../../src/cli/program.ts) returned
`settings.proxy.upstream_base_url` — the top-level legacy leaf. Every
`golem proxy status` / `start` / `restart` banner therefore announced
`-> https://api.anthropic.com` while the proxy was correctly serving an active
OpenRouter account.

**The proxy was never wrong.** `buildProxyFromSettings` resolves the active account
through `resolveActiveUpstream`; only the *display* read the old leaf. That is the worse
failure mode of the two: routing that is correct but reported wrong reads as a failed
`golem account use`, so the user's next move is to re-run the thing that already worked.

Fixed by resolving the banner through `resolveUpstreamDisplay(settings.proxy).baseUrl` —
the same resolver the runtime uses, so the two cannot drift apart again. The general
lesson is the one R8.8 and the effective-level fix each landed on independently: a
display must be *derived from* the mechanism, never a parallel reading of the same
settings.

## 2. Panel setting toggles were silently masked by config precedence

`controlRowHtml` rendered the scope `<select>` in `writableScopes` order and marked
nothing `selected`, so the browser pre-selected the first option — `project`.

Precedence is `default < user < project < local < env`. Toggling a setting whose value is
owned by the `local` layer wrote `project`, `local` kept winning, and the next 15s refresh
snapped the row back to its old value. The control was not broken; it was *outvoted*, and
the UI had no way to say so. This is why `inference.local_coder_enabled` could not be
turned off from the panel.

Fixed by pre-selecting the layer that owns the current value, falling back to the first
writable option when the owner isn't writable (`default`, `env`).

Worth naming as a pattern: **any UI over a layered config must select the owning layer by
default**, or every control silently becomes a no-op for exactly the users who have
customized that setting.

## 3. "Switch upstream…" paid a ~2.8s CLI round-trip on every open

`buildModel` normalized the account list with `Array.isArray(accounts) ? accounts : []`,
but `golem account list --json` emits the `AccountsReport` **object**
(`{active, active_unknown, accounts:[…]}`). The cache was therefore always empty, and
`pickAccount` fell through to a blocking CLI call — measured 2.6–3.0s, because
`collectAccounts` probes every account's credential store (one DPAPI file decryption per
account on Windows).

Fixed by accepting either shape. Note the defect was invisible to the tests *and* to the
eye: the quick-pick still showed the right accounts, just slowly. A shape mismatch that
degrades to a correct-but-slow path is harder to notice than one that throws.

## Out of scope / still open

- The ~2.8s cost of `golem account list --json` itself. The unwrap takes it off the
  quick-pick's critical path, but `fetchModel` still pays it on the 15s poll. Caching
  `store.status` is the obvious move if it shows up in a profile.
- Unrelated, found while running the gate: `tests/integration/checkpoint-ledger.test.ts`
  (R8.9) timed out at the 20s default under a full-suite run and passed in isolation —
  real `git` subprocess latency on Windows, not the code under test. Raised to 90s via
  `vi.setConfig`.
