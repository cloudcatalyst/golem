# R9.12 — the served-WebFetch red dot goes green, behind a CA that cannot lie

**Date:** 2026-08-10
**Task:** R9.12 (supersedes the decision recorded in R9.7)
**Notes:** verification-notes §122, §123, §124 (correcting §120 and §121)

## Outcome

A WebFetch served from Golem's cache now renders as a normal green tool call, by default,
in any session started with the wiring `golem init` writes. Every other session — no
wiring, no restart yet, cloud, Desktop-app-managed, or a machine where someone else owns
`NODE_EXTRA_CA_CERTS` — gets R9.7's deny-and-serve, byte for byte. No session is worse off
than before, which was the design constraint the whole shape was built around.

Both halves were proven by live `claude -p` runs against the built artifact, not by tests
alone:

| session | result |
|---|---|
| CA trusted | `is_error=false`; heading answered from context; **no network fetch** |
| no env | `is_error=true`, `NOT AN ERROR — Golem served this URL from its knowledge base…` |

## How it works

The endpoint serves a **stub**, not the page. That one decision is what makes the design
acceptable: WebFetch's per-fetch summarizer runs over a few hundred bytes of placeholder,
while the raw cached page reaches the model through `additionalContext` — un-summarized
and prompt-independent, so Decision 42 is preserved instead of inverted. The hook picks
per call between `allow`+rewrite and the `deny` floor, and the floor is the *original*
code path rather than a reimplementation of it, so its framing survives every failure.

## Key lessons

**1. The untested field in the contract was the whole answer.** §115 tabulated
`additionalContext` from the docs and never exercised it. Exercising it took one temporary
hook branch and three fetches, and it overturned the standing decision. Two years of
reasoning downstream of an unexercised line in a table.

**2. `additionalContext` survives a failed tool call.** Measured with a rewrite to a dead
port: `ECONNREFUSED`, and the payload still arrived intact. This is the property that
makes an optimistic rewrite safe — the worst case stops being "lost fetch" and becomes
"content delivered, ugly transcript". §121's blocker B was simply false.

**3. Measure against the client you actually ship to.** §121 validated the `CA:FALSE` leaf
trick against **Node/OpenSSL** and concluded "ship a leaf, never a CA". Claude Code is a
compiled **Bun** binary using **BoringSSL**, which refuses a leaf anchor outright. The same
recipe, the same command, opposite results — and the wrong stack cost a full build cycle
plus a written-up REGRESSED verdict before the `OPENSSL_internal` string in an error
message gave it away. When a finding rests on TLS, crypto, or parsing behaviour, name the
implementation, not the language.

**4. Always run the control.** When our hand-rolled certificate failed, the obvious
suspect was the hand-rolled DER. Generating the identical shape with `openssl` and
watching it fail the same way is what redirected the investigation from "our encoder is
buggy" to "this client rejects this class of anchor". One extra command; it changed the
conclusion.

**5. A forbidden thing and a dangerous thing are not the same thing.** The rule was "no
CA, ever", written when a CA meant unlimited signing power. `nameConstraints` splits those
apart: the shipped CA is accepted as an anchor yet provably cannot issue a certificate for
`api.anthropic.com` — refused by the client with `permitted subtree violation`. The right
move on hitting the boundary was to ask *what the boundary was protecting*, then close that
specific hole, rather than either obeying the rule or quietly breaking it.

**6. Fail-closed beats fail-open, and BoringSSL agrees.** An `iPAddress` constraint makes
BoringSSL reject the whole anchor (`unsupported name constraint type`) rather than ignore
the extension it cannot parse. That is the safe direction, and it is why the residual —
the IP name form staying unconstrained — is documented rather than papered over.

**7. Prompt text is behaviour, and needs measuring like behaviour.** The first stub said
"placeholder only, no page text here"; the model then reported a **succeeded** fetch as
having errored, which invites a pointless retry. The stub and the context note now both
assert success explicitly. A string that changes what the model concludes is not copy.

**8. Say what you trusted.** Turning this on by default installs a CA into Claude Code's
trust store. `golem init` prints what it trusted, why, and — specifically — what the CA
cannot do; `--no-loopback-cert` declines; `golem uninit` removes it; `golem status`
separates "wired" from "in effect", because §112 means a correct settings file plus no
restart still means red.

## Costs and residual risk

- One summarizer call over the stub per served fetch. Small, fixed, not zero.
- The `iPAddress` name form cannot be constrained. Whoever can read the CA key can mint a
  certificate for any **IP literal** that a session started with this env would trust. They
  cannot mint one for any **hostname** outside `*.golem.invalid`, and Claude Code reaches
  `api.anthropic.com` by hostname. `pathlen:0` blocks sub-CAs. Keys are `0o600` in
  `.golem/loopback/`.

## Found in passing, filed not folded

- `golem uninit` stopped removing everything `golem init` adds — caught by an existing
  test, fixed here with the ownership rule extended to the CA.
- The `local-coder` gate denies **every** non-trivial code write. (Filed as R9.17. The
  cause recorded here at the time — "`session_id` rotates per tool call" — was inferred
  from two denials writing two different ids, and is **wrong**: the id is stable, and the
  real defect was a single-slot state that concurrent sessions overwrote.)
- `golem proxy restart` reports "did not come up" for a proxy that is running. (Filed as
  R9.18. Also misdiagnosed here as a shutdown/port-release issue — port release measured at
  **4ms**; the real cause was 6.7s of credential resolution against an 8s `waitForPort`
  budget.)

## Addendum — the provenance label, and a swap that never fired

Asked to tell a cache-served fetch from a live one, three attempts landed in the wrong
place before one worked. Each failure was informative:

1. **Wrong hook.** The label went into the WebFetch PostToolUse hook — which `golem init`
   registers `async: true`, so its stdout is discarded. That is *why* the module was
   documented store-only; the contract was right and I read past it. Output substitution
   has to come from the non-async CCR hook.
2. **Wrong assumption about the payload.** Suspecting PostToolUse saw the original URL
   rather than the rewrite, I probed instead of guessing: it sees the **rewritten** URL,
   `s=hit&a=14h%20ago` intact. Not the problem.
3. **A real bug underneath.** The label still didn't fire, because `findTextSlot` returned
   null: WebFetch answers with `{bytes, code, codeText, result, durationMs, url}` and the
   key list was `output|stdout|content|text`. **The oversized-output swap had therefore
   never fired for WebFetch at all** — silently, because a missed swap looks exactly like a
   small page. `web-fetch.ts`'s own `textOf()` had included `result` since it was written.
   Two lists of the same knowledge, drifting where nothing compared them.

### Then the label turned out to be invisible anyway

It works — the receipt is in `updatedToolOutput` and in the transcript — but the user
reported seeing no change. The VS Code extension renders a collapsed WebFetch as
`Fetched from {url}`, generated from the **original input URL**, with no result line. So:

- the row itself cannot be labelled (we do not own it, and our rewrite is not what it shows)
- `updatedToolOutput` is only visible once the entry is revealed
- `systemMessage` — documented as "Warning message shown to the user" — **never appeared**,
  neither in the VS Code view nor anywhere in a headless run's event stream

The resolution was to accept it: **Focus view (`Ctrl+Alt+F`)** reveals tool results, and the
receipt is unconditionally in the session transcript. Which is arguably the right end state
— R9.12's goal was that a served fetch look like a *normal* fetch, and it does.

**Lesson, again:** three of the four dead ends here were assumptions about someone else's
renderer or contract. The two-minute probes — dump the payload, grep the cached doc, read
the transcript JSONL — each settled in one shot what reasoning had got wrong.
