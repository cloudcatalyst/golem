# R12.11 — channel wins, conditionally: `ask` is not `deny`, and the fix is one hook away

**Question this spike answers:** can Golem enforce ADR-0002's class line
(`destructive`/`outward` never remotely approvable, ADR-0006 §2) on an
approval that arrives through Anthropic's own channel relay — the thing [[R12.7 — the channel that appeared: continue is not approve, and the reason expired]] found already exists — or does holding that line require the
from-scratch pairing/relay/hosted-account stack that R12.3/R12.4/R12.8/R12.9
were paused to build? A spike: the deliverable is a decision with evidence,
not code. Full evidence lives in `docs/plan/verification-notes.md` §141;
this page is the durable pointer into it.

## The load-bearing discovery

`src/autonomy/gate.ts` — `decideGate` — never emits `deny`. Its emission type
is `"allow" | "ask" | null`; for `destructive`/`outward` it emits `{emit:
"ask", ...}` at **every** autonomy level, and `src/hooks/pre-tool-use.ts`
turns that into `PreToolUse`'s `permissionDecision: "ask"`. `ask` forces a
question; it does not resolve one. That distinction is the whole spike: a
forced question is exactly what opens a permission dialog, and Anthropic's
channel relay (`notifications/claude/channel/permission_request`, per R12.7)
is documented to notify a connected channel of that dialog with no exemption
field for a particular call. So Golem's *shipped* mechanism does not, by
itself, protect the class line against the relay — `ask` and "remotely
answerable" turn out to be the same event once a dialog exists.

## What closes the gap without a new transport

`code.claude.com/docs/en/hooks` (re-fetched 2026-08-22, fresh copy confirmed
by cache `fetchedAt`/byte-length, not reused from a 12-day-stale copy)
documents an event Golem does not register: **`PermissionRequest`**. It
fires "when Claude Code is about to ask you for permission" — strictly
before `PreToolUse`'s `ask` would otherwise lead to a dialog — with a
`hookSpecificOutput.decision.behavior: "allow" | "deny"` shape, distinct
from `PreToolUse`'s flat `permissionDecision`. In non-interactive sessions,
"if no hook returns a decision, it denies the tool call." If a
`PermissionRequest` hook resolves `destructive`/`outward` with a real `deny`
before any dialog exists, there is nothing left for a relay to be notified
of — by construction, not by exemption. That is a change to a hook Golem
already owns (`src/hooks/`), not a new transport, a new account model, or a
new pairing mechanism.

## The five items, each dated and marked

1. **Ordering** — documented: `PermissionRequest` runs before `PreToolUse`
   would lead to a dialog. Observed (headless `-p`, 4 runs): a forced `ask`
   resolved to a silent denial with no dialog and no relay notification —
   now *explained*, not merely observed, by the documented headless fallback
   ("if no hook returns a decision, it denies the tool call"). The
   interactive case — the one that actually decides this — is
   **documented-only**: no PTY test harness exists in this repo, and
   building one is out of this spike's scope (arguably against CLAUDE.md's
   "no heavyweight native deps" rule). Filed as `R12.13`, `owner: user`.
2. **Does a `deny` survive a remote `allow`?** — Golem currently has no
   `deny` to test; the question is near-vacuous for the shipped mechanism.
   Re-posed for the mechanism `R12.12` would add (`PermissionRequest`-level
   `deny`): documented ordering says it resolves first, so there is no
   remote `allow` left to race against — but this, too, is
   **documented-only** until `R12.13`'s live run.
3. **Preview constraints, costed honestly** — reconfirmed from §136: opt-in
   per session by launch flag, off the curated allowlist, no delivery
   acknowledgement for reply-tool messages (a separate gap from the
   permission-relay question above — kept distinct, not conflated).
4. **What a channel route does NOT give — R12.5's disposition** — capability
   2 (remote authorize) is carried first-party once the hook fix ships;
   capability 1 (observe) was never in question. **Reduce, don't cancel,
   R12.5**: struck to observe-only, `R12.3`'s deadline dependency and
   `R12.4`'s mTLS-pairing dependency removed with the tasks they depended on.
   Pairing/auth for the reduced, read-only scope is explicitly left
   undesigned — not answered by this spike.
5. **The auth collision** — reconfirmed: the channel path wants
   claude.ai/Console auth; Golem's account routing is a separate axis. Still
   unestablished as a *general* claim across every account shape; observed
   only for the Pro/Max-individual, no-org case this session's live testing
   used, where the org-level `channelsEnabled` check is skipped entirely.

## Unexplained, flagged rather than resolved

Across four live headless `claude -p` runs, the throwaway test channel
connected in two and failed to connect in the other two, with no correlation
found to hook presence or absence. Ruled out: the channel script itself
(works standalone); the documented `MCP_PROTOCOL_NEGOTIATION`/`2026-07-28`
rejection mode (the installed SDK does not list that revision at all). No
root cause confirmed — recorded honestly as open, not papered over.

## Recommendation, and the one property that decided it

**Channel wins — conditionally.** The deciding property: whether the class
line resolves *before* a dialog can exist, not merely whether a dialog gets a
question. Golem's `ask`-at-`PreToolUse` mechanism does not carry that
property; the documented (not yet live-confirmed) `PermissionRequest` event
does. That is why the recommendation is conditional rather than flat: it
rests on a live interactive confirmation (`R12.13`) that could not be run in
this spike's headless-only environment.

## Disposition

- **Cancelled** (`golem task cancel`): `R12.3`, `R12.4`, `R12.8`, `R12.9` —
  the from-scratch pairing/relay/hosted-account stack a paused
  [[R12.1 — ADR-0006, and the line that kept ADR-0002 intact]] set aside for
  this spike to judge. Each cancelled task keeps its original PAUSED note
  plus a dated CANCELLED block pointing here and at `verification-notes` §141.
- **Reduced**: `R12.5`, to capability 1 (observe) only.
- **Filed**: `R12.12` (`owner: agent`) — register a `PermissionRequest` hook
  alongside the existing `PreToolUse` one, emitting a real `deny` for
  `destructive`/`outward`, keeping the existing `ask` as defense-in-depth.
  `R12.13` (`owner: user`) — the live interactive confirmation `R12.12`'s
  unit tests structurally cannot reach, because it needs a real terminal and
  no PTY harness exists in-repo.
- **ADR-0006** carries a dated re-verification block for capability 2 and an
  updated capability-table row, alongside the existing R12.7/capability-3
  block — the pattern is now two "reason expired, outcome reconsidered"
  entries in the same document, not a silent rewrite of either.

## Lesson

The pre-compaction draft of this spike was trending toward "neither yet,
unclear" on the assumption that Golem's mechanism was already a `deny`.
Reading `src/autonomy/gate.ts` directly — rather than trusting a throwaway
test hook's comment, which turned out to describe a shape Golem does not
have — is what turned an inconclusive spike into a decisive, evidenced one.
Second lesson, same shape as R12.7's: don't trust an AI-summarized fetch for
a load-bearing negative finding when the underlying cached document is one
`indexOf` away — a summarized WebFetch response for this spike arrived with
an explicit truncation caveat ("treat the negative finding as scoped to the
text shown, not to the page"), and the quotes that actually decided this
spike came from reading the cached JSON directly.
