# R8.14 — the write half, and why it is mostly refusals

`golem pkg` shipped read-only in Decision 53(e) on purpose. R8.14 is the
deliberately-deferred other half: `install`, `remove`, `upgrade`. See
[[Managed Tools]] for the standing policy this implements.

## Outcome

`golem pkg install|remove|upgrade <id> [--yes] [--dry-run]`, backed by a new
`src/pkg/install.ts` and a declarative `PkgInstaller` recipe on the manifest row.
Two rows get an automated path (`caveman` via `claude plugin`,
`typescript-language-server` via global `npm`); every other row refuses with a
reason and its documented human route. +23 tests, `wiki check` clean, tsc/biome
green.

Verified live on this machine: the refusal matrix, both exit codes (`1` refused,
`3` consent-not-given, `0` dry-run), the plan preview, and the corrected
detection. **Not** verified live: an actual install — that is an outward,
machine-modifying act, and the two runnable recipes would have installed software
nobody asked for.

## What it replaced

There was already a `pkgInstall` in `src/cli/pkg.ts`. It hardcoded Caveman,
built two `execSync` **shell strings**, had no pin, no consent, no audit line, and
no route for `remove` or `upgrade`. It shipped as an unremarked-on convenience,
and it violated three standing rules at once (argument-array spawn, explicit
consent for outward acts, pinned versions). Worth noting as a pattern: the
read-only surface was carefully designed and documented, and then a write path
appeared inside it later without anyone re-reading the constraints the read-only
decision had written down.

## Key lessons

**1. When a task's constraints are all refusals, the deliverable is the refusal
matrix — and it belongs in pure code.** `planPkgAction` decides what *would*
happen and returns either a runnable plan or a refusal with a reason. It spawns
nothing, touches no filesystem, and takes no config, so all six refusal branches
are unit tests rather than an integration harness, and `--dry-run` can print the
exact argv before anyone consents. The executor is a separate function whose
runner is injectable — every execution property (order, stop-on-failure,
tolerated failures, installer-not-on-PATH) is tested without spawning an
installer.

**2. Consult the gate; do not re-implement its conclusion.** The obvious
implementation of "installing needs consent" is `if (!consent) return`. Instead
`runPkgAction` asks `decideGate(level, "outward")` and acts on its answer, which
is `ask` at every autonomy level including the most permissive. Two things follow
that the `if` would not have given: the user sees the gate's *own* reason
("this action leaves the machine / is hard to reverse — approval required (no
autonomy level auto-approves it)"), and the test that matters can loop over
`AUTONOMY_LEVELS` and assert consent is still required at each — a regression in
ADR-0002's matrix would fail *here* too, rather than silently making installs
auto-approvable.

**3. "Upgrade must not move a pin" is best enforced by making upgrade *be*
install.** The temptation is a version-comparison guard. Instead a
`"manifest"`-pinned row declares `upgrade: "reinstall"`, and the planner expands
that to the install steps — so an upgrade's argv is byte-identical to install's
and contains no argument that *could* name a newer version. There is nothing to
guard because there is nothing to move. Playbook-pinned rows (both Headroom rows,
governed by T-C4) refuse `upgrade` outright and say why. Drift guards then assert
those two shapes are the only legal ones, so the invariant lives in the data and a
new row cannot quietly invent a third case.

**4. An honest "no" needs somewhere to be recorded.** Caveman's upstream
installer has no version selector at all (§133). Rather than fabricate a pin or
leave the field blank, the row records `pinPolicy: "upstream-unpinned"` — the
registry's job is to say *who governs the version*, and "the upstream does, and
gives us no say" is a real answer. A drift guard enforces the corollary:
`upstream-unpinned` must not co-exist with a pin.

**5. Adding a `remove` verb changed what the read half had to prove — and it was
lying.** `pluginOnDisk` checked for `~/.claude/plugins/cache/<marketplace>/<name>/`.
`claude plugin uninstall` empties `installed_plugins.json` and leaves that cache
behind, so `golem pkg list` reported `[found] caveman` while `claude plugin list`
said "No plugins installed" — for ten days, on the surface whose entire selling
point is not claiming a state it is not in. The registry file is now authoritative
in both directions, with the cache as fallback only where no registry exists.

**A cache is not an inventory.** When detection must answer "is this installed",
read the file the tool itself would have to update to answer that question. A
directory that merely exists proves someone once installed it — a different claim.
The write verb is what made the stale positive load-bearing: a `remove` whose
result `list` cannot see is worse than no `remove` at all.

**6. Scope discipline cut two rows that looked easy.** `unpdf` and
`web-tree-sitter` are npm modules, so `npm install <pin>` seemed like a free
recipe — but they resolve inside *Golem's own* install, so a project-local install
would not land on its resolver path and detection would keep saying "not found"
after a successful-looking install. They are refused, with a drift guard
(`a module row must not carry an installer`) so nobody re-adds them. `uv`,
`ollama` and `rtk` are refused because their installers are shell scripts or OS
packages — exactly the shell-string spawning the task forbids.
