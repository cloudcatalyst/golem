# R9.22 — the CA trust moves to the scope that was always right for it

Related: [[R9.12 — the served-WebFetch red dot goes green, behind a CA that cannot lie]]
(the wiring this corrects), [[Configuration Surfaces]], [[Web Cache]]

**Date:** 2026-08-10
**Task:** R9.22
**Notes:** verification-notes §13 (settings precedence), §121-C (the ownership rule)

## Outcome

`golem init` no longer writes a machine-absolute path into a committed file. The
loopback CA trust R9.12 shipped now lands in `.claude/settings.local.json`, and a
Golem CA path left in the committed file by an earlier init is deleted on sight.

The gate was behavioural, so it was proven behaviourally: `golem init` on this repo
now produces **no diff at all** to `.claude/settings.json`, and the key appears in the
local file beside a pre-existing unrelated one it left untouched.

| scope | holds | why |
|---|---|---|
| `.claude/settings.json` (committed) | `ANTHROPIC_BASE_URL`, `ENABLE_TOOL_SEARCH` | portable; presence tells a teammate the project is wired |
| `.claude/settings.local.json` (gitignored) | `NODE_EXTRA_CA_CERTS` | machine-absolute; means nothing on another clone |

## What was actually wrong

Not the certificate, and not the trust — R9.12's design was sound. The defect was one
line of *placement*:

```json
"NODE_EXTRA_CA_CERTS": "D:\\Personar\\Source\\repos\\golem\\.golem\\loopback\\ca.pem"
```

in a file every clone receives. Nothing breaks — TLS still works and the green path
degrades to R9.7's deny floor — but Claude Code says so twice at every start on any
other machine, and `golem init` produced a diff that was actively bad to commit. A
feature that inflicts a warning on someone who never opted in is not free.

The local scope is *higher* precedence than the committed one (§13: managed → CLI args
→ `settings.local.json` → `settings.json` → `~/.claude/settings.json`), so moving the
key changed nothing about how it is read. Only about who receives it.

## The two halves that make it safe

**Self-heal, not just shadow.** Writing the local file alone would leave the stale path
sitting in everyone's diff, merely out-ranked. `isStaleGolemCaPath` recognises a Golem
CA from a *different* checkout root by its trailing `.golem/loopback/ca.pem` segments —
the signature of an older init on another machine — and deletes it. The tail is read off
our own path rather than hard-coded, so it follows `loopbackCaPath` if that ever moves.

**The ownership rule spans both files now.** §121-C says Golem sets this only when
nothing else owns it, because concatenating a user's TLS-inspection bundle with ours
makes a copy that goes stale when theirs rotates. With two scopes, that check has to
read both *before* writing either — a foreign value in the local file must veto a write
to the committed one, and vice versa. `uninit` inherited the same widening.

## The lesson

**A file-level fix has an in-memory half.** The design was easy; the trap was that
`init.ts` holds `settings` as a live object and writes it again in a later step (MCP
permissions). Healing the file on disk while that object still carried the key meant the
next write put the machine-absolute path straight back — a bug that would have passed
the new unit tests, because they exercise the wiring module directly and never reach
init's second write. The integration test on a real project directory is what would
have caught it; noticing the ordering first is what made it never happen.

**Every reader of a moved key has to move with it.** `golem status` read the committed
file to report `wired`. Left alone it would have reported `wired: false` on a correctly
wired project — worse than the original defect, because a working green path being
called broken is what sends someone debugging a non-problem.

**Watch what the test runner inherits.** The first `status` assertion failed on
`foreign_ca` being set — correctly. `trusted` and `foreign_ca` read *this process's*
environment, and the runner inherits the developer's own `NODE_EXTRA_CA_CERTS`. A temp
project cannot pin those; only `wired`, which reads files, is assertable there.

## Verification

`tsc --noEmit`, `biome check`, `npm run verify:deps` all clean. +10 tests (5 unit on the
new wiring helpers, 4 integration on init/uninit across both scopes, 1 on status's read
order). Full-suite runs showed unrelated timeout flakes under parallel load — including
`checkpoint-ledger` and `credentials-win32`, which this change cannot touch; every
affected file passes in isolation.
