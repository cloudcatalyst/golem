# R10.17/R10.18 — two "can't fail" fallbacks that turned diagnosable errors into silence

**Date:** 2026-08-14
**Tasks:** R10.17 (done), R10.18 (done)
**Outcome:** `Read` output is offloadable for the first time. An upstream that produces nothing now says so, on both the streaming and non-streaming paths.

Follow-on from [[R10.14/R10.15 — a screenshot became 125k tokens of prose, and the model answered with nothing]], which asked why nothing had trimmed the payload.

## The shared theme

Both defects are the same mistake wearing different clothes: **a fallback that
cannot fail, and therefore cannot report.**

| site | the "safe" fallback | what it cost |
|---|---|---|
| `toolResultText` (R10.14) | `JSON.stringify` any unknown block | a 500 KB image became prose |
| `findTextSlot` (R10.17) | unknown shape → pass through untouched | `Read` was never once offloaded |
| `openAIChatToAnthropic` (R10.18) | no content → emit `{type:"text",text:""}` | an empty answer, indistinguishable from silence |

Each is defensible in isolation and correct as *policy*. Together they meant a
broken request produced a well-formed, empty, 200 OK — the least debuggable
outcome available.

## R10.17 — `Read` was never offloaded, ever

`findTextSlot` probed only top-level keys of `tool_response`. `Read` nests:

```
{ type: "text", file: { filePath, content, numLines, startLine, totalLines } }
```

The text is at `file.content`. Nothing matched, so the handler took its
"shape we don't understand" branch every single time.

Surveying real transcripts made it undeniable:

| count | top-level keys | matched? |
|---|---|---|
| 270 | `…,stderr,stdout` (Bash) | `stdout` |
| 80 | `content,filePath,…` (Edit) | `content` |
| **62** | **`file,type`** ← `Read` | **no** |

This is **R9.12's bug verbatim** — `result` was missing from the same list, so
WebFetch never swapped either, also silently. Twice now, two lists of the same
thing drifting apart where nothing checked.

Fixed with an explicit `NESTED_TEXT_PATHS` list rather than a recursive hunt: a
recursive search would happily find some unrelated string in a payload it does
not understand at all. Tests are built from the **recorded** shapes — an invented
payload is exactly what let this pass for two releases.

## R10.18 — Golem was manufacturing the silence

```ts
if (content.length === 0) content.push({ type: "text", text: "" });
```

and the streaming twin, `// No content at all — emit a valid empty text block.`

The upstream said "I produced nothing." Golem said "here is a valid response
containing nothing." No client can tell that from a model deliberately answering
with silence, which is why Claude Code looped on it for a day.

Now:

- **non-streaming** → throws `EmptyCompletionError`, surfaced by the proxy as a
  502 naming the model. Matched by `err.name` in `server.ts` so the proxy keeps
  its layering and does not import from `providers/`.
- **streaming** → by `_flush` the headers and `message_start` are already out, so
  no HTTP status remains. The notice goes **in-band**, Golem-prefixed and
  attributed, per the honesty rail.
- `finish_reason: "length"` gets its own wording — it is a different problem with
  a different fix (raise `max_tokens`).
- Gated on content **and** tool calls, so a tool-only turn is untouched.

Live, on a real target:

```
{"type":"error","error":{"type":"api_error","message":"golem proxy: upstream model
 \"deepseek/deepseek-v4-flash-0731\" returned no content — it hit max_tokens before
 emitting any output; raise max_tokens or shorten the request"}}
```

## Two tests had to be changed, deliberately

`tolerates a missing content / usage…` and `emits a valid empty message when the
stream carries no content` both asserted the exact behaviour being removed. They
were rewritten rather than deleted — the fallback coverage they existed for now
rides on a response that has content, and the empty case is asserted on its own.

Worth noting: those tests were **passing the whole time**. A test can lock in a
misfeature just as firmly as a feature.

## Lesson

When adding a fallback for an input you do not understand, ask what tells you it
fired. If the answer is "nothing", the fallback is a silent failure with good
manners. All three sites here needed the same thing: a way to notice.

## Filed, not built

- **R10.16** — the keepalive gap: no eager `message_start`, no `ping`, and SSE
  comment keepalives dropped before they can help.
- **R10.19** — `headroom_config` keys are validated only when Headroom runs, so
  on a caching upstream an unreachable key is silently dropped after all.
- **R10.20** — thinking blocks are synthesized on the way out and discarded on
  the way back; needs a decision, not a patch.
