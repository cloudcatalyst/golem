# R3.6 — MEMORY-scope federated search (Headroom memory sidecar)

**Before:** `FederatedSearch.search()` (`src/interfaces/knowledge.ts`) has
declared `Scope = "knowledge" | "memory"` and `DEFAULT_SCOPES` including both
since C1, but `GolemKnowledgeBase.search()` never actually looked at the
memory half — a both-scopes request silently returned knowledge-only hits. R3
was explicitly gated on an ask before starting (R3_BATCH.md), since it's the
one task in the batch that pulls in an optional Python dependency; the user
approved starting it mid-batch.

## Verifying Headroom's actual memory API (CLAUDE.md "verify, don't assume")

The docs page (`headroom-docs.vercel.app/docs/memory`) describes
`HierarchicalMemory`, `MemoryConfig`, and a `MemoryCategory` import. Fetching
the pinned package's actual GitHub source (`headroom/memory/__init__.py`'s
`__all__`) turned up a real docs/source contradiction: **`MemoryCategory`
does not exist** in the shipped package. The verified, concrete surface is
the "Simple API" in `easy.py`:

```python
class Memory:
    def __init__(self, backend="local", db_path=None, ...): ...
    async def save(self, content, user_id, importance=0.5, ...) -> str: ...
    async def search(self, query, user_id, top_k=10, ...) -> list[MemoryResult]: ...
    async def clear(self, user_id) -> int: ...
    async def delete(self, memory_id) -> bool: ...
```

Critically, there is **no point-lookup-by-id** — only search/save/clear/delete.
That constrains two downstream design decisions below.

## Design decisions

- **`projectId` → Headroom's `user_id`.** `Memory.search()`/`.save()` require a
  `user_id`; Golem scopes everything by `projectId`. One Headroom memory
  namespace per Golem project.
- **Search-only, no write path.** Golem doesn't run through `headroom wrap`
  (mutually exclusive per verification-notes §5) and the frozen
  `FederatedSearch` contract has no write method. Nothing today populates
  Headroom's memory store, so in practice MEMORY-scope hits will be empty
  until a future population/write task exists. This is stated here plainly
  rather than left to be discovered later: R3.6 wires the plumbing, it does
  not create memory content.
- **Two independent sidecar processes, not one shared process.** The
  `[memory]` extra pulls sentence-transformers and (transitively) torch — much
  heavier than the bare `headroom-ai` the compression sidecar uses. They get
  separate opt-in settings (`compression.headroom_sidecar` vs
  `knowledge.memory_federation_enabled`), separate worker scripts
  (`headroom-worker.py` vs `headroom-memory-worker.py`), and separate PyPI
  extras strings, launched as separate `uv run` processes. Both TS classes
  still live in the one file, `headroom-adapter.ts`, per CLAUDE.md's literal
  hard rule that Headroom client imports are confined to that file.
- **No point-lookup means no `fetch` round-trip for memory hits.** The MCP
  `fetch` tool already special-cases `wiki:`-prefixed synthetic chunk ids
  (graph-first wiki hits were never stored in the vector driver either) by
  resolving them straight from the wiki store instead of calling
  `knowledge.getChunk()`. Memory-scope hits get the same shape of special
  case, but since Headroom's `Memory` API has no way to re-fetch a fact by id,
  `fetch` on a `memory:<id>` chunk id returns an explanatory error instead of
  attempting an unreliable fallback query. The hit's full content already
  rides in the `Hit.chunk.text` returned by `search()`; only the MCP tool's
  240-char `text_preview` truncates it.

## What was built

- `src/compression/memory-search.ts` — the neutral `MemorySearchProvider`
  seam (`search(query, projectId, k) => MemoryFact[] | null`), mirroring
  `SemanticCompressor`'s fail-open shape (`null` = unavailable).
- `src/compression/headroom-memory-worker.py` — new Python HTTP worker
  exposing `/health` + `/memory/search`, built on the verified `easy.Memory`
  API.
- `src/compression/headroom-adapter.ts` — extracted a private
  `HeadroomWorkerProcess` class (spawn/health-check/lazy-start/stop lifecycle)
  now shared by the existing `HeadroomSidecar` (behavior-preserved) and the
  new `HeadroomMemorySidecar implements MemorySearchProvider`.
- `GolemKnowledgeBase.search()` (`src/knowledge/knowledge-base.ts`) now runs
  KNOWLEDGE and MEMORY independently per the requested `scopes`, merges by
  score when both return hits, and degrades to whichever side actually
  produced results (including today's common case: MEMORY-scope silently
  empty). New `isMemoryChunkId()` export lets `src/mcp/server.ts`'s `fetch`
  handler recognize the synthetic `memory:<id>` prefix.
- `knowledge.memory_federation_enabled` config leaf (`src/config/schema.ts`),
  default off.
- `src/cli/build-knowledge.ts` constructs `HeadroomMemorySidecar` and passes
  it as `memorySearch` into `openKnowledgeBase()` only when the setting is on.

## Verified

`tests/fixtures/fake-headroom-memory-worker.mjs` +
`tests/integration/headroom-memory-adapter.test.ts` mirror the existing
`HeadroomSidecar` fake-worker coverage (start/health/search success, lazy
start, missing-command/non-200/startup-timeout/unhealthy fail-open) with no
real Python/uv/torch needed in CI. `tests/unit/knowledge/knowledge.test.ts`
adds federation-branch coverage: memory-only search with a provider, merged
knowledge+memory ranking, graceful degradation when the provider resolves
`null`, and the pre-existing knowledge-only behavior when no provider is
configured. Full gate (`tsc --noEmit`, `biome check .`, `format:check`,
`vitest run`) green — 93 files / 881 tests. (One `cli-init.test.ts` idempotency
test failed only when run under the full suite's parallel load — a
pre-existing Windows temp-dir race unrelated to any file this task touched;
it passes cleanly in isolation.)
