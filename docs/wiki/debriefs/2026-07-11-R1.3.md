# R1.3 — credit-card redaction false-positive fix (T-C3)

Fixes §50 (verification-notes.md): the `credit-card` rule's bare Luhn gate
let a space-separated ASCII byte dump with irregular digit grouping through
as a false-positive card redaction.

## What changed

- `src/pipeline/redaction-rules.ts` — added `hasConsistentSeparatorChar` and
  `hasUniformGrouping`, combined into exported `isCreditCardLike`. The
  `credit-card` rule's `validate` now points at `isCreditCardLike` instead of
  bare `luhnValid`. `luhnValid` itself is unchanged.
- `src/pipeline/index.ts` — re-exported `isCreditCardLike` from the barrel.
- `tests/unit/pipeline/redaction-audit.test.ts` — new
  `describe("T-C3: credit-card separator-format guard (§50)")`: the §50
  repro as a negative case (byte dump, irregular grouping, must NOT redact),
  plus two positive regression cases (contiguous and 4-4-4-4-grouped
  Luhn-valid test card numbers, must still redact).
- `docs/plan/verification-notes.md` — new §55 documenting the fix; §50 marked
  fixed with a pointer to §55.
- [[Redaction Stage]] — appended the resolved false-positive class to the
  "Known false-positive classes" list (append-only per wiki zone rules; the
  stale "Open, not yet fixed" section is superseded by the new note, not
  deleted).

## Design notes

- The plan's literal suggestion ("requiring separator consistency") would
  **not** have fixed the actual §50 repro on its own — an all-space,
  irregularly-grouped byte dump is already "consistent" under that narrower
  reading. `hasUniformGrouping` (every digit group between separators must
  be the same length) is the check that actually defeats it, so both checks
  are required together.
- Plan/reality discrepancy: `docs/plan/R1_BATCH.md`'s R1.3 "Read first"
  section names `tests/unit/pipeline/redaction-corpus.ts`, which does not
  exist in this repo. The actual T-C3 adversarial corpus lives in
  `tests/unit/pipeline/redaction-audit.test.ts`; the per-rule positive/negative
  smoke corpus is `tests/unit/pipeline/redaction.test.ts`. New cases were
  added to the former (audit corpus is where the other §31/§37/§49 fixes
  also landed their regression cases).

## Verification

- Negative/positive digit strings for the new tests were derived and
  Luhn-verified independently via a throwaway Node script (`node -e`), not
  authored by eye — deterministic arithmetic, not delegated to the local
  model (which is unreliable for exact digit-grouping arithmetic, per prior
  observation this batch).
- Encountered the redaction escape hatch directly while authoring these
  tests: literal card-shaped strings I wrote myself rendered back to me on
  the next turn as `[REDACTED:credit-card:N]`-style placeholders (this
  repo's own session is proxied through Golem's redacting proxy, which
  redacts the resent conversation history each turn). Confirmed the actual
  on-disk file was correct via two methods that don't depend on trusting the
  rendered text: a digit-masked structural view (`str.replace(/[0-9]/g,
  "D")`) showing real lengths/grouping without echoing sensitive-shaped
  digits, and the real `npm test` pass/fail. Recorded in verification-notes
  §55 as a reconfirmation of the existing escape-hatch handling approach
  (§49/R1.1), not a new bug.
- Full gate: `tsc --noEmit`, lint, format:check clean; `npm test` — 722
  tests (719 + 3 new) all pass, including every pre-existing credit-card
  case in both `redaction.test.ts` and `redaction-audit.test.ts`.
