# R13.12 — `default_coder` picks a MECHANISM, and Golem generates the subagent it cannot spawn

## Outcome

`inference.default_coder = "claude-sonnet-5"` now causes `golem init` to write
`.claude/agents/golem-coder.md`, so delegating a coding task to a different model
is native: a full agentic loop, real tool use, its own context — and, because a
subagent's traffic still goes through `ANTHROPIC_BASE_URL`, redaction, compression
and telemetry all still apply.

`inference.coder_prompt` frames every coder task from one source, whichever
mechanism runs it. Unset `default_coder` still means "the work stays in this
session" (R13.11), which is the settled default rather than a gap.

The `claude-cli` removal that the brief scoped in was **deferred to R13.14**, on
purpose. See "The sequencing call" below.

## The constraint that shaped the whole design

**An MCP server cannot spawn a harness subagent.** MCP servers expose tools *to* a
client; there is no call in the protocol surface Golem uses by which `coder` could
invoke Claude Code's own Task tool. So the obvious reading of the request — "set
`default_coder` and the coder tool runs a Sonnet agent" — cannot be implemented
inside the tool at all.

What Golem *can* do is own the wiring:

- **generate the definition** at `init` time, so the delegation is native and the
  user never hand-authors an agent file that drifts from their Golem config;
- **say so** when a task arrives at `coder` anyway.

The second half was a real choice. Silence was the alternative: leave the
definition there to be noticed. Rejected, because the failure mode is invisible —
the generated agent sits unused while `coder` dispatches somewhere the user did not
choose for this purpose. So `coder` returns an ordinary (non-error) result naming
the subagent and its model. An explicit `target` still wins, because the caller
named a destination for *that* call.

## The ambiguity, and how it was decided

`claude-sonnet-5` and `anthropic` are both bare words. Nothing in the string says
which set it came from, so `default_coder` has to choose a precedence:

1. **A declared target wins.** Declaring a target is a deliberate act, and reading
   its id as a model name would send work somewhere the user did not choose while
   reporting success — precisely the failure R10.8's fail-closed lookup exists to
   prevent.
2. **A bare gateway id resolves to its first target**, matching what
   `resolveDefaultTargetId` does for `default_target`. This had to be written
   explicitly: `resolveTarget` does *not* do gateway resolution — that rule lives
   in the default-target path — and `default_coder = "openrouter"` meaning
   something different from `default_target = "openrouter"` would be a gratuitous
   inconsistency between two adjacent settings. Caught by a test that asserted the
   convenient assumption and failed.
3. **A colon-shaped id that resolves to nothing raises.** Registry ids are
   `gateway:model` shaped, so such a value is a typo'd target, not a model called
   `openrouter:qwn/...`. Reading it as a model would produce an agent definition
   naming a model that does not exist — a failure that surfaces later, elsewhere,
   as "There's an issue with the selected model".

## Why a plain model id, not `golem/<target>`

Both are documented shapes and R9.2 shipped the proxy half of the virtual id. But
verification-notes **§114 caveat 5 is still open**: the slash in `golem/<id>` was
never confirmed Claude Code-side, and R9.2 closed with that check outstanding. A
plain id is a documented "full model ID" per the frontmatter table §114 quotes,
and sidesteps the unverified part entirely. The generated file asserts
`not.toContain("golem/")` so this stays deliberate rather than drifting.

## Why the coder prompt is not a skill

The user asked directly. R9.11's recorded rule answers it — *"skills orchestrate,
tools execute. A skill never reimplements a tool."* A system prompt is neither, and
three properties rule a skill out:

1. **Direction.** A skill's body is injected into the context of the session that
   invokes it. This text must reach the *drafter* — an HTTP `system` field, or a
   subagent definition — so a skill would load it into the wrong context.
2. **Portability.** `SKILL.md` is one client's format, and R9.11's first argument
   for keeping tools as tools is that R6.1 extends this pipeline past Claude Code.
   The MCP server must read this prompt in a process that may have no Claude Code.
3. **Semantics.** Skill frontmatter's `description` drives *when to invoke*, which
   is meaningless for a system prompt and misleading once stale.

The skill that *does* belong nearby is a different artifact: guidance about *when*
to delegate rather than work inline. That is R9.11's converse test — "rare,
procedural, and needs prose about when" — and it is not this setting.

## Generated, but not owned

`.claude/agents/golem-coder.md` is generated **and** expected to be edited: it is a
prompt someone will tune, and `golem init` runs on every version bump. So it reuses
`managed-files.ts` exactly as the skills do (R9.5) — an edited definition is
reported as a `conflict` and kept, never overwritten.

Two things that are easy to get wrong and were done deliberately:

- **Removal is part of the install step.** When `default_coder` changes from a
  model to a target, or is unset, the definition must go. An install-only step
  would leave a file naming a model the config no longer selects, with nothing in
  it saying so — `/golem/slider` outliving R11.1 is the precedent, and
  `pruneRetiredSkills` was the shape of the answer.
- **`.claude/agents/` is a SHARED namespace.** Unlike `.claude/skills/golem/`,
  which is a Golem-owned directory `uninit` may take whole, init and uninit here
  only ever touch the one basename Golem owns — and prune the directory only if it
  is empty afterwards.

## The sequencing call

The brief scoped removing the `claude-cli` spawn provider into this task. It was
split into **R13.14** instead, and the reason is the point:

R13.12 proves `golem init` writes a correct definition, that its frontmatter
matches the documented shape, and that `coder` declines and names it. **Nothing in
this repo can prove the part that matters** — that Claude Code honours the
generated `model:`, runs the delegation, and routes it through
`ANTHROPIC_BASE_URL` so Golem still sees the traffic. That needs one real
delegation in a live session.

`claude-cli` works today. Deleting it on the strength of an unverified replacement
inverts the safe order. R13.14 carries the removal, the migration shape, and the
one live check that gates it — including a trap worth knowing before anyone
starts: the settings schema validates `provider` against an enum, so simply
dropping the member makes an existing settings file fail to *parse*, breaking
every command rather than producing a targeted migration error.

## Key lessons

1. **"The harness can do X" and "Golem can make the harness do X" are different
   claims.** An MCP server has no path to its client's tools. Where that is the
   gap, the answer is to own the *wiring* (generate the artifact) and be honest at
   the point of use, not to simulate the capability.
2. **A generated file that people are meant to edit needs provenance from day
   one**, not after the first complaint about a clobbered edit.
3. **Generation implies de-generation.** Any step that writes a file from config
   must also remove it when the config stops calling for it, or it becomes a
   confident lie the moment the setting changes.
4. **Two adjacent settings that accept the same shape must resolve it the same
   way.** `default_coder` nearly diverged from `default_target` on bare gateway
   ids, because the convenient assumption (that `resolveTarget` handles them) is
   false — the rule lived one layer up. A test caught it.
5. **Don't delete the working thing to make room for the unproven thing.** Split
   the removal, name the check that gates it.
