# 2026-08-19 — R10.23: the error frame Golem threw away

A user reported two things in one message. The first: deepseek through OpenRouter
kept answering with Golem's own *"returned an empty completion — no text and no
tool calls"* notice, and then **nothing further**. The second, almost an aside:
one short *"waiting for API"* pause on plain Claude Opus 5.

They turned out to be the same kind of bug twice — Golem holding information it
did not pass on.

Related: [[Architecture]] (§3b byte-faithful vs translating),
[[R10.17/R10.18 — two "can't fail" fallbacks that turned diagnosable errors into silence]] (which wrote the notice this one
replaces), [[OpenRouter reclassified to case (b) — five stacked defects]] (which left the reasoning question
open), [verification-notes §128 / §129].

## What was actually happening

**The notice was not the failure. It was covering for it.**

OpenRouter, like any OpenAI-schema gateway, cannot change the HTTP status once
tokens are flowing — so it reports a mid-stream failure as an ordinary `data:`
frame with a top-level `error`:

```json
{"model":"deepseek/deepseek-v4-flash","provider":"StreamLake",
 "error":{"code":"server_error","message":"Provider disconnected unexpectedly"},
 "choices":[{"index":0,"delta":{"content":""},"finish_reason":"error"}]}
```

The translator's `#handleLine` dropped every frame that carried no `delta`. So
the provider's own explanation was discarded, `#blockCount` stayed 0, and
R10.18's empty-completion notice fired **in the real cause's place**. Then
`mapStopReason` turned the unrecognised `finish_reason: "error"` into `end_turn`.

That last step is the whole "no further updates". **In-band prose is a completed
turn.** Golem told the client the model had finished speaking, so the client
rendered the text and waited for the human.

**The second dropped signal, in the same file.** Both translators read only
`reasoning_content`. OpenRouter documents that name as a *request-side* alias and
returns the trace as `reasoning` (repeating it in `reasoning_details`). Captured
live: every deepseek chunk carried `delta.reasoning`, and `reasoning_content`
never appeared once. So every reasoning trace from every OpenRouter model had
been silently discarded — which answers, and corrects, the open question
[[OpenRouter reclassified to case (b) — five stacked defects]] left behind: it guessed OpenRouter needed an
explicit `reasoning: {…}` request field. It did not. Golem was reading the wrong
field name.

**And the aside was real too.** The Anthropic path is a raw byte pipe, so the
proxy cannot stall a response — but the request side `await`s four stages before
forwarding, and Stage 1.5 (local answer) runs a vector search, hence an embedder,
hence a multi-second first call on a cold local model. It is gated to single-turn
requests — exactly the ones that OPEN a session. So the first turn of a session
paid, and only that one, which fits "one occurrence" far better than any upstream
explanation. Nothing bounded it; nothing logged it.

## The lesson worth keeping

R10.18 wrote, in a comment that was load-bearing for its whole design:

> by `_flush` the headers and `message_start` have already gone out, so an HTTP
> status is no longer available

True about the status — and wrong about the options. Anthropic's streaming
protocol has carried an `error` event all along, valid *at any point* in the
stream, including after content deltas:

```sse
event: error
data: {"type": "error", "error": {"type": "overloaded_error", "message": "Overloaded"}}
```

The reasoning stopped one question early. "I cannot use the mechanism I reached
for" became "I must degrade to prose", when the protocol had a purpose-built
mechanism one doc page away. **When a constraint forces a worse shape, re-read
the protocol before accepting the degradation** — especially in a translator,
whose entire job is knowing what the target protocol can express.

Two corollaries this batch also earns:

- **A failure and a finished turn must never look alike.** The distinction is not
  cosmetic: it decides whether the client may retry. Empty completions here are
  *intermittent* — repeated live probes of the same request succeeded — so making
  them a retryable `error` event is what turns a dead end into a hiccup. The one
  case deliberately left in-band is `max_tokens` with nothing visible, because it
  is deterministic and a retry would fail identically.
- **If Golem spends a user's time, Golem says so.** Third occurrence of this
  pattern (§84's banner naming a config field instead of the resolved route,
  R10.19's unreachable `headroom_config`, now a silent 2-second hold). An
  honest-observability tool that lets the upstream wear latency it did not cause
  is lying by omission.

## The trap the fix walked into

Mapping the reasoning trace *reintroduced the original bug in a new costume*.
R10.18 gated its notice on `content.length === 0`. Once the trace becomes a
`thinking` block, a reasoning-only answer has content — and still nothing a
client can act on, which is precisely the "no visible output" loop R10.14 chased
for a day. An existing test even asserted the old shape ("does NOT fire when only
a thinking trace came back"), so the suite would have blessed the regression.

Hence the gate is now **visible** output (text or tool_use), not block count, and
a trace-with-no-answer keeps its trace *and* gains a notice next to it — the
trace is real output and must not be thrown away (R10.20), but it cannot be the
whole turn either.

Generalising: **when you start mapping a signal that used to be dropped, re-check
every emptiness test downstream of it.** They were written in a world where that
signal did not exist.

## Live verification

Real bytes from the user's own OpenRouter account, fed through the built
translator (2026-08-19):

| case | result |
| --- | --- |
| real deepseek stream | `delta.reasoning` + `reasoning_details` present, `reasoning_content` absent; trace now surfaces as a labelled thinking block |
| truncated mid-reasoning | trace kept, notice appended in-band, valid terminal events |
| documented error frame | one `error` event naming model, provider and "Provider disconnected unexpectedly"; **no** `message_stop` |
| empty stream | one `error` event, `api_error`, R10.18's wording preserved |

`qwen/qwen3.7-flash` streams a trace too — so the reported deepseek/qwen
asymmetry was never "one reasons, one doesn't". It is how much of `max_tokens` the
trace eats, and which provider OpenRouter routed to that minute.

Gates: `tsc --noEmit`, `biome check`, `verify:deps` all exit 0; 2,771 tests with
only the known R10.2 contention flakes (`cli-slider`, `cli-status`,
`headroom-adapter`, `credentials-win32`, `runtime-assets-drift`), all green
re-run in isolation.

## Left for later, on purpose

- **A proxy-level retry.** The proxy has none anywhere; adding one needs its own
  idempotency thinking. R10.23 makes the failure retryable *by the client* instead.
- **`reasoning: {effort}` on the request.** `proxy.upstream_reasoning_effort` is
  sent as OpenAI's `reasoning_effort`, which OpenRouter does not document — their
  parameter is nested. If it is inert, that is the same "config that cannot take
  effect" trap §84 named. It changes what Golem SENDS, and therefore cost, so it
  gets its own task rather than a drive-by.
