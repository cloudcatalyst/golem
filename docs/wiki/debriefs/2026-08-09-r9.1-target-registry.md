# R9.1 — the target registry (2026-08-09)

Related: [[Configuration Surfaces]], [[R8.M1 — three upstream-switch UI defects, none of them in the routing]].
Spine for R9.2 (proxy routing) and R9.3 (`coder` on any target), which can now proceed
in either order.

## The one structural idea

Split what `proxy.accounts` had fused:

| registry | answers | holds secrets? |
|---|---|---|
| `proxy.accounts` (unchanged) | *whose credential* — id → provider + OS-keychain reference | reference only |
| `proxy.targets` (new) | *which endpoint + model* — id → provider, base_url, model, `account` ref, `trust` | **none** |

The pivot the proposal named: **a local model is an ordinary target whose provider is
`ollama`.** "Optional local coder" stops being a special case.

Because a target holds no secret, **the whole ADR-0003 threat model carries over
untouched.** That is the property that kept an `M` honest, and it is the one thing that
must not be traded for convenience later: a `key`/`api_key` field on a target would
silently reintroduce plaintext-secrets-as-settings, which invariant 1 forbids outright.
There is a test asserting a registered target serializes without one.

## The config was already a target registry, and that changed the design

`proxy.accounts` in this repo's own `.golem/settings.local.json` held **six** entries —
and five of them share one OpenRouter credential while naming five different models
(`openai/gpt-oss-20b:free`, `poolside/laguna-s-2.1:free`, `qwen/qwen3-14b`,
`google/gemma-4-26b-a4b-it`, `deepseek/deepseek-v4-flash`).

That is precisely the many-targets-one-account case, in production, before the registry
existed — and it is what a one-target-per-account design would have got wrong. It became
the test fixture rather than a tidier invented one.

It also forced a decision the task doc only implied. `golem target list` **derives a row
from every account**, so an existing config is already a usable registry with no edit at
all. The alternative — an empty `proxy.targets` reporting an empty table while the proxy
happily serves those six accounts — would have shipped a new surface that was wrong about
the machine it ran on from the first minute. R8.32 was exactly that failure mode; not
repeating it was cheap here.

Live, against this repo, unedited:

```
  * anthropic                    anthropic https://api.anthropic.com
        trust=vendor account=(inherit) no stored key (inherits the client's auth) (default upstream config)
    openrouter-laguna            openrouter https://openrouter.ai/api/v1 model=poolside/laguna-s-2.1:free
        trust=third-party account=openrouter-laguna key set — DPAPI-encrypted file … (from account)
    … six accounts, each resolving its own credential
```

An explicit `proxy.targets` entry **replaces** a derived row of the same id, in place — so
adopting an account as a target (to add a `trust` level or a different model) neither
duplicates it nor reorders the table, and it inherits the same-id account so the
credential is not silently dropped.

## Fail-closed, and what that had to mean concretely

`resolveTarget` returns a discriminated result, never a fallback. An unknown id yields no
target *and the list of ids that do exist*:

```
golem: unknown target "ghost" — it is in neither proxy.targets nor proxy.accounts.
Configured targets: anthropic, moonshotai-kimi-k2.7-code, … No substitute was used.
```

This is the one failure mode a routing table must not have. A registry that quietly
substitutes a neighbour for a typo'd or stale id sends **your context** to a model you did
not name — the same reasoning ADR-0003 applied to accounts, where the cost of a silent
switch is a request billed to the wrong key. Here the cost is disclosure, which is worse.

`resolveTarget` is exported now and consumed by `show`/`test`; R9.2 gets the behaviour
already pinned rather than re-deciding it under routing pressure.

## Trust: stored, surfaced, and deliberately pessimistic

`trust` is `vendor | local | lan | third-party`, enumerated rather than free-form so the
redaction floor it will set in R9.3 is auditable and a typo is a config error.

The default when it is omitted does the real work. `defaultTrustFor` resolves a loopback
Ollama to `local`, a non-loopback Ollama to `lan`, `anthropic` to `vendor`, and
**everything else to `third-party`** — the level that will earn the *most* redaction. The
direction is the whole point: an omitted field must never buy a target more of your
context than it asked for. An unparseable base URL lands on the cautious side too.

## The cost that was accepted, written down rather than discovered

`credentialEnvForProxy` now resolves **N credentials, not 1** — every account some target
references, each under its own `perAccountEnvVar`. No new secret mechanism was needed:
`perAccountEnvVar` was already per-account by design (Decision 47), and the CLI still owns
resolution and injects at spawn.

The honest consequence is a **wider blast radius**: the daemon's environment carries N keys
where it carried one, so a proxy compromise now exposes more. That is recorded at the
function that causes it, not left for whoever finds it later. An unkeyed target is skipped
rather than fatal — one missing credential must not stop the proxy starting for the targets
that *are* keyed, and `golem target list` reports the gap.

## Inert on purpose

Nothing routes on this. The proxy still serves one upstream; the registry is configuration
and reporting until R9.2 consumes it. That is what made it safe to land alone, and it is
stated in the module header so the next reader does not assume otherwise.

The one behaviour change is what gets **printed**: startup now warns per misconfigured
target — translating provider with no model, doubled version segment — for *every* target
rather than only the served one. A broken target you have not routed to yet is still
broken, and the point of a registry is learning that before a request depends on it.

## Verification

`tsc --noEmit`, `biome check` (451 files), `verify:deps` ok, full suite **2337 tests**
(+37). Live against this repo's real six-account config: all six listed with credentials
resolving, `show` correct, unknown ids failing closed on both `show` and `test` with exit 2.

**Not verified live:** `golem target test` against a real third-party endpoint. That is an
outward call carrying the user's credential, so only the keyless path (`anthropic` →
`no-credential`, no network) was exercised here. The probe path itself is the one
`account login` already uses.

## Lesson

The migration input was not a detail to accommodate at the end — it was the strongest
available evidence about the shape. Six accounts already sitting in a settings file, five
sharing a key and naming different models, answered the central design question (are these
one registry or two?) more convincingly than any argument in the proposal.

Reading the config you already have before designing the schema that replaces it is nearly
free, and it decided both the split and the derive-from-accounts behaviour.
