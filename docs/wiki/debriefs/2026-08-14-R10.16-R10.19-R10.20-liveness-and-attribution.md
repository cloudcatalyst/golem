# R10.16/R10.19/R10.20 — liveness, and saying whose words these are

**Date:** 2026-08-14
**Tasks:** R10.16 (done), R10.19 (done), R10.20 (done)
**Outcome:** a slow translated stream now pings instead of going silent for two minutes (3 pings observed live). A `headroom_config` key that cannot reach Headroom is reported even when the stage never runs. A thinking block Golem synthesizes now says it is Golem's.

Third batch from one investigation. See
[[R10.14/R10.15 — a screenshot became 125k tokens of prose, and the model answered with nothing]]
and [[R10.17/R10.18 — two "can't fail" fallbacks that turned diagnosable errors into silence]].

## R10.16 — keepalive, and the fidelity cost I declined to pay

Two gaps: `message_start` was lazy, and nothing ever emitted `ping`. A translated
stream therefore sent **zero bytes** for the whole prefill — 124–152s measured.

The obvious fix is to emit `message_start` eagerly. I implemented it, and a test
immediately caught what it costs:

```ts
// Uses the upstream's id/model from the chunks.
expect(firstData(sse, "message_start").message).toMatchObject({
  id: "c1", role: "assistant", model: "qwen2.5-coder:7b",
});
```

`message_start` carries the model, SSE cannot retract, and emitting it before the
upstream has spoken means naming the **configured fallback** instead of the real
serving model. That is a fidelity cost on the exact rail (Decision 25) this repo
guards most carefully — paid for a UI nicety.

So I reverted it. The defect is the dead socket, and a `ping` fixes that at zero
fidelity cost:

- **Forward the upstream's own keepalives.** `#handleLine` returned early on
  anything that was not a `data:` line, which discards SSE **comment** lines —
  the standard idle keepalive, which OpenRouter emits during a long prefill. Real
  liveness was arriving and being thrown away. Relaying it beats inventing it.
- **A 10s heartbeat** for genuine silence, `unref`'d, stopped before the terminal
  events because pushing after `end` throws.
- **Neither forces `message_start` out.** Consequence, accepted and documented: a
  ping can precede `message_start` on a slow prefill.

The lesson is the one a good test exists to teach: *the obvious fix and the
correct fix differed, and only the assertion knew.*

## R10.19 — a warning that only fired when it was not needed

R9.8's gate was "an unreachable key is REPORTED, never silently dropped", and it
shipped `#reportIgnoredConfig` to do it. But the report lived in the adapter, so
it ran only when Headroom actually compressed something — and on a caching
upstream the semantic stage is gated off *before* the adapter is reached.

Measured: a project carried
`headroom_config: {"plugins":[{"name":"openrouter-context-compression"}]}` for
weeks. `plugins` is not a `CompressConfig` field — R9.8 documented that exact key
as its motivating example. Occurrences of the warning in that project's proxy
log: **zero**.

So the check moved to where the config is READ. `golem status` now says it, next
to the "level 3 is inert here" line a user is already staring at, and says both
facts together because either alone misleads: the key would be filtered anyway,
*and* the stage is off on this upstream.

The static field list can fail to warn (a Headroom release may add a field) but
must never warn wrongly — a live worker's `supported_config` overrides it.

## R10.20 — a reasoning trace that read as a data leak

A user opened a fresh conversation in a third project and saw a garbled block
before any answer: half-reconstructed hook names, MCP tool lists, and a
first-person line — *"…I should investigate the code rather than use context7."*

They asked, reasonably: **is Golem crossing over on the backend?**

It was not, and the proof was cheap: the block named `mcp__golem__log`, which does
not exist in the twelve-tool registry. Only a model could have invented it. The
supporting checks agreed — four proxies on four distinct ports, and global
`~/.golem/` holds credentials and gateway config, no conversation data at all.

But the reason it *looked* like a leak is Golem's doing. `map_reasoning_to_thinking`
defaults true, so `reasoning_content` becomes an Anthropic `thinking` block —
carrying no signature, and **indistinguishable from a real one**. The content was
the model's own; nothing on screen said so.

Now labelled, on both paths:

```
[Golem: the upstream model's own reasoning trace, relayed verbatim — not an
Anthropic thinking block]
```

The request-side drop also became an explicit branch. The behaviour is unchanged
— traces are large and most OpenAI-schema endpoints ignore an inbound
`reasoning_content` — but it now reads as a decision rather than an oversight,
which is what produced R10.14's `content: null` bug in the first place. Whether to
send them back stays open, and wants measurement, not a guess.

## Lesson

R10.17/R10.18 were about fallbacks that could not report. This batch is the
neighbouring failure: **output that does not say where it came from.** An
unlabelled reconstruction cost a user real doubt about whether their projects
were isolated — a far more expensive question than the feature was worth.
