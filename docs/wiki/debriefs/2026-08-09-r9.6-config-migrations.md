# R9.6 — a renamed setting no longer stops working in silence (2026-08-09)

Related: [[Configuration Surfaces]], [[R9.8 — marker-free by default, and the warning nobody could read]]

Unblocks **R9.10** (`docs/plan/tasks/R9.10.md`), which renames `inference.local_coder_enabled` — the rename that motivated building this.

## Outcome

Golem had no migration machinery. A settings file naming a key that no longer
exists loaded with **exit 0** and a warning only `golem status` printed — so the
setting silently stopped taking effect while every surface reported success.

There is now one declarative table (`src/config/migrations.ts`), consulted by the
loader. A renamed key keeps working from an existing file, is reported exactly
once with the file and key to edit, and `golem config set` / `writeSetting`
resolve retired names so no write path can put one back.

`proxy.active_account` → `proxy.default_target` (R9.1) moved onto it, and the
bespoke `?? settings.active_account` fallback inside `resolveDefaultTargetId` is
gone.

## Key lessons

**A migration table whose `from` is still a live leaf is a fiction.** Both names
stay writable, the loader never consults the table, and registering the entry
changes nothing — the most comfortable possible way to ship a no-op. So
`assertLeafRename` refuses that combination and its test enforces it: you cannot
register a rename without actually retiring the old leaf. Making the invariant
executable is what turns "we have migrations now" into something true.

**Retiring the key is where the real work was.** The table plus the loader hook
is ~120 lines. Retiring `proxy.active_account` touched the schema, the UI model,
the control surface, both account writers, the display resolver, the target
registry and six tests — because a settings leaf is not a variable, it is an API
with consumers. That asymmetry is worth planning for: *the mechanism is cheap and
the first use of it is not.*

**The rename had quietly split in two.** R9.1 unified *routing* on
`default_target` but the *account* layer went on reading `active_account`, and
nothing noticed because both keys existed. Collapsing them exposed a case neither
half handled: the unified selector may legitimately name a **target** that is not
an account, which the account layer would have reported as a misconfiguration on
every proxy start. Fixed by telling it which target ids exist — a selector naming
one is not an error, so the account layer stands aside and routing serves it.
Fail-closed is intact: a selector in *neither* registry still warns, and the proxy
independently checks both registries at startup.

**A warning nobody reads is not a warning — and R9.8 is why this one lands.**
Config warnings surfaced only in `golem status`, the TUI, and the control surface,
none of which anyone runs after an upgrade that appears to work. They now print at
proxy startup too, because the proxy is the process that consumes the settings.
That is only worth doing because R9.8 stopped the detached daemon spawning with
`stdio: "ignore"` — before that commit this line went to the same nowhere. Two
tasks composing: one produced a diagnostic, the other a place to read it.

**Refusing a case is a design decision worth writing down.** Section renames are
rejected rather than half-supported, because `GOLEM_<SECTION>_<KEY>` splits on the
first underscore after the prefix — a section rename changes how every one of that
section's env vars parses. `assertLeafRename` states and enforces that boundary,
so the next person meets a clear refusal instead of a subtle env-parsing bug.

## Verification

Full suite green (2445 passed, +11), `tsc`, `biome`, all 0. Smoke-tested against
the built CLI with a temp project whose `settings.json` names only the retired
key: both key spellings read back as `proxy.default_target` with the file as
provenance, `golem status` prints the actionable rename warning, and
`config set proxy.active_account …` writes `default_target` and says so.
