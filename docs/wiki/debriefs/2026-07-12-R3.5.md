# R3.5 — note→distill shaping into question/artifact drafts

**Before:** `golem note` captures landed in `.golem/notes/notes.jsonl` (T4)
and stayed there — the T3 distillation engine only knew how to shape a
fetched, cached URL into a `type: source` draft. A quick note had no path
into the wiki short of a human manually rewriting it into page form.

## What was built

- `distillNote`/`NoteDistillInput`/`NoteDraft` (`src/knowledge/distill.ts`) —
  a note-specific prompt asks the local `summarizer` role to first classify
  the note as `question` (open/unresolved, worth investigating later) or
  `artifact` (a decision, snippet, or design note worth keeping as-is), then
  write a summary in its own words and suggest wikilinks from the caller's
  `existingTitles` list only — never inventing a page.
- `parseDistillResponse`, a generic helper factored out of the existing
  `distillPage` body (JSON-parse, zod validate against a caller-supplied
  schema, kebab-case the slug with a title fallback, canonicalize wikilinks
  to existing titles' casing). Both `distillPage` and `distillNote` now call
  it — `distillPage`'s six pre-existing tests still pass unmodified, so the
  refactor changed no observable behavior.
- `writeNoteDraftFile`/`findDraftByNoteTs` (`src/knowledge/distill-store.ts`)
  — writes a note-derived draft into the same `.golem/distill/<slug>.md`
  directory URL-drafts use, with `type` set to the model's classification and
  a synthetic `note:<ts>` string in `sources` (there's no URL to cite). This
  keeps draft lookup on the existing `sources`-array pattern rather than
  adding a second lookup mechanism — and means `listDraftFiles`/
  `golem wiki distill --pending` needed zero changes to list both draft kinds
  together.
- `findNoteByTs` (`src/cli/notes.ts`) — resolves one captured note by its
  exact `ts` (the log's unique key).
- `src/cli/distill-note.ts` (new) — `distillNoteCapture`, the CLI-layer
  engine, mirroring `distillOne`'s shape exactly: resolve the target note (by
  `ts`, or the most recently captured one via `listNotes(dir, 1)`), reuse an
  existing draft unless `--force`, construct local inference + load existing
  wiki titles the same way, call `distillNote`, then `writeNoteDraftFile`.
- `golem note distill [ts]` subcommand (`src/cli/main.ts`), alongside the
  existing `note`/`note list` commands — `--dir`, `--force`.

## Design decisions

**Reuse over new mechanism, everywhere it was possible.** The whole feature
adds only two new types, one new function in `distill.ts`, two new functions
in `distill-store.ts`, one in `notes.ts`, and one new CLI-wiring file — no new
storage directory, no new draft-listing path, no new frontmatter shape beyond
setting `type` to the model's classification instead of a hardcoded
`"source"`. `WikiPageType` already included `"question"`/`"artifact"`
(`src/interfaces/wiki.ts`), so no interface change was needed either.

**Synthetic `note:<ts>` provenance marker instead of a separate lookup
field.** A note-derived draft has no URL, but the draft-storage layer's only
existing way to find "the draft for X" is scanning `sources` for a literal
match. Rather than adding a `noteTs` field to `WikiFrontmatter` (a frozen
interface — CLAUDE.md requires flagging dependent workstreams for any
change), storing `note:<ts>` as the sole `sources` entry keeps `findDraftByUrl`
and `findDraftByNoteTs` structurally identical, just matching a different
string shape.

**Delegate-first drafting caught real issues.** Per CLAUDE.local.md, a first
draft of `distillNote` was requested from the local model via `delegate`
before writing the real implementation. The draft passed a raw zod schema
object as the `jsonSchema` chat option (should be a JSON-Schema-shaped
literal), redefined `DistillParseError`/kebab-casing instead of reusing the
existing ones, and didn't factor any shared logic — used only as a rough
reference, not merged in.
