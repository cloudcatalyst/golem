# R8.18 — `golem llamacpp`

R8.18 was the "install and run a local llama.cpp server" line item, but in this
batch it became the concrete realisation of spec **Decision 56**'s reframe: no default
model, fit-for-hardware selection, llama.cpp first-class rather than a fallback, and the
first real step toward **operating with no upstream at all**.

## What shipped

- **`golem llamacpp models`** — the curated GGUF ladder (Qwen3 1.7B → Qwen3.6-35B-A3B),
  ranked against **measured free RAM** on this machine, with each entry's fit shown as
  arithmetic. `proven: false` entries are listed so the trade is visible but **never
  recommended**. "No catalog model fits this machine's free RAM" is a valid answer,
  printed with the floor-model escape hatch.
- **`golem llamacpp setup`** — one consented command that: picks (recommended or named),
  **proves** it fits RAM *and* the target volume before asking, downloads the pinned
  `b10216` release + the chosen GGUF **resumably** and **sha256-verified against digests
  the publishers report**, extracts into place, starts the server detached, reads `/props`
  back, and writes the `inference.providers` entry from what the server actually said.
- **`--no-start`, `--no-draft`, `--models-dir`, `--port`, `--scope`** — the knobs for a
  2.5 TB `D:` volume, a non-loopback port, and recording the choice in the right settings
  layer.
- Three new settings keys, each described in `SETTING_META`: `inference.llanacpp_models_dir`,
  `inference.llamacpp_model`, `inference.llamacpp_port`.

The whole line obeys Decision 26's install rules: never automatic, never imported by
`golem init`, always consented, Golem ships none of the bytes.

## Why the ladder is sorted by active parameters, not download size

A 35B-A3B MoE is 19 GB to download but **3B active per token**. With `-ngl 99
--n-cpu-moe 999`, every layer runs on the GPU and the expert tensors stay in RAM — so on an
8 GB card only attention + the KV cache touch VRAM, and the 35B model drafts faster than
a dense 14B does, while knowing far more. A catalog sorted by GB puts the 19 GB MoE below
the 8 GB dense model and is wrong for exactly the machines this is for. The fit check
(`checkFit`) uses **quant-discounted resident bytes**, and `rankModels` scores on
effective params per GB — the mistake of sorting by nominal size is the one the module
was written to avoid.

## Bugs found by running it (the whole point of a gate that runs live)

This task found **four** defects, none caught by review. Detail in
[verification-notes §114–115](verification-notes.md). Short form:

1. **No Linux CUDA build exists.** The planner derived Linux asset names from Windows,
   producing names upstream does not publish. On Linux + NVIDIA the answer is **Vulkan**,
   and the Linux CPU asset has no `-cpu-` infix. `verifyAssetName` now checks the resolved
   name against the *live* release listing before any download, and fails with the
   available names.
2. **The 3-second probe runner killed extraction.** `ProbeRunner` budgets 3s for status
   probes; unpacking 140 MB exceeds that. Extraction moved to `InstallCommandRunner`
   (the same seam `golem ollama setup` uses). Choosing the wrong runner is invisible until
   the input is big enough.
3. **`tar` on Windows is not one program.** bsdtar reads `-f C:\…` as a hostname, and plain
   `tar` on a shell with Git on PATH is GNU tar (cannot read zip). Extraction now runs
   cwd + bare filename, names `%SystemRoot%\System32\tar.exe` first, and falls back to
   plain `tar` then PowerShell `Expand-Archive`.
4. **`--model-draft` without `--spec-type draft-mtp` segfaults** the server, not errors.
   The draft file is now gated on a `specType` field and only passed with its type.

## Live measurement (the gate)

Qwen3.6-35B-A3B-MoE, Q4_K_M, on this machine (RTX 3070 Laptop 8 GB, driver 596.21,
CUDA 13.3, 64 GB RAM ~33 GB free, weights on `D:`):

| metric | value |
|---|---|
| throughput (400-token completion, end to end incl. prompt eval) | **15.7 tok/s** |
| working set after load | ~5 GB (weights mmap'd, not resident) |
| server init window | CPU path: seconds; CUDA offload: adds the GPU init window |
| `/props` context window | 16,384 (read live, not assumed) |

The gate text deliberately tolerates a slow number: a MoE on first load is not fast, and
the honest alternative is to hide that fact. Whether the MTP draft model improves
throughput is still open — it loads and the server reports it, but speculative decoding
only pays at sustained higher load and a single 400-token probe cannot show it.
