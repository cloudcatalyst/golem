# R8.32 — a running proxy nothing was wired to (2026-08-06)

Found by dogfooding the same day
[[R8.31 — stopping the proxy meant a dead port, and unwiring alone could not fix it]]
shipped, and reported as a question rather than a bug: *"I've started the proxy, but I'm not
seeing it updating the settings.json. Is the latest version deployed?"*

Related: [[Dogfooding Golem]], [[Configuration Surfaces]].

## The answer to the question was "yes, and that is not the problem"

The build was current and the daemon was up. `golem proxy start` simply never writes
`.claude/settings.json` — wiring belongs to `golem init` / `golem proxy wire`, and R8.31
had *deliberately* kept `start`/`stop` out of that file so the two lifecycles stop
churning a git-tracked artifact. Working as designed.

The real state was worse than the question implied. `env.ANTHROPIC_BASE_URL` was absent
entirely, so Claude Code had been talking **straight to `api.anthropic.com`** — no
redaction, no compression, no telemetry — while every surface reported success:

- `golem proxy status` → `running (pid 63900) on port 4930 -> https://api.anthropic.com`
- the statusline → green `⬢ Golem · Aggressive → anthropic · ✂ full`
- `golem status` → `Proxy: http://localhost:4930 — reachable`

None of those is *wrong about the daemon*. All of them are wrong about Golem.

## Why this is the mirror of R8.31, and worse

R8.31 fixed live wiring pointing at a **dead port**. This is a live port with **no
wiring** pointing at it. The asymmetry is the whole finding:

| | R8.31 | R8.32 |
|---|---|---|
| symptom | every request fails, connection-refused | every request **succeeds** |
| who notices | the user, immediately | nobody |

A defect that breaks loudly gets reported in an hour. This one is only visible if you
already suspect it — and the surfaces built to tell you were all answering a different
question. R8.31's debrief closed with exactly this lesson: *"'Is the process running?'
and 'where is the client pointed?' are independent facts, and every surface here knew
only the first."* It named the gap and then fixed only the half that was failing loudly.
The other half sat there for a day.

## The statusline was the worst offender

`golem proxy status` merely omitted something. The statusline **asserted** it: it derived
`proxyRunning` from the pid file alone, so it painted a confident green `⬢` beside
"Aggressive" and a `✂ full` brevity badge describing transforms that were not running on
any byte of traffic. The most load-bearing surface in the product — rendered every prompt
— was the most confidently wrong.

`⬡ Golem · Unwired` now, in **yellow, not dim**. Dim is the resting state for "off",
which is something the user chose; this is a misconfiguration they almost certainly did
not. Same reasoning R8.31 applied when it suppressed `✂ full` under the shim: a badge for
a stage that is not running is a lie regardless of which state stopped it.

## What was cheap, and what that says

The fix needed **no new mechanism**. `readWiringState` already returned exactly the
required `"golem" | "foreign" | "none"`, already unit-tested, already imported by the one
surface that half-handled this — R8.31 built it. The work was calling it on three more
paths and agreeing on the wording, which is why an `S` was honest.

One shared `wiringGap()` produces the message for all four surfaces. Four hand-written
strings would drift, and drift in status text is always toward reassurance.

`foreign` deliberately gets a *different* message with **no remedy offered**: another
gateway owning `ANTHROPIC_BASE_URL` is the human's decision and the ownership rule forbids
touching it, so suggesting `golem proxy wire` there is advice to clobber someone else's
config. `none` gets the remedy — and it names `golem proxy wire`, not the `golem init`
that `golem status`'s checkbox had been recommending for a one-key repair.

## The constraint worth pinning

Status now **reads** `.claude/settings.json`. The obvious next step is to have it repair
what it finds, and that is precisely the mistake R8.31 avoided. A test asserts
`collectStatus` leaves the file byte-identical, because a status command that quietly
edits config would pass every other assertion in the suite.

## Verification

Standing bar green (`tsc`, `biome check`, `verify:deps`, **2298 tests**, +12). Live, by
unwiring this repo's own proxy and reading all four surfaces, then restoring:

- `golem proxy status` → `⚠ … NOT in the request path (no redaction, no compression, no telemetry)`
- `golem proxy status --json` → `"wiring":"none","in_path":false`
- `golem status` → the warning **adjacent to the proxy line**, not six lines up in a checkbox
- statusline → `⬡ Golem · Unwired → anthropic (claude-opus-5)`, no level, no brevity badge
- re-wired: all four quiet again, `.claude/settings.json` back to its committed bytes

## The cause, once asked

The task shipped with "how did the wiring get removed?" recorded as an open question —
neither `uninit` nor `unwire` had knowingly been run. The answer, given the same day:
**the maintainer deleted the `env` block by hand, deliberately, to go direct to Anthropic
and get the work done.**

Worth noting what the honest-but-wrong instinct was here. An unexplained config change
*looks* like a bug, and it is tempting to hunt for a rogue caller. There wasn't one. The
right move was recording it as an open question and asking, rather than shipping a guess —
but the cheaper move would have been asking first.

More importantly, **it inverts the significance of the finding.** Going direct is not a
rare accident in this project; it is a routine act — and R8.31's debrief had already noted
the *same* hand-edit sitting uncommitted in the working tree weeks earlier, treating it as
evidence of a design gap. So the running-but-unwired state is one this repo enters **on
purpose and often**, which makes a statusline that paints confident green over it a
recurring lie rather than an edge case. The task was sized `S` on the assumption it was
tidying a corner. It was not.

One question does stay open, and it is ergonomic rather than diagnostic: `golem proxy
unwire` shipped in R8.31 *hours before* this hand-edit and does exactly this job —
ownership-guarded, reload surfaced. A hand-edit was still preferred. Discoverability of a
brand-new command is the obvious explanation, but it is worth confirming before assuming
the command is good enough.

## Lesson

R8.31 wrote down the right lesson and then acted on half of it. Naming a gap in a debrief
is not the same as closing it, and the half that fails silently is the half that will still
be broken tomorrow — precisely *because* it never generates a complaint.

The narrower version: **"running" is a fact about a process, not about a product.** Every
status surface that reports a daemon's health should be asked what the user actually wants
to know, which is almost always "is this thing doing anything for me?"
