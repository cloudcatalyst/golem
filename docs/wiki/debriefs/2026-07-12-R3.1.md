# R3.1 — chat-judge rerank

**Before:** `R3_BATCH.md`/`ROADMAP.md` framed R3.1 as a choice between two
options — extend the frozen `InferenceService` contract with a `rerank`
method, or introduce a brand-new `Reranker` interface — and gated the
feature at slider ≥2. Both assumptions were stale by the time this task
started.

## The design decision (Decision 34)

Neither listed option was needed. `InferenceService.chat()` already accepts
a `jsonSchema` to force structured output, and the "judge" role is already
wired at every hardware tier in the model catalog. `rerankHits()`
(`src/knowledge/rerank.ts`) calls `chat("judge", ..., { jsonSchema })` with
the candidate hits' `chunkId`s and asks for a relevance-ordered list back —
zero changes to any frozen contract in `src/interfaces/`.

Gating at "slider ≥2" also no longer holds: Decision 31 (same day) settled
that the slider means exactly one thing — compression aggressiveness — and
must never auto-engage the local model at any level. Rerank is a local-model
call, so it can't ride the slider. It's gated instead by its own setting,
`knowledge.rerank_enabled` (default `false`), the same shape Decision 33 used
for `local_answer_enabled` — opt-in until there's real usage evidence it
helps.

## The failure-mode design point

`distillPage`/`distillNote`/`synthesizeWeekly` (R3.5/R3.4) let `chat()`
errors propagate — the model's output *is* the result there, so there's
nothing to fall back to. Rerank is different: it augments an
already-successful search. `rerankHits()` therefore catches everything
internally — unreachable model, non-JSON output, a response that drops or
invents a `chunkId` — and falls back to the pre-rerank order rather than
throwing. A rerank problem must never turn a working search into an
`isError` tool result.

## What was built

- `src/knowledge/rerank.ts` — `rerankHits(inference, query, hits)`.
- `knowledge.rerank_enabled` config leaf (`src/config/schema.ts`), default off.
- `GolemMcpServerDeps.rerank?: InferenceService` (`src/mcp/server.ts`),
  applied in the `search` tool handler after `boostWikiHits`, before the
  `k` truncation.
- `src/cli/main.ts`'s `golem mcp serve` wires `deps.rerank` from the same
  `inference` instance already built for `delegate`, when
  `settings.knowledge.rerank_enabled` is on.

## Verified

`tests/unit/knowledge/rerank.test.ts` (fake `InferenceService`): reorder on a
valid response, fallback on malformed JSON / dropped id / invented id /
duplicate id / a throwing `chat()`, and a 0/1-hit short-circuit that skips
the model call entirely. `tests/integration/mcp-knowledge.test.ts` adds two
end-to-end cases through the real MCP `search` tool: hits reorder when
`deps.rerank` is injected, and stay untouched when it's absent. Full gate
(`tsc --noEmit`, `biome check .`, `format:check`, `vitest run`) green — 92
files / 871 tests.
