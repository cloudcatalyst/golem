Shipped the R3.7 spike's recommended fix. `FileVectorDriver.#flush()` built
one `Array.join("\n")` string for the whole collection and hard-crashed
(`RangeError: Invalid string length`) between 30k–50k chunks — V8's max string
length. The raw-article KB grows monotonically, so this needed fixing before
it hit the wall.

## What landed (`src/knowledge/file-driver.ts`)
- `#flush()` now streams one JSON line per record through a `createWriteStream`
  (`#writeRecordsStreamed`) instead of building one giant string. Backpressure
  is honored via `events.once(stream, "drain")` — which rejects if the stream
  errors mid-wait, so an I/O failure surfaces instead of hanging. The temp-file
  + `rename` atomicity (crash mid-write never leaves a half-truncated file) is
  unchanged.

## Verification
- Re-ran the spike's synthetic benchmark (512-dim, ~700-char chunks): 30k / 50k
  / 60k all complete — **the crash wall is gone** (was 30k–50k). Search latency
  is the same brute-force cosine curve as the spike (fix doesn't touch search).
  Numbers appended to [[r3.7-lancedb-scale-spike]].
- Committed regression test: streams 3,000 ~1KB records, reloads, asserts every
  record survives (guards dropped-line / missing-trailing-newline bugs under
  drain). The full 50k+ crash-wall check stays an uncommitted scratch bench —
  too heavy for CI.
- `tsc`, lint, format clean; `npx vitest run` 922 green (+1).

## Notes
- Out of scope (spike's second finding, left as-is): every upsert still
  rewrites the whole collection, so steady-state single-chunk ingest is still
  O(corpus). A WAL/append + compaction would fix that if it ever becomes
  user-visible; LanceDB stays deferred (real usage ~4k chunks). No frozen
  interface touched (driver internal).
