# R8.30 — Headroom worker-respawn backoff + stderr tail

**Verdict: shipped.** Two related defects in the Python sidecar lifecycle, both from the fresh-eyes audit.

Related: [[Compression]], [[Dogfooding Golem]].

## Problem 1: no respawn backoff

`#cleanup` reset `#startPromise` on worker death, so every request that found `!isRunning()` called `start()` immediately. A flaky Python environment (e.g., uv temporarily failing to find Python 3.13) produced repeated spawn-attempt log noise, and each attempt consumed the startup timeout.

**Fix:** Exponential backoff (1s → 2s → 4s, capped at 30s) between respawn attempts, reset on successful start. New test verifies the delay.

## Problem 2: startup timeout hides stderr

`child.stderr.on("data", ...)` captured stderr but only logged it on unexpected exit. A startup timeout logged a generic "Headroom sidecar failed to start" with no actionable diagnostic — the user could not see "uv couldn't find Python 3.13" or similar.

**Fix:** Startup timeout error message now includes the captured stderr tail (truncated to ~2 KB).

## Verification

- New test file: `tests/fixtures/fake-headroom-worker.mjs` (simulates a worker that starts, dies, or fails)
- Integration test: `tests/integration/headroom-adapter.test.ts` verifies backoff delay on unexpected death
- All 13 Headroom tests pass, full suite green
