# R12.6 — a doorbell, not a channel

Research spike, no code. The question ADR-0006 left open: a companion app whose
owner must remember to open it is not a companion app, so **how does a phone learn
a permission prompt is waiting** without adding a party that can read what is being
asked? Full evidence with quotes, dates and URLs is
`docs/plan/verification-notes.md` §135. See [[Architecture]] for where the
companion app sits.

## Outcome

**Outcome 1 of the brief's three, conditionally: a self-hosted-enough path exists.**
Web Push, originated by the blocked laptop, carrying a fixed constant. Content is
genuinely unreadable by Apple and Google — that was the hypothesis the brief
refused to let us assume, and it verified. The remaining third parties are named
rather than glossed: Apple (APNs) for iOS/Safari, Google (FCM) for Chrome/Android,
Mozilla (autopush) for Firefox. No Golem-operated push service, so R6.3's bar
holds, and the relay is untouched.

Two clean negatives are recorded beside it, and they are the durable half: **there
is no Apple-free way to wake a locked iPhone that is off Wi-Fi**, and **no LAN-only
mechanism addresses the case the feature exists for.**

One precondition is untested and gates everything: whether an iOS 26 Home Screen
web app installed from an origin whose certificate chains to a *user-installed*
Golem CA can subscribe at all. Until that is observed on a real device, **R12.5
ships the degraded path** and puts one sentence on screen: *"Alerts are off — this
screen only updates while it is open."*

## Key lessons

**1. The reopened option was the wrong one, and the reason was one bullet in the
ADR.** Revision 2 promoted relay-originated push to option 1 because a relay
already holding a connection is the obvious origin. But sending a push to a
VAPID-restricted subscription requires a JWT signed by the key bound at subscribe
time, so the relay would hold a private signing key — and §3b's first bullet says
"It holds no key and terminates no TLS". The obvious place to put a feature is not
always a place that can hold it. The weaker "relay as dumb POST-forwarder" variant
fails differently: RFC 8030 makes the endpoint a capability URL ("Knowledge of a
push URI implies authorization to send push messages"), so forwarding hands over a
durable address plus the ability to ring it. §3b concedes DoS and metadata; it does
not concede **offline addressability** — reaching a paired device when no session is
open at all, which is the one thing the current relay provably cannot do.

**2. The decisive argument was not cryptographic, it was about who is awake.** The
event being announced is "Claude Code is waiting for a decision *on this laptop*".
The laptop is therefore awake by definition, holding the prompt, and perfectly able
to make one outbound HTTPS POST. Relay-origination buys exactly one thing — hiding
the laptop's IP from Apple/Google — and in relayed mode the relay already sees both
endpoints' addresses. **When evaluating where a capability should live, check which
participant is guaranteed to be online at the moment it fires.** That question
dissolved a whole design branch in one line, before any threat modelling.

**3. "Encrypted" and "private" are different claims, and the specs say so
themselves.** The body is opaque — RFC 8291 exists precisely "to be secured against
inspection, modification, and forgery by a push service", with the decryption keys
minted on the phone. But the W3C Push API's own privacy section concedes the rest:
timing, frequency and size are exposed, and "the only known mitigation is to
increase the apparent message size by padding". VAPID makes the sender a *stable
pseudonym on purpose*. So the honest statement is not "Google can't see anything",
it is "Google learns when this developer's agent needed a decision, and not what it
was" — the same *class* of signal §3b already concedes to the relay, disclosed to a
second party. That is a new concession and it needs its own sentence in the ADR, not
a clause folded into an existing one.

**4. Read the carve-outs, not the MUST NOTs.** RFC 8030 §8.2 looks airtight — push
URIs "MUST NOT provide any basis to correlate communications for a given user
agent", "User and device information MUST NOT be exposed". Then the Push API adds:
"The push endpoint MUST NOT expose information about the user to be derived by
actors **other than the push service**." The whole privacy guarantee is scoped to
everyone except the party we were asking about. A spec's strong language is often
strong against the wrong adversary.

**5. A platform restriction we would have fought turned out to be the feature.**
Apple: "Safari doesn't support invisible push notifications … If you don't, Safari
revokes the push notification permission for your site." No silent push means push
cannot be a background sync channel — so push count equals notification count, and
no covert side channel exists, *not even one we could build by accident*. The
constraint enforces the design we wanted anyway. Android agrees from the other
direction: high-priority FCM is what beats Doze, and Android 13+ downgrades apps
that send it without showing a notification.

**6. The right primitive for a rarely-opened app is the newest one, for a
non-obvious reason.** Classic Web Push binds the subscription to a service worker
registration, and WebKit says ITP "deletes all website data for websites you haven't
visited in a while. This includes service worker registrations", which "would render
the push subscription useless". A companion app is *by construction* opened rarely —
it is the pathological case for classic push. Declarative Web Push
(`window.pushManager`, Safari 18.4, now §3.3 of the December 2025 Push API draft)
survives service-worker removal. WebKit even documents our exact scenario, in a
section headed "What if I can't send the notification description through the
internet?": a generic always-displayable fallback in the push, optionally replaced
by a service worker reading local state. That is the design, written by someone
else, for the same reason.

**7. The self-hosted alternatives fail identically, and their own maintainers say
so.** Judged on the only case that matters — locked, off Wi-Fi — every LAN-only
option is a no. Background Sync does not exist in Safari (MDN BCD:
`version_added: false`, open bug since 2018). ntfy's own docs require a self-hosted
server to forward poll requests to an APNs/Firebase-connected upstream, because
"iOS heavily restricts background processing", making instant push impossible
"without a central server"; unaided, delivery "can take hours". UnifiedPush has no
iOS distributor at all. Local Push Connectivity is SSID-bound by design and gated
behind an entitlement requested from Apple. **When every alternative fails at the
same point, that point is the actual constraint** — here, that a locked phone off
Wi-Fi is reachable only through the one persistent connection the OS itself keeps.

**8. Answering the transport question surfaced a bigger unanswered one.** A push
subscription is bound to an *origin*, and under §3a the companion app's origin is
the laptop — a LAN address that changes with the network, while §3b deliberately
gives the app two transports. Web Push needs one origin for the life of the pairing.
So R12.5's "the UI must not know which transport it is on" hardens into a
requirement on the **origin**, and it lands on R12.8. Recorded as an explicit
untested dependency with a two-observation test rather than an assumption in either
direction, in the manner of §100/§108 — and specifically because §123 is the
precedent for a plausible TLS assumption failing on contact with a real client.
