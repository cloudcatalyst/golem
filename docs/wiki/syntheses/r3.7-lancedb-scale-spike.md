# R3.7 — LanceDB scale spike: not the right lever, and not for the reason expected

**Question:** ROADMAP flagged LanceDB as "optional; only pays at 10⁵+
vectors." Before building a new vector-driver implementation, is this repo
(or any realistic single-project KB) anywhere near that scale?

## Method

Measured `FileVectorDriver` (`src/knowledge/file-driver.ts`) two ways:

1. **Real scale today**: `.golem/knowledge/*/meta.json` on disk — two
   collections, 2,224 + 1,743 = **3,967 chunks total**, 512-dim vectors.
2. **Synthetic scale**: a throwaway benchmark (batched `upsert`, `search(k=10)`,
   and steady-state single-chunk `upsert`) against fresh collections at
   4k/10k/30k/50k/100k chunks, same 512-dim, ~700-char chunk text — run
   locally, not committed (read-only spike, no shipped code).

## Result — the actual bottleneck is not search latency

| n | full ingest | search(k=10) avg | single-chunk upsert (steady-state) |
|---|---|---|---|
| 4,000 | 2.0s (0.50ms/chunk) | 4.18ms | 442.6ms |
| 10,000 | 12.2s (1.22ms/chunk) | 28.64ms | 1,172.4ms |
| 30,000 | 100.3s (3.35ms/chunk) | 74.96ms | 3,259.6ms |
| 50,000 | **crash** | — | — |
| 100,000 | **crash** | — | — |

Brute-force cosine search stays cheap even at 30k (75ms) — that was
ROADMAP's original worry, and it turns out to be the *least* pressing one.
The real cost is **`#flush()` rewriting the whole collection on every single
upsert** (`file-driver.ts:127-144`): it collects every record into an array,
joins it into one giant string (`lines.join("\n")`), and writes that. So
"index one more file" costs grow with **total corpus size**, not with what
changed — 443ms at 4k chunks, 3.3s at 30k. That is already a user-visible
incremental-ingest cost well before any crash.

## The actual wall: a hard crash, not a slow degrade, and it's earlier than assumed

At both 50,000 and 100,000 chunks, `upsert` throws:

```
RangeError: Invalid string length
    at Array.join (<anonymous>)
    at FileVectorDriver.#flush (file-driver.ts:131:46)
```

`lines.join("\n")` builds one JS string for the whole collection before
writing it. Each record's embedding vector alone serializes to ~8-9KB of
JSON (512 floats), so total collection size crosses V8's max-string-length
ceiling somewhere **between 30,000 and 50,000 chunks** at this embedding
dimension — not at "10⁵" as the ROADMAP backlog note assumed. That's a hard
crash (`RangeError`), not a graceful slowdown: past the wall, `golem index`
would fail outright, not just get slow.

## Go/no-go

**No-go on LanceDB right now.** Real usage (3,967 chunks) sits ~8-13x below
the crash wall and ~25x below the "10⁵" figure ROADMAP used to justify
deferring it — LanceDB adoption is not justified by today's data volume by
either number.

**But the crash wall is real and closer than the backlog assumed**, and it
has nothing to do with needing an ANN index — it's a pure serialization bug
(building one string instead of streaming writes). The right near-term lever
(mirroring [[R2.5 — Headroom read_lifecycle disable verification]]'s finding
that the real lever was something narrower than the originally-proposed one)
is:

- **Fix `#flush()` to stream-write records** (line-by-line append or a
  WAL + periodic compaction) instead of `Array.join`-ing the whole
  collection into one string. Pure TS, zero new dependencies, removes the
  crash ceiling entirely, and also fixes the O(corpus-size) steady-state
  ingest cost that's already visible well below the crash line.
- Defer LanceDB until either (a) a real project's chunk count approaches
  the tens-of-thousands range for real (not synthetic) usage, or (b) the
  now-identified incremental-ingest cost becomes user-visible in real
  dogfooding — neither is true today.

This flush fix is **not built as part of this spike** (R3.7 is scoped
read-only/measurement-only per `R3_BATCH.md`) — it's recorded here as a
concrete, low-cost follow-up recommendation for a future task, same as
[[R2.5 — Headroom read_lifecycle disable verification]]'s recommendation fed
directly into R2.6.
