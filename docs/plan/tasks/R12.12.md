## Why this exists

R12.11 found the deciding fact: Golem's gate (`src/autonomy/gate.ts`) never emits
`deny` for `destructive`/`outward` — it emits `ask` at every autonomy level, on
the `PreToolUse` hook. `ask` forces a question; it does not answer one. Per
`code.claude.com/docs/en/channels-reference` (fetched 2026-08-22), a permission
dialog — once it exists — is exactly the event a connected, permission-relay-capable
channel is notified of, and nothing in the hooks or channels reference exempts a
specific call from that relay after the dialog exists.

The same docs name an event Golem does not use: **`PermissionRequest`**. It fires
"when Claude Code is about to ask you for permission," strictly before
`PreToolUse`'s `ask` would otherwise lead to a dialog, and "if no hook returns a
decision, it denies the tool call." Its decision shape is
`hookSpecificOutput.decision.behavior: "allow"|"deny"` (plus `message` for deny),
nested differently from `PreToolUse`'s flat `permissionDecision`.

**The fix**: for `destructive`/`outward`, resolve the call at `PermissionRequest`
with `behavior:"deny"` (a real decision), instead of only forcing `ask` at
`PreToolUse` (a deferred question). If the documented ordering holds, this means
no dialog is ever shown for these two classes, and therefore — by construction —
nothing for a channel relay to be notified of. This is a change to a hook Golem
already owns, not a new transport.

## What to build

1. **Register a `PermissionRequest` hook** alongside the existing `PreToolUse`
   one (`src/hooks/settings-writer.ts` wires hook registration into
   `.claude/settings.json` today — extend it, following the same matcher
   conventions already used for `PreToolUse`).
2. **New handler, mirroring `src/hooks/pre-tool-use.ts`'s structure**: classify
   the pending call the same way (`classifyAction`/`classifyBash` from
   `src/autonomy/classify.ts`), and for `destructive`/`outward` emit
   ```json
   { "hookSpecificOutput": { "hookEventName": "PermissionRequest",
     "decision": { "behavior": "deny", "message": "<the existing gateReason text>" } } }
   ```
   For every other class, defer (exit 0, no stdout) — `PermissionRequest` should
   not take over decisions `PreToolUse`'s `allow` path already resolved (those
   calls never reach `PermissionRequest` at all, since they were never asked).
3. **Keep `PreToolUse`'s existing `ask` for `destructive`/`outward` as a second,
   redundant layer** rather than removing it — defense in depth, and it is what
   keeps the audit log (`appendActionLog`) and pending-call recording
   (`recordPending`) working exactly as they do today. Do not weaken or remove
   any existing decision; this task only adds a decision one event earlier.
4. **Same fail-safe discipline as `PreToolUse`**: any crash, missing project
   state, or invalid input in the new hook must exit 0 with no stdout (defer to
   native), never auto-allow, matching `src/hooks/pre-tool-use.ts`'s existing
   catch-block contract.
5. **Update ADR-0006's R12.11 block** (this file's `design` field) to mark the
   fix shipped, once it lands — that block currently says "the fix has not been
   built."

## What this task's own tests can and cannot prove

Can prove (unit/recorded-shape, same style as the existing `PreToolUse` hook
tests): the new hook emits the right JSON shape for each `ActionClass`; it
defers correctly when the gate is disabled or the action is not
`destructive`/`outward`; it fails safe on a malformed payload; the existing
`PreToolUse` behavior is unchanged byte-for-byte for every input that isn't new.

Cannot prove: that a `PermissionRequest`-level `deny` actually pre-empts a
connected channel's `permission_request` notification in a live interactive
session. That requires a real terminal (not `-p`/headless — confirmed
structurally unable to open a dialog at all, verification-notes §141) and a real
connected permission-relay channel, which this task's automated tests cannot
drive. **That confirmation is `R12.13`, filed separately as `owner: user`.**

## Out of scope

Rebuilding or removing the existing `PreToolUse` `ask` behavior. Any change to
`ActionClass`, `classifyAction`, or `classifyBash` (ADR-0002's classification is
not in question here, only which hook event enforces its output). Building a
PTY/interactive test harness (see R12.13) — this task's tests are recorded-shape
only, same discipline as the rest of `src/hooks/`.
