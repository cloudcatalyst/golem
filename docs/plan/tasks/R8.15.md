## Goal

Make "which local model does Golem use, on which backend" a **user-editable data
decision** instead of a frozen table of Ollama tags, and make llama.cpp / LM Studio /
any OpenAI-compatible server a first-class backend rather than a nominal one.

## Why — the spec already decided this and the code only half did it

Spec §169: *"Ollama-first behind an OpenAI-compatible interface … Anything speaking the
same protocol — llama.cpp server, LM Studio, vLLM — is a drop-in swap via config."*

The **transport** honours that — `src/inference/ollama-client.ts` is plain
`/v1/chat/completions` + `/v1/embeddings` against `inference.ollama_base_url`. Nothing
else does. Point that URL at a llama.cpp server today and:

- `catalog.ts` still asks for `qwen2.5-coder:7b`. llama.cpp serves whichever GGUF you
  loaded under whichever id you chose, so the name is simply wrong and there is **no
  override anywhere** — changing it means editing a frozen module-level const.
- `availability.ts` resolves "pulled?" through Ollama-**native** `/api/tags`, which does
  not exist on llama.cpp (it has `/v1/models` and `/props`). Every slot reports
  `unknown` and `availabilityWarning` shouts about a healthy endpoint.
- Every remediation string says `ollama pull <model>` — advice that cannot work.

Concrete stakes on this repo's own dev box (RTX 3070 Laptop, 8 GB VRAM): a llama.cpp
server with `-ngl 99 --n-cpu-moe 999` runs a 22 GB Qwen3.6-35B-A3B MoE by keeping experts
in RAM and attention on the GPU. That is a materially better drafter than
`qwen2.5-coder:7b` on the same hardware, and Golem currently has no way to name it.

## What to do

**The settings shape** — an array leaf, precedent `proxy.accounts` and `plugins.entries`:

- `inference.providers`: `[{ id, api: "openai-completions", base_url, api_key_env?, models: [{ id, role?, context_window?, embed? }] }]`.
- Resolution order for a role: **user provider table first, tier catalog as fallback.**
  An unconfigured install must behave byte-identically to today — an empty
  `inference.providers` changes nothing, resolves nothing, costs nothing.
- Env still wins over both, matching the existing `GOLEM_INFERENCE_*` convention.
- Whole-entry replacement, not deep merge: a provider id present in the user's config
  replaces the shipped entry for that id entirely. This is deliberate (see the design) —
  deep-merging lets a future release inject fields into a user's entry silently.

**Availability, per provider and honest:**

- Ollama provider → keep `/api/tags` (it is richer, and `matchesPulledName`'s strict
  tag semantics exist for a reason).
- Anything else → `/v1/models`. A server that lists nothing useful yields `unknown`,
  never `not-pulled`. The three-state discipline in `availability.ts` is not negotiable —
  claiming a model is missing when we could not look is the R4.4 dishonest-zero failure.
- The `ollama pull …` remediation string appears **only** for the Ollama provider.

**Context window from `/props`:** llama.cpp reports its live `n_ctx`. Read it and use it;
do not hardcode a window. If `/props` is absent or unparseable, the window is unknown and
must be reported as unknown rather than guessed.

**Surfaces to update:** `golem devices` (per-provider table), `golem local status`,
`golem local url`, the `devices` MCP tool, and the pre-run warnings
(`availabilityWarning` / `roleWarning`) that `golem bench tools` and `bench repo-map`
already print.

## Out of scope

- **Changing `src/interfaces/inference.ts`.** It is a frozen contract. This task changes
  role→model *resolution*; callers still name a role, never a model. If that turns out to
  be impossible, stop and flag it rather than editing the interface quietly.
- **Installing or downloading anything.** No `llama-server` bootstrap, no GGUF fetch.
  `golem ollama setup` stays the only place that asks to pull, and it stays Ollama-only.
- **Retiring the hardware tier.** The tier stays as the fallback for an unconfigured
  install; this task does not re-litigate Decision 6's advisory catalog.
- **Cloud providers in this table.** The local inference path is local. Upstream routing
  is `proxy.accounts` and stays there.

## Gate detail

The gate is a live run, not a unit test: llama.cpp serving a user-named model, Ollama
stopped, and the three status surfaces telling the truth. Record the result in
`docs/plan/verification-notes.md` with the date, the server command line, and the model
id — the same bar §89/§100 set for any local-model measurement.

## Progress (2026-08-01) — code complete, gate UNMET

Built and deployed; every check green (`tsc`, Biome lint + format, 2,339 tests) and the
running proxy is on the new build. Full record in **verification-notes §112**.

Landed:

- `src/inference/providers.ts` — the table and its resolution. Explicit role claims
  beat catch-alls; declaration order decides within each pass; a chat catch-all is
  never routed an embedding request (wrong-space vectors corrupt the index rather than
  degrading it); an undeclared context window stays `undefined`.
- `src/inference/openai-models.ts` — `/v1/models` and llama.cpp `/props`, with the URL
  normalisation that `/v1`-suffixed base URLs need (`/props` is at the server root).
- `availability.ts` — per-provider probing, one round trip per distinct endpoint.
  Asymmetric on purpose: unlisted is `not-pulled` on Ollama and `unknown` anywhere else.
- `service.ts` — routed first, tier ladder as fallback, routed failure outranks the
  ladder's as the reported `cause`. `inference.providers` in the settings schema.
- `golem devices` / `golem local status` — per-row provider, live window, and pull
  advice only where it can work.

**Verified live against a real OpenAI-compatible server (Ollama's own `/v1`)**: the
empty table is byte-identical to pre-R8.15, a declared provider routes and reports its
provenance, and the pull advice scopes correctly.

**Still open — this is what the gate wants.** No llama.cpp server has been run. Unproven:
`/props` returning `n_ctx` in a shape `parsePropsResponse` accepts on a current build;
`/v1/models` matching the serves-any-id reasoning; and the `-ngl 99 --n-cpu-moe 999` MoE
setup on 8 GB VRAM that motivated the task. `owner: user` for that step in practice — it
needs a llama.cpp build and a multi-GB GGUF download, which is the user's call.
