## Goal

Narrow the `level` MCP tool to levels **1–3**. Level 0 stays a fully supported
setting, reachable only from the CLI (`golem slider 0`).

## Why

Level 0 is a deliberate full bypass in which **redaction does not run** —
`LEVEL_TABLE[0].redaction === false` (`src/interfaces/policy.ts:182`), per spec
Decision 30. That is a legitimate user choice and is not in question.

What is in question is *who can make it*. Today:

- the `level` MCP tool (`src/mcp/server.ts:211`) calls `deps.sliderStore.set()`
  directly, and `sliderLevelInput` (`src/mcp/shared.ts:22`) accepts `0`;
- the write **persists across sessions** (the tool's own description says so),
  so the effect outlives the conversation that caused it;
- the only guardrail is a warning string in the tool's *response* — emitted
  **after** the write has already landed.

So any content that reaches the model's context — a poisoned tool result, a
hostile file, a crafted web page — can persistently disable the project's most
important hard rule ("redaction must never be weakened or reordered"), and the
user's only signal is a line in a tool result they may never read.

## The precedent being mirrored

ADR-0002 already settled this exact question for the autonomy level (threat item
4, "Level tampering / injection"):

> The level cannot be set from within a tool call (no MCP surface writes it) —
> only the explicit `golem autonomy` CLI.

and, in the same item, an invalid value resolves to the **most restrictive**
setting, never the least.

The slider tool currently does the opposite of both halves: it is writable from
a tool call, and the value it can write includes the *least* safe setting in the
product. This task brings it in line.

## Not a contradiction of Decision 8

Decision 8 puts the slider on MCP so the model can "request more context
fidelity mid-task". That intent is preserved exactly — the model keeps 1–3, so
it can still raise fidelity or dial compression. The only capability removed is
turning redaction **off**, which was never what Decision 8 was for.

## Scope

- `level` tool rejects `0` with a clean, actionable error naming the CLI path
  (`golem slider 0`) and stating that level 0 disables redaction. **Reject
  before the write** — never persist then warn.
- Keep the legacy 4/5 → 3 mapping intact.
- Update the tool description so the accepted range is honest.
- `.claude/skills/golem/bypass/SKILL.md` currently instructs the agent to "Call
  the `level` MCP tool with the chosen level", including 0. Rewrite it to route a
  true full bypass to the CLI, and to prefer level 1 (its existing advice) for
  everything else. Check `.claude/skills/golem/slider/SKILL.md` for the same.
- Check whether `sliderLevelInput` is shared with any other MCP surface before
  narrowing it; if it is, narrow at the `level` tool rather than the shared
  schema so nothing else changes meaning.

## Out of scope

- **Changing `LEVEL_TABLE` or anything in `src/interfaces/policy.ts`** — it is a
  frozen contract, and Decision 30 (a USER decision) stands: level 0 remains a
  real, supported, fully-bypassing level.
- Removing level 0, or making it harder to reach from the CLI.
- The `x-golem-bypass` per-request header — a different mechanism, unchanged.
- Any change to how a level-0 state is *reported*. `status`, `statusline`,
  `stats` and the VS Code surfaces must keep surfacing it loudly; this task
  narrows who can set it, not how visibly it is shown.

## Watch for

- A level-0 state set via the CLI must still round-trip through the MCP surfaces
  that *read* it. Narrowing the input must not make `stats`/`level` unable to
  report an existing 0.
- The error path is the security boundary here, so it deserves a test of its own:
  assert that a `level: 0` tool call leaves the persisted value untouched.
