## The defect

Found live on 2026-08-14, diagnosing a duoop session that had stopped answering
entirely on `openrouter:deepseek/deepseek-v4-flash-0731`.

`toolResultText` flattens a `tool_result`'s content blocks to a string, and
anything that is not a text block goes through `JSON.stringify`:

```ts
if (bb.type === "text" && typeof bb.text === "string") parts.push(bb.text);
else parts.push(JSON.stringify(b));
```

Claude Code's `Read` on a `.png` returns an **image block inside a
`tool_result`**. So each screenshot became its own base64 payload serialised as
prose and handed to the model as a `role:"tool"` message.

Measured on the real transcript (`b926139c…jsonl`, 247 messages):

| tool_result | tool | bytes |
|---|---|---|
| idx 180 | `Read` | 501,802 |
| idx 199 | `Read` | 576,342 |
| idx 217 | `Read` | 624,112 |

That is ~1.7 MB of the conversation's 1.87 MB — roughly **420k of its 468k
tokens** — of base64 text. deepseek-v4-flash has no vision (`modalities.input:
["text"]`), and fed that, it returned an empty completion: HTTP 200,
`stop_reason: end_turn`, `output_tokens: 0`, zero content. Claude Code then
injects `[Your previous response had no visible output…]` and loops. That
session had been doing so since `2026-08-13T06:23:13Z`.

Removing any one of the three screenshots restored answers immediately;
stripping thinking blocks, empty turns and nudges changed nothing.

The failure is silent precisely *because* of the stringify. Sent as real image
blocks the same model gives a clean, actionable error:

```
{"error":{"message":"No endpoints found that support image input","code":404}}
```

## What to build

**1. A capability signal in the catalog.** models.dev already carries it, and R8.8
already caches that document as Golem's own data — so this is a field, not a new
runtime dependency:

```json
"modalities": { "input": ["text"], "output": ["text"] }
```

Add `inputModalities` to `ModelCatalogEntry`, populate it in
`normaliseModelsDevPayload`, and set it on the built-in Claude entries. Resolve a
target's vision support where the translator is built (`buildUpstreamTransport`)
and pass it into the request translation.

**2. Vision-aware translation.** With vision, images must actually reach the
model; without it, they must cost ~20 tokens instead of 125k.

- OpenAI's `role:"tool"` message takes text, not image parts — so images found in
  a `tool_result` cannot ride along inside it. Hoist them: emit the tool message
  with a short marker in place of each image, then follow it with a `role:"user"`
  message carrying the `image_url` parts.
- Without vision, replace each image with a one-line placeholder naming the media
  type and size. It must read as an omission, not as data.
- Leave top-level `image` blocks in a user turn on today's `imagePart` path when
  vision is supported.

**3. Unknown stays pass-through.** A model absent from the catalog keeps current
behaviour. A wrong "no vision" guess silently blinds a model that can see; a
wrong pass-through produces the 404 above, which says exactly what is wrong.

## Watch for

- **Do not weaken the placeholder into silence.** Dropping an image with no trace
  is how a model answers confidently about something it never saw.
- Tool-call pairing must survive the hoist: the `role:"tool"` message still has to
  directly answer its `tool_call_id`, and the hoisted user message must come after
  every tool message for that turn, or providers that validate ordering will 400.
- `combineContent` returns `null` for an assistant turn with no text and no
  images. With no `tool_calls` that yields `{role:"assistant", content:null}`,
  which is malformed for OpenAI-compatible endpoints — 22 such messages (all
  thinking-only turns) were in the transcript. Emit `""` in that case.
- Base64 in a `data:` URI is still large. This task stops it being *prose*; it
  does not resize images.

## Out of scope

- The `count_tokens` gap (R10.15) and the streaming keepalive gap (R10.16), both
