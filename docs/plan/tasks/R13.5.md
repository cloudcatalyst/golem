## Why this exists

R13.3 produces a stream of session events and accepts messages. This task is the
wire between that and a phone, and its whole job is to be honest about state:
ADR-0006's rule — "a dropped link shows not connected, never a stale approved,
never a queued decision that might land later" — is inherited here for
conversation, where the same failure looks like a message the user believes they
sent.

## What to build

1. **SSE for the downstream.** One endpoint per attached session, emitting typed
   events (assistant text delta, tool call, tool result, permission question,
   turn end, session end). No WebSocket dependency; no framework. Reconnect with
   a cursor so a client can resume from where it dropped.
2. **POST for the upstream.** One endpoint that takes a message, requires a valid
   client certificate and a live user factor (R13.4), records attribution (R13.3, invariant 4), and returns
   **only after delivery is real** — the ADR's §3b point is that injection is
   acknowledged, so do not undermine it here by acknowledging optimistically.
3. **Backpressure and bounds.** A slow client must not stall the session; a
   flood of messages must not queue unboundedly. Say what the limit is in the
   error rather than dropping quietly.
4. **Idempotency.** A message carries a client-generated id so a retry after a
   dropped connection cannot double-send. This matters more than it looks: a
   duplicated instruction to an agent is not a duplicated packet.
5. **Connection state as a first-class event.** The client is told, not left to
   infer. When the session ends, or the park fires, or the host dies, the stream
   says which — invariant 3 in wire form.

## Out of scope

The UI (R13.6). Starting or branching sessions (R13.8). Injection into a live
harness session (R13.7) — different mechanism, and its delivery semantics are
its own. Any transport beyond the local network (invariant 9). Push notification
(R12.6).

## Gate detail

Integration tests over the real server: attach, receive a full turn's events in
order, POST a message and observe it delivered, kill the connection mid-turn and
resume with no loss and no duplicate, and assert an unpaired POST is refused.
Plus a test that asserts a disconnected client is told so. Wiki page documenting
the event shapes, because a device client (R13.6) and any future one will code
against them.

## Outcome

shipped — SSE downstream + POST upstream behind mTLS; seq-based resume with gap reporting, idempotent by messageId, acknowledged only on real delivery
