## The defect

R9.12's wiring adds this to `.claude/settings.json`, which **is checked in**:

```json
"NODE_EXTRA_CA_CERTS": "D:\\Personar\\Source\\repos\\golem\\.golem\\loopback\\ca.pem"
```

An absolute path, specific to one machine and one checkout location, in a file every clone
receives. On any other machine the path does not resolve, and Claude Code says so twice at
every start — measured during R9.12 with a deliberately missing file:

```
warn: ignoring extra certs from <path>, load failed: error:10000002:SSL routines:OPENSSL_internal:system library
Warning: Ignoring extra certs from `<path>`, load failed: No such file or directory
```

Not dangerous — TLS still works, and the green path simply degrades to R9.7's deny floor —
but it is noise Golem inflicts on someone who never opted in, and it makes `golem init`
produce a diff that is actively bad to commit.

`ANTHROPIC_BASE_URL` does not have this problem: `http://localhost:<port>` is portable.

## Options

- **Write it to `.claude/settings.local.json` instead** — the gitignored, machine-local
  scope, which is exactly what a machine-specific path is. Needs checking that Claude Code
  reads `env` from the local scope with the same precedence.
- Keep it in the committed file but write a **relative** path, if Claude Code resolves
  `NODE_EXTRA_CA_CERTS` relative to the project (it probably does not — verify before
  relying on it).
- Have `golem init` detect that the existing value is a *stale Golem path* (same filename,
  different root) and rewrite it silently, so a clone self-heals on first init.

The first is almost certainly right; the third is a good companion regardless.

## Watch for

- Whatever scope it lands in, `golem uninit` must still remove it, and the "never clobber a
  value someone else owns" rule (§121-C) still applies.
- `golem status` reads the committed file today to report `wired` — it must follow.

## Outcome

shipped — CA trust moved to .claude/settings.local.json, committed file self-heals
