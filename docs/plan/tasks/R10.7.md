## The defect

The P_MIN tier in `src/inference/catalog.ts` declares:

- `textEmbed: "bge-m3"` — 1024-dim
- `codeEmbed: "nomic-embed-text"` — 768-dim

Both feed the SAME collection. `FileVectorDriver.upsert` resets the whole
collection whenever the incoming vector width differs from the stored one, so on
P_MIN a mixed text/code ingest can thrash: each kind of file wipes the other's
vectors and re-embeds.

Every other tier pairs same-width models, which is why this has gone unnoticed —
P_MIN is the lowest-capability tier and the least exercised.

## Why it is being recorded rather than fixed

R10.6 hit it while pinning the build-side embedder and deliberately left it: its
hard rules forbade changing the tier catalog's model choices, and that is the
right constraint — swapping a model on a tier changes retrieval quality for
everyone on that hardware and deserves its own decision.

Note R10.6's pin path sets `text` and `code` to the same model, so a pinned build
incidentally avoids this. That is a side effect, not a fix: an unpinned P_MIN
build still has it.

## Options

- **Pair the widths at P_MIN** — smallest change; needs a judgement about which
  model, and a note on what it costs the other kind of content.
- **Separate the collections (or namespace by width)** — fixes the class rather
  than the instance, and would also make a future mixed-width tier safe. Bigger.
- **Refuse at build time** — surface the mismatch instead of silently thrashing;
  weakest of the three but better than the current silence.

## Watch for

`FileVectorDriver.upsert`'s reset-on-width-change is doing exactly what it should
in isolation — do not weaken it. The bug is upstream, in asking one collection to
hold two widths.

## Outcome

shipped: P_MIN codeEmbed raised to bge-m3 so text and code share a width; direction chosen because textEmbed drives the signature and every query. Class guarded by a per-tier width test derived from the HardwareTier enum, with an anti-vacuity check, verified to fail on the old pairing.
