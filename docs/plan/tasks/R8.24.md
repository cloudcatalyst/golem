## Problem

`isHighEntropyToken` requires all three character classes to be present:

```ts
export function isHighEntropyToken(value: string): boolean {
  // requires lowercase, uppercase, AND digit all present
  const hasLower = /[a-z]/.test(value);
  const hasUpper = /[A-Z]/.test(value);
  const hasDigit = /[0-9]/.test(value);
  if (!hasLower || !hasUpper || !hasDigit) return false;
  // ... entropy calculation ...
}
```

A base32-encoded secret uses only uppercase letters A–Z and digits 2–7. It has no lowercase characters, so it fails the `hasLower` check and passes through undetected. A base64 secret (the dominant format for API keys, tokens, etc.) has all three classes and is caught correctly. This gap affects provider-specific secrets that use base32 (e.g., some TOTP seeds, certain legacy API formats).

## Fix

Relax the character class requirement: a high-entropy token needs at least two of the three character classes, not all three. Or use a separate branch for uppercase-only + digits patterns:

```ts
const hasLower = /[a-z]/.test(value);
const hasUpper = /[A-Z]/.test(value);
const hasDigit = /[0-9]/.test(value);
// Need at least 2 of 3 character classes (catches base32: uppercase + digits, no lowercase)
if ((hasLower ? 1 : 0) + (hasUpper ? 1 : 0) + (hasDigit ? 1 : 0) < 2) return false;
```

## Out of scope

- Adding base32-specific detection (the 2-of-3 heuristic catches it without a separate code path)
- Modifying the entropy threshold itself
- Any changes to the redaction rules' regex patterns
