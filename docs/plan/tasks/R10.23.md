## The defect

Reported by the user, on their own traffic:

> When I was using the deepseek model through the proxy I kept getting errors
> that stated "Golem The upstream model "deepseek/deepseek-v4-flash-0731"
> returned an empty completion — no text and no tool calls. This is the
> upstream's response, not a reply from the model." and I would get no further
> updates. I didn't seem to get this when using the qwen models, even though
> both of these were accessed via openrouter.

Three separate faults, stacked so that the first one wore the second one's name.

**1. The mid-stream error frame was discarded.** An OpenAI-schema gateway that
fails *after* the headers have gone out cannot change the HTTP status, so it
reports the failure as an ordinary `data:` frame carrying a top-level `error` —
OpenRouter documents exactly this, usually alongside `finish_reason: "error"`.
`#handleLine` dropped every frame without a `delta`, so "Provider disconnected
unexpectedly", a mid-stream rate limit and a provider 502 all arrived as *no
frames at all*. `#blockCount` stayed 0, R10.18's generic empty-completion notice
fired in the real cause's place, and `mapStopReason("error")` → `end_turn`
closed the stream as a turn that had finished normally. Hence "no further
updates": in-band prose IS a completed turn, so the client renders it and waits
for the user.

**2. The reasoning trace was dropped on every OpenRouter model.** Both
translators read only `delta.reasoning_content` / `message.reasoning_content`.
OpenRouter documents `reasoning_content` as a **request-side alias** and returns
the trace as `reasoning` (+ a structured `reasoning_details`). This is the "no
thinking deltas arrive from OpenRouter" open question left **unverified** in
[verification-notes §84]; it is now answered — see §128.

**3. The pipeline could hold a live request open, unbounded and unlogged.**
Unrelated to OpenRouter, and the likely cause of the user's second report ("one
occurrence of calls to the default claude opus 5 model giving 'waiting for API'
for a short period"). Stage 1.5 (local answer, Decision 33) `await`s a vector
search — and therefore an embedder, which on a cold local model is a
multi-second first call — inline, before the request is forwarded. It is
eligible only on single-turn requests, i.e. exactly the ones that OPEN a
session, so the first turn of a session was the one that paid. Nothing bounded
it and nothing logged it, so the wait was indistinguishable from upstream
latency and the API wore a delay it did not cause.

## What was built

- **Anthropic's streaming `error` event** as the translated stream's way of
  saying "this did not finish" (verified shape: docs.claude.com streaming,
  2026-08-19 — `event: error` / `{"type":"error","error":{"type":…,"message":…}}`,
  and the spec allows it at any point in the stream). The upstream's code maps
  onto Anthropic's own error types (429 → `rate_limit_error`, 401 →
  `authentication_error`, 503 → `overloaded_error`, else `api_error`), and the
  message names the model, the serving provider and the upstream's own text,
  attributed to the upstream (Decision 25). Nothing is emitted after it.
- **`reasoning` and `reasoning_details`** read on both paths, plaintext
  preferred so a gateway that sends BOTH (OpenRouter does) cannot duplicate the
  trace. `reasoning_content` still works for DeepSeek-direct and Moonshot.
- **A "visible output" gate** replacing R10.18's `content.length` check. Once
  the trace is mapped, a reasoning-only answer has content and no *visible*
  content — the same "no visible output" loop R10.14/R10.18 fought, one costume
  over. Nothing at all stays an error; a trace-with-no-answer keeps the trace
  and gains an attributed notice beside it, on both paths.
- **An error-shaped 200 body** (`{"error":{…}}`, no usable `choices`) relayed as
  the upstream's refusal instead of surfacing as `ZodError` blaming Golem's
  translator.
- **A 2s budget on the local-answer stage**, fail-open exactly as its error path
  already was, plus a one-line `golem proxy: pipeline held this request Nms …`
  log with a per-stage breakdown past 750ms.

## Deliberately NOT built

- **A proxy-level retry.** The proxy has none, anywhere, and adding one belongs
  in its own task with its own idempotency thinking. R10.23 instead makes the
  failure *retryable by the client*, which is the client's job to do.
- **`reasoning: {effort}` on the request.** `proxy.upstream_reasoning_effort` is
  sent as OpenAI's `reasoning_effort`, which OpenRouter does not document —
  their parameter is a nested `reasoning: {effort}` object. So the setting is
  probably inert on OpenRouter, which is the exact "config that cannot take
  effect" the §84 debrief warned about. Recorded in §128; it needs its own task
  because it changes what is SENT (and therefore cost), not how a response is
  read.
- **The max_tokens case as an error.** It is deterministic — a retry spends the
  budget the same way — so it stays in-band where the reader can act on it.

## Live verification (2026-08-19)

Against the user's own configured OpenRouter account, real bytes fed through the
built translator:

| case | result |
| --- | --- |
| real `deepseek/deepseek-v4-flash` stream | `delta.reasoning` + `delta.reasoning_details` on every chunk, `reasoning_content` **never** |
| real stream truncated mid-reasoning | trace kept as a labelled thinking block, notice appended in-band, valid terminal events |
| OpenRouter's documented error frame | single `error` event naming model, provider (StreamLake) and "Provider disconnected unexpectedly"; no `message_stop` |
| empty stream | single `error` event, `api_error`, wording preserved from R10.18 |

`qwen/qwen3.7-flash` streams a trace too, so the reported deepseek/qwen
asymmetry is not "one reasons and one does not" — it is how much of the budget
the trace eats, plus which provider OpenRouter routed to.
