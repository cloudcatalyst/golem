## STATUS 2026-08-10: SHIPPED, default-on (§124)

The green path works and is on by default. §123 (below) concluded it could not ship;
§124 overturned that by constraining the CA instead of forbidding it. Both halves of the
gate were proven by live `claude -p` runs against the built artifact:

| session | WebFetch of a cached URL | evidence |
|---|---|---|
| `NODE_EXTRA_CA_CERTS` naming Golem's CA | **green** | `is_error=false`; model answered `Example Domain` from `additionalContext`; no network fetch |
| no such env (every un-wired session) | **red, unchanged** | `is_error=true`, `NOT AN ERROR — Golem served this URL from its knowledge base…` — R9.7's text verbatim |

What ships: a `CA:TRUE, pathlen:0` anchor carrying
`nameConstraints=critical,permitted;DNS:golem.invalid`, signing a leaf whose SAN is
`IP:127.0.0.1` only. The constraint is enforced by the client — a leaf that also carried
`DNS:api.anthropic.com` was refused with `permitted subtree violation`. Zero new
dependencies (`verify-deps: 5 runtime … all pinned exactly`). `golem init` sets the env
**only when unset**, prints what it trusted and why, and `--no-loopback-cert` declines;
`golem uninit` removes it again, and leaves a foreign value alone.

Residual risk, unresolved by design: the `iPAddress` name form cannot be constrained
(BoringSSL rejects the anchor outright if it is), so the CA key could mint a certificate
for any IP literal. It cannot mint one for any hostname outside `*.golem.invalid`. See
§124.

## SUPERSEDED 2026-08-09: measured, and the green path does NOT ship (§123)

Built and tested end to end. The result is **REGRESSED**, which this task's gate names as
an acceptable answer. Claude Code on Windows is a compiled **Bun** binary using
**BoringSSL**, and BoringSSL refuses a `CA:FALSE` leaf as a trust anchor — measured three
ways, including an `openssl`-generated leaf as a control to rule out Golem's own DER:

| trust anchor in `NODE_EXTRA_CA_CERTS` | live `claude -p` WebFetch |
|---|---|
| Golem's hand-rolled `CA:FALSE` leaf | FAIL — `unable to verify the first certificate` |
| `openssl` `CA:FALSE` leaf (§121's recipe) | FAIL — `unable to verify the first certificate` |
| `openssl` `CA:TRUE` self-signed | **OK** — served, `is_error=false` |

So green requires a **CA** in Claude Code's process-wide trust, which this task's own "Out
of scope" forbids and §120 objected to for good reason. §121's "ship a leaf, never a CA"
was measured against Node/OpenSSL and does not transfer.

**What is in the tree:** the whole path is built and passing (2511 tests), but the green
decision and the endpoint are behind `GOLEM_LOOPBACK_SERVE=1`, off by default, so shipped
behaviour is byte-for-byte R9.7. What survives independent of the verdict is §122's
`additionalContext` finding — confirmed live: when the rewritten fetch failed, the page
still reached the model, which answered from it and reported the failure accurately.

**The open fork** (needs a decision, see §123): accept the red dot permanently and delete
the machinery; ship a CA anyway with eyes open; or measure the one shape not yet tried — a
publicly-trusted certificate for a hostname that resolves to `127.0.0.1`, which needs no
trust-store change at all, at the cost of a third-party domain dependency.

## Goal

Make R9.7's red dot go away **by default**, without asking the user for anything and
without any session being worse off than it is today.

R9.7 declined the loopback design; §121 withdrew its cert reason; §122 then withdrew the
two reasons that remained. What is left is a design with a hard floor: every session
either gets the green path or gets exactly what R9.7 ships.

## What §122 already established (do not re-derive)

- `additionalContext` on a `permissionDecision: "allow"` **reaches the model**, as a
  `<system-reminder>` prefixed `PreToolUse:WebFetch hook additional context:`.
- It is delivered **even when the tool call fails** (measured with a rewrite to a dead
  port returning `ECONNREFUSED`). Content delivery is decoupled from tool success.
- Over ~10 KB it is moved to a `tool-results/*.txt` file behind a 2 KB preview, so the
  existing `MAX_SERVED_CHARS = 8_000` cap + CCR ref stays the right shape.
- `updatedInput` replaces the **entire** input object, so `prompt` must be carried through.
- WebFetch upgrades `http`→`https` and validates the cert; `file://`/`data:` are rejected.
  HTTPS on `127.0.0.1` is the only reachable shape.
- A self-signed `CA:FALSE` leaf in `NODE_EXTRA_CA_CERTS` validates and **appends to** the
  default store. Ship a leaf, never a CA.
- The global `golem` being a junction to the repo means a `npm run build` takes effect on
  the next hook invocation — hook iteration needs no Claude Code restart (settings `env`
  still does, §112).

## The design

**The endpoint serves a stub, not the page.** This is the whole unlock. The loopback
response is a few hundred bytes ("Golem served <url> from its knowledge base; the content
is in the accompanying context"), so WebFetch's summarizer runs over a stub instead of a
page. The **raw cached text** goes to the model via `additionalContext` — prompt-independent
and un-summarized, so Decision 42 is preserved rather than inverted.

**Three-state serve path**, decided per call:

| state | hook output | dot |
|---|---|---|
| endpoint trusted *and* proven reachable this session | `allow` + `updatedInput.url`→stub + `additionalContext`=page | green |
| anything else (no cert, cert not trusted, endpoint down, cloud/Desktop session, `NODE_EXTRA_CA_CERTS` owned by someone else) | today's `deny` + page in `permissionDecisionReason`, unchanged | red |
| raw-mode off / cache miss that fails to self-fetch | unchanged fail-open | n/a |

The fallback is the *known-good* path, not a second implementation of it — §122's caveat:
a failed rewrite renders an opaque `ECONNREFUSED`/TLS error where today's deny renders
Golem's `NOT AN ERROR —` framing, so `deny` must stay the floor rather than being replaced
by a rewrite that might fail.

**Trust detection, in order of strength.** No flag, no user question:
1. The hook is a child of Claude Code, so `process.env.NODE_EXTRA_CA_CERTS` in the hook
   *is* what Claude Code was started with. Pointing at our cert file → strong first-turn
   signal, available before any fetch has happened.
2. A latch in `.golem/state/` recording that a real WebFetch actually arrived at the
   endpoint upgrades that from "probably" to "proven".
3. Neither → deny-and-serve. First fetch of a session, or any doubt, takes the floor.

## Scope

- **Cert lifecycle.** Generate a leaf (SAN `DNS:localhost,IP:127.0.0.1`,
  `basicConstraints=critical,CA:FALSE`, `extendedKeyUsage=serverAuth`) into `.golem/`,
  key permissioned as tightly as the platform allows. Cross-platform, so no `openssl`
  dependency — see **Open question** below. Handle expiry and regeneration.
- **The endpoint.** HTTPS on loopback serving the stub for `?u=<url>` with a per-run
  unguessable nonce from `.golem/state/` (any process on the machine can reach it). The
  endpoint no longer needs to serve page content at all, which also removes the
  "redaction before storage" hazard from the serve path — but the cache/ingest path it
  shares is unchanged and redaction still runs before storage.
- **The hook**: the three-state decision above, plus the latch write.
- **`golem init` wiring**: set `NODE_EXTRA_CA_CERTS` **only when unset** (§121 C), print
  one line and stay on the floor otherwise. Say plainly that a restart is required (§112).
- **`golem status` row** saying whether the cert is trusted *in the session that is
  actually running*, and which of the three states the last serve took.

## Out of scope

- Installing anything into the **OS** trust store (`owner: user` territory).
- Any form of CA. If a design needs signing power, it is the wrong design.
- The proxy-side summarizer short-circuit (§120 part (b)) — it puts the raw page in
  context whole.
- Serving page **content** from the endpoint. §122 makes that unnecessary, and it is what
  made the old design a fidelity regression.

## Settled: the cert generator adds NO dependency

Decided 2026-08-09 (user). The leaf is built by **hand-rolled minimal X.509 DER over
`node:crypto`** — a fixed template written as ASN.1 and signed with `createSign`, verified
in tests by parsing it back with `node:crypto`'s `X509Certificate`. Rejected: a pure-JS
X.509 library (breaks the five-dep floor for a cosmetic feature) and shelling out to
`openssl` (makes the green path depend on what happens to be installed — on Windows, on
Git-for-Windows shipping `openssl.exe`). The template never varies, so the ASN.1 surface
stays small and parser-checkable.

## Watch for

- **A restart is required** for `NODE_EXTRA_CA_CERTS` to take effect (§112), so the enable
  path must say so rather than appearing to work immediately. Until the restart the floor
  path runs, which is correct and invisible.
- **Do not clobber someone else's `NODE_EXTRA_CA_CERTS`.** Concatenating their bundle with
  ours creates a copy that goes stale when theirs rotates. Set only when unset.
- **The residual token cost is real**: one summarizer call over the stub per served fetch,
  on top of the `additionalContext` payload. Small and fixed, but it is not zero and
  `golem stats` should be able to show it.
- **Verify the stub's summarizer output is harmless.** The model sees WebFetch's answer
  *about the stub* as the tool result, alongside the real page in context. The stub text
  must make that unambiguous.
