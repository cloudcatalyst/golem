## The defect

`golem init` registers `web-fetch-pre` with `timeout: 15`. On a cache miss the hook fetches
the page itself (Decision 42 raw mode) before serving it. For a large page that takes
longer than 15s, so Claude Code kills the hook and runs WebFetch normally.

Observed with `https://www.rfc-editor.org/rfc/rfc5280` (327,623 chars after extraction):

- the web cache **does** contain it, `raw: true` — Golem's own fetch completed
- the tool result was WebFetch's genuine answer about the RFC, not Golem's serve label —
  so Claude Code fetched the same page a second time and paid the summarizer for it

Both halves happened: one download by Golem, one by WebFetch, plus a summarizer call. The
user sees a normal answer, so nothing looks wrong; the cost is silent. It self-heals from
the *next* fetch onward, because the cache write landed.

## Why it is not just "raise the timeout"

The pre hook blocks the tool call while it runs, so a generous timeout turns a slow page
into a long stall with no feedback. The real question is what Golem should do when it
cannot serve within budget:

- decline early (fail open) **before** starting an expensive fetch it may not finish, so
  only one download happens; or
- serve from a partial/streamed read; or
- fetch in the background, serve the deny/floor this time, and have the *next* fetch hit.

The third is closest to how the cache already behaves, and costs one slow fetch once.

## Scope

- Bound the self-fetch by the hook's own budget rather than the platform's kill: know the
  timeout, and give up early enough to fail open cleanly.
- Decide and record which of the strategies above applies.
- A test with a deliberately slow fetcher proving only one fetch is paid for.

## Watch for

- The timeout lives in `.claude/settings.json`, written by `golem init` — the hook cannot
  read it from the payload, so any budget it enforces has to be kept in step with what init
  writes, or derived from a single constant.
