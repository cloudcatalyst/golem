## The asymmetry

Found 2026-08-14, tracing the R10.14 empty-response bug.

**Response side** — Golem CREATES thinking blocks. A reasoning model's
`reasoning_content` becomes a leading Anthropic `thinking` block, in both the
non-streaming and the streaming translator:

```ts
content.push({ type: "thinking", thinking: reasoning });
```

**Request side** — Golem DISCARDS them. `translateMessages` handles `text`,
`image` and `tool_use` on an assistant turn. There is no `thinking` branch, so
the block falls off the end and nothing is sent upstream.

So Golem manufactures reasoning into the transcript and then withholds it from
the model that produced it. Every turn, the model sees a conversation in which
it apparently thought nothing.

This was visible in the real duoop transcript: 22 assistant turns were
thinking-only, and all 22 translated to a message with no content at all. R10.14
fixed the malformed shape that produced (`content: null` → `""`), which was the
urgent half. It deliberately did not decide what SHOULD be sent.

## An observed instance (2026-08-14)

A user opened a fresh conversation in a third project, also on
`openrouter:deepseek/…`, and saw a block of garbled text before any answer: a
jumbled reconstruction of hook names, MCP tool lists, and finally a first-person
line — *"The user is asking about a CLI tool usage … I should investigate the
code rather than use context7."*

That last line is a reasoning trace verbatim. The model had spent its reasoning
echoing its own context, and Golem — `map_reasoning_to_thinking` defaults to
`true`, and this model is `reasoning: true` on models.dev — faithfully turned it
into a `thinking` block and handed it to the client.

It read as a data leak. It was not: the block named `mcp__golem__log`, a tool
that **does not exist** in the 12-tool registry, which is only possible if the
model invented it. But a user cannot know that, and *"is your proxy mixing my
projects together?"* is an expensive question to have to ask.

So there is a third question beyond the two directions: **should a synthesized
thinking block be surfaced unlabelled at all?** Golem's carries no `signature`
(documented as display-only, non-Anthropic in origin), which may also be why it
rendered inline rather than as collapsed thinking. Whatever is decided about
sending reasoning back, the block Golem invents on the way out should be
identifiable as Golem's reconstruction of the upstream's trace — not
indistinguishable from an Anthropic thinking block.

## Why this needs a decision, not just a patch

Three defensible answers, and the right one is not obvious:

1. **Keep dropping, deliberately.** Reasoning traces are large, most
   OpenAI-schema endpoints ignore an inbound `reasoning_content`, and replaying
   them costs tokens for nothing. If this is the answer, the drop belongs in a
   documented branch that says so — not in the absence of a branch.
2. **Send them back as `reasoning_content`.** Some reasoning models accept prior
   reasoning and are measurably better with it. models.dev records an
   `interleaved: { field: "reasoning_content" }` hint per model, which is a
   capability signal in the same family as R10.14's `modalities.input` and
   reachable the same way.
3. **Fold them into the assistant text.** Cheapest to implement, and wrong for a
   coding agent — it turns private reasoning into content the model will treat
   as its own prior output.

Measure before choosing. The honest default may well be (1).

## Also worth settling here

- **Signatures.** Golem's synthesized thinking blocks carry no `signature`, which
  is documented as display-only and non-Anthropic in origin. If any inbound path
  ever forwards a thinking block to a real Anthropic upstream, an absent or
  fabricated signature is an API error — confirm the byte-faithful path is the
  only one that ever carries a genuine signature, and write that down.
- The Gemini translator has the same question and should be settled with it.
