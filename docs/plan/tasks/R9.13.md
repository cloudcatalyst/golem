## Goal

R9.6 made a renamed setting keep working: the loader redirects a retired key to
its replacement and warns. What it deliberately did not do is *fix the file*, so
adoption is manual — a project that upgrades keeps its retired keys, and keeps
the warning, until a human runs `golem config set`.

The user asked, 2026-08-09, for the file to be fixed when a project realises it
is running a new version of Golem, and chose the **full auto-fix** posture: all
three scopes rewritten, with a backup.

## Why a version stamp, and what it is not

Correctness does not depend on the version comparison. The trigger for a rewrite
is **the presence of a retired key**; the stamp only decides *when to bother
looking*, so a missing, stale or wrong stamp degrades to "scanned more or less
often than needed", never to a bad rewrite. Say this in the module header — the
next reader will otherwise assume the stamp is load-bearing and guard it as if
it were.

`.golem/state/version.json`, alongside R9.5's `managed-files.json`: gitignored
by the `**/.golem/state/**` rule `init` already writes, removed by `uninit`.

## What the work is

- **`src/config/migrate-files.ts`** — sweep the three files from
  `settingsFilePaths()` against `SETTING_MIGRATIONS`. No second table.
  - retired key alone → renamed **in its original position** in the JSON object,
    value preserved. Position matters: `.golem/settings.json` is committed, and
    a key that jumps to the end of its section turns a one-line diff into a
    whole-section one.
  - retired **and** live key present → drop the retired one. Same semantics as
    the loader's shadowed-key branch (`loader.ts:231`), so the file ends up
    saying what the loader already did.
  - preserve indent and trailing-newline convention; write atomically
    (temp + rename), as `writeSetting` does.
  - **malformed JSON → report and leave alone.** Never clobber a file Golem
    cannot parse; this is `readExisting`'s existing stance.
- **Backups** to `<project>/.golem/state/config-backups/<scope>-<version>.json`
  before the first write of a run. Deliberately *not* `settings.json.bak`
  alongside the original: `.golem/state/` is already gitignored, so the backup
  does not show up as an untracked file in the user's repo.
- **`migrateOnVersionChange()`** — read stamp, compare to `VERSION`, run the
  sweep with `write: true`, stamp the new version. Best-effort throughout: a
  failure here must never stop a proxy from starting.
- **Wire-in**: `golem proxy` (foreground and daemon — its stderr reaches
  `.golem/proxy.log` since R9.8) and `golem init`. **Not** `golem status`:
  a read-only diagnostic that silently rewrites files is its own surprise.
- **`golem config migrate`** — manual sweep. `--check` by default (report, exit
  0), `--write` applies. `--dir`, `--json` like the rest of `golem config`.

## Honest reporting is the whole point of the posture

The user accepted that a committed `.golem/settings.json` may be rewritten
without being asked. That trade is only defensible if the diff is explained, so
the report is not optional decoration:

- one line per change, naming the file, both key names, and the release that
  renamed it
- one line naming the backup path
- silence when there is nothing to do

## Out of scope

- Value migrations. `migrateSliderLevel` (0–5 → 0–3) already runs at read time
  and `slider-store.set()` drops the legacy flat key; leave both alone.
- Section renames — `assertLeafRename` refuses them because `GOLEM_<SECTION>_<KEY>`
  parsing splits on the section boundary. Unchanged here.
- Removing the loader's read-time redirect or its warnings. The sweep reduces how
  often they fire; it does not replace them, and a file Golem declined to rewrite
  still needs them.
- Migrating anything outside settings files (tasks, state, knowledge index).
- Prompting. The posture chosen is auto-fix, not confirm-then-fix.
