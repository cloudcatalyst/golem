## Why this exists

"Ideally being able to start new sessions within projects using the proxy from
the companion app is also desirable" — the user's second ask, and the one that
turns the companion app from a chat window into something that can begin work.
Branching is the same capability seen from the other end: the session tree
already knows where a conversation forked, and this is the task that lets a
person fork one on purpose.

## What to build

1. **A project list worth trusting.** Enumerate the projects Golem actually
   knows — from configured roots and from conversations already observed — and
   say when a root is stale or unreachable rather than offering it. A project
   picker that offers a path that no longer exists is worse than a text field.
2. **Start a hosted session** in a chosen root, through R13.3, from the device.
   The device names it; the session belongs to the project.
3. **Fork from a turn.** Pick a conversation (R13.2's store, keyed as
   `session-tree.ts` keys it), pick a turn, and open a new hosted session seeded
   with the history up to that point. Record the fork's origin — conversation id
   and turn — so the tree shows where it came from, which is what
   `session-tree.ts`'s branch detection was built to see.
4. **The original is immutable.** A fork never rewrites, truncates or reorders
   the conversation it came from. If the original is a *live* harness session,
   the fork is emphatically a copy: nothing about the developer's running session
   changes, and the UI says so.
5. **Sensible refusals.** No store entry, evicted history, a project whose
   `.claude` wiring is missing, a root inside a worktree that resolves elsewhere
   (`ccr-ref-scope`'s lesson) — each refuses with a reason naming what it looked
   for.

## Out of scope

Non-Claude runners (ADR-0007 §10). Editing files from the device. Rewinding or
mutating a live harness session — forking a copy is the whole point, and
anything that touches the developer's own session belongs to R13.7 and its
visibility rules. Cross-machine sessions: a hosted session runs on the machine
Golem runs on.

## Gate detail

Integration tests: start a session in a temp project root and observe it live;
fork from a recorded conversation at turn N and assert the new session's context
contains turns 1..N and nothing after; assert the original store entry is
byte-identical afterwards; assert each refusal names what it looked for. Plus the
manual device demonstration in the gate line. A wiki page covering what a fork is
and is not — with the sentence that a fork of a live session does not change the
live session, because that is the assumption users will bring and it is wrong.
