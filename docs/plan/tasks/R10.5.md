## The defect

`scripts/copy-assets.mjs` copies exactly one asset:

```js
const ASSETS = [["src/compression/headroom-worker.py", "dist/compression/headroom-worker.py"]];
```

`headroom-memory-worker.py` is never copied. `defaultMemoryWorkerPath()` resolves
the worker next to the built module, so from `dist/` the file is simply absent —
the MEMORY sidecar (R3.6/C4, `knowledge.memory_federation_enabled`) **cannot
start from a built install**. It fails open, so it has been silently doing
nothing rather than erroring.

It works from source (`tsx`), which is why it was never noticed.

## Why this is not a one-line fix

Adding the file to `ASSETS` is the mechanical part. The judgement is that this
CHANGES BEHAVIOUR for anyone who has the feature enabled: today it is off-by-
accident, and afterwards it actually spawns a second Python process. That
deserves to be a deliberate act, in its own change, with its own verification —
not a drive-by line in an unrelated commit. R10.3 deliberately left it alone.

Check while there:
- whether anything else under `src/` is loaded by path at runtime and equally
  missing from `ASSETS` (the same class of bug, not just this instance)
- whether the sidecar should announce that it is unavailable rather than failing
  open silently — a feature that is enabled in config and does nothing is the
  exact "a setting that does nothing must not also say nothing" case
  `proxyLogPath`'s comment already argues for

## Out of scope

Changing when the memory sidecar spawns, or its gating.
