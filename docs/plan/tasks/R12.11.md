## Why this exists

R12.7 found that **Anthropic relays permission prompts to a channel**
(`notifications/claude/channel/permission_request`) — which is ADR-0006
capability 2, shipped first-party. Golem was about to build an mTLS pairing
layer (R12.4), a relay (R12.8), a hosted account system (R12.9) and a client
(R12.5) to carry exactly that. All five are paused pending this spike.

**A channel is an MCP server.** Golem already ships one (`src/mcp/`). So the
question is not "can we" but "does ours earn its place beside theirs".

## The question, stated so it can be answered wrongly

Golem's remaining claim is **not the transport — it is the class line.**
Anthropic's relay approves whatever the human taps; ADR-0006 §2 says
`destructive` and `outward` are never remotely approvable, and ADR-0002's
`classifyAction` is what enforces that. So:

**Can Golem enforce its class line on an approval that arrives through
Anthropic's channel relay?**

If yes, the paused stack is largely unnecessary and Golem's contribution is
policy sitting in a hook it already owns. If no — if the relay bypasses
`PreToolUse`, or answers before Golem's gate runs, or cannot be told "not this
class" — then the from-scratch transport is the only way to keep the property
that made ADR-0006 acceptable, and the pause should lift.

Determine which, from live docs and a real run. Do not answer it from the shape
of the API.

## What to establish, with dates

1. **Ordering.** When a permission prompt is relayed to a channel, does Golem's
   `PreToolUse` hook still run, and does it run *before* the remote answer is
   applied? §136 records that the local dialog is held open in parallel and the
   first answer wins — establish what that means for a hook that wants to force
   `ask` or emit `deny`.
2. **Whether a `deny` survives a remote `allow`.** This is the whole spike in one
   test. §105 is the precedent: hook precedence was settled by a live run, not by
   reading, and `deny` beat a rewrite.
3. **The preview constraints, costed honestly.** Research preview;
   Team/Enterprise must enable it; custom channels need
   `--dangerously-load-development-channels`; opt-in per session by launch flag
   ("being in `.mcp.json` isn't enough"); **no delivery acknowledgement**; an
   explicitly unstable contract. Each one is a reason a shipped feature cannot
   depend on it *today* — say which would have to change, and what a user sees
   meanwhile.
4. **What a channel route does NOT give.** ADR-0006's observe tier (capability 1)
   is a read surface, not an approval path. If the channel answers capability 2,
   does anything still want a phone-shaped dashboard — and is that R12.5 reduced,
   or R12.5 cancelled?
5. **The auth collision.** §136 notes the channel path wants claude.ai/Console
   auth, which collides with Golem's account routing (ADR-0003, Decision 47).
   Establish whether that is a real conflict or a coexistence.

## Out of scope

Building either route. Reviving "continue" — Decision 59(g) declines capability 3
on the authority argument, not on feasibility, and this spike does not reopen it.
Changing ADR-0006's class line: whichever transport wins has to satisfy it, and a
route that cannot is a route this spike rejects.

## Gate detail

A dated verification-notes section, plus a recommendation naming the property that
decided it. Three acceptable outcomes:

- **Channel wins** → propose cancelling or reducing R12.3/R12.4/R12.5/R12.8/R12.9,
  with an ADR-0006 revision recording that the threat model is now satisfied by
  someone else's pipe and Golem's own policy.
- **From-scratch wins** → lift the pause, and say which of the preview
  constraints is the one that made it lose.
- **Neither yet** → the honest answer if the relay cannot be gated and the preview
  cannot be depended on. Then say what the user loses in the meantime, which is
  remote *unblocking* while keeping remote *observation*.
