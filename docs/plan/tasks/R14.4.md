## What this is

The orchestration half of [[Buzz Integration]], on top of R14.3 (`golem acp`)
and R14.2 (identities). A human or another agent `@mention`s **Golem** in a
project channel; Golem's orchestrator — its own `buzz-acp` process with its own
Nostr identity — resolves the request the way it does today (task doc lookup,
clarification) and dispatches by posting `@mention` messages to the persona
agents from R14.2, in the same thread, instead of calling the `Agent` tool.

The transport-vs-content split is the settled design decision (USER,
2026-09-19): **the dispatch prompt content does not change, only the transport
and the completion signal.** Do not re-litigate it; if it proves unworkable,
that is a `verification-notes.md` finding, not a silent redesign.

## The one thing the design got wrong: turns are not resumable in memory

[[Buzz Integration]] says Golem "watches the thread". It cannot. Confirmed in
`verification-notes.md` §19 item 7:

- `buzz-acp` holds **at most one prompt in flight per channel**. An
  orchestrator that blocks waiting for a persona reply deadlocks the channel
  that the reply has to arrive through.
- `BUZZ_ACP_IDLE_TIMEOUT` defaults to **620 seconds** and cancels a quiet turn.
- **By default a new @mention CANCELS the turn in flight.** §20 item 5 corrects
  §19 here, from `crates/buzz-acp/src/config.rs:366-378`:
  `--multiple-event-handling` / `BUZZ_ACP_MULTIPLE_EVENT_HANDLING` defaults to
  **`steer`** — *"cancel+re-prompt, framing the new mention as a message that
  arrived mid-task"*. The batched-drain behaviour §19 described is the
  **non-default `queue`** mode; `interrupt` and `owner-interrupt` are supersede
  variants. So the orchestrator must survive being cut off **part-way through a
  turn it had already started posting from**, not merely being handed two
  events at once. Both shapes are real — under `queue`, two replies still arrive
  as one prompt — so handle both.
- `!rotate` invalidates the ACP session, and `buzz-acp` respawns the agent on
  crash. Process memory is not a place state survives.

So the orchestrator is a **state machine across turns, not a loop within one**:
receive a prompt → read durable state for this thread → post zero or more
messages → **end the turn** → be woken later by a reply that mentions it. The
gate is written to prove exactly this, because an implementation that works in
one long turn will pass a naive test and fail in a real channel.

## Files, in the order to touch them

1. **`src/buzz/cli-client.ts`** — a typed wrapper over the `buzz` CLI, which is
   how an agent posts (§19 item 8; there is no ACP method for it). JSON in,
   JSON out; exit codes **0 ok · 1 user error · 2 network · 3 auth · 4 other ·
   5 write conflict** — map each, and treat 5 as retryable and 3 as fatal.
   `buzz-acp` pre-injects `BUZZ_RELAY_URL`, `BUZZ_PRIVATE_KEY` and
   `BUZZ_AUTH_TAG` into the subprocess environment, so no credential handling
   belongs here. Argument-array spawn, cross-platform, per `CLAUDE.md`.
   The dispatch call is:

   ```
   buzz messages send --channel <uuid> --reply-to <thread-root-id> \
     --mention <persona-pubkey> --content -
   ```

   with the dispatch prompt on stdin (`--content -`). **Use `--mention` rather
   than an inline `@Name`** — §19 item 6 records that Buzz matches mentions on
   the `p` tag, and an inline handle changes the message body.

   **The shell-out is settled; do not re-derive it.** §20 item 8 checked for a
   library to wrap instead: `block/buzz` publishes **no** npm package (its
   `buzz-sdk`/`buzz-core`/`buzz-cli` are Rust crates), no `@buzz-xyz/*` or
   `@block/buzz*` scope exists, and every npm hit on the name is an unrelated
   project. The alternatives are hand-rolling a Nostr client (`nostr-tools` +
   NIP-42 by hand) or calling the relay's REST surface directly, and both would
   mean reimplementing the credential handling that `buzz-acp`'s injected
   `BUZZ_PRIVATE_KEY`/`BUZZ_AUTH_TAG` give the CLI for free. If one is ever
   published, revisit — it is the same trade-off the ACP SDK decision took the
   other way in R14.3, and it only flips when there is a real library.
2. **`src/buzz/thread-state.ts`** — durable per-thread state under
   `.golem/state/buzz/<thread-root-id>.json` (gitignored): which task, which
   personas dispatched and when, which replied, what the sequence is, what has
   already been posted. Must be idempotent against replay — §19 item 7 records
   that `buzz-acp` **replays all unprocessed @mentions on startup**, so the
   same dispatch event can arrive twice and must not produce two dispatches.
   Key the dedupe on the Nostr event id.

   **It also carries the deferred half of R14.3's rate-limit policy.** R14.3
   ends a rate-limited turn rather than waiting (see its MUST HANDLE section and
   `verification-notes.md` §20); this file is where that turn leaves its place:
   a `deferred` record naming `untilIso` (the observed window reset), the reason,
   the step the sequence had reached, and the id of the status message already
   posted — so a resume neither re-posts it nor re-dispatches a persona that
   already got its brief. On waking, a thread whose `deferred.untilIso` is still
   in the future re-defers **silently** (no second channel message; one per
   deferral, keyed on that record) rather than burning another model call to
   discover the same limit. Expiry is not a guarantee of headroom — re-check
   before dispatching.
3. **`src/buzz/orchestrator.ts`** — the state machine. Given an inbound prompt
   (possibly several batched events) plus thread state, decide: acknowledge,
   ask for clarification, dispatch the next persona, summarise and finish, or
   **defer** (the rate-limit branch from R14.3 — record, post once, end the
   turn). Deferral is a state of the sequence, not an error path: a deferred
   thread resumed later must re-enter at the step it left, and a heartbeat wake
   on a not-yet-due thread must be a no-op.
   Reuses the existing dispatch-prompt content builder — the persona prompt
   from `resolvePersonaPrompt()` in `src/inference/personas.ts` plus the task
   brief — unchanged, so a persona reads the same brief whichever transport
   carried it.
4. **`src/buzz/acp-turn.ts`** (from R14.3) — route a turn to the orchestrator
   when the process was launched as the orchestrator identity, and to the plain
   persona path otherwise. One branch, at the top; keep the rest shared.
5. **`tests/unit/buzz/`** — drive the orchestrator across separate turns with a
   scripted ACP client and a faked `buzz` CLI. Assert: no dispatch is repeated
   on a replayed event; two batched replies in one prompt advance the sequence
   once; a turn that dispatches also ends; a turn cancelled mid-post (the
   `steer` default) does not duplicate what it already posted when re-prompted;
   a rate-limited turn defers, posts exactly one status message and ends; a
   heartbeat wake before `deferred.untilIso` is a no-op that posts nothing; and
   a resume after it re-enters at the recorded step.

## Sequencing and scope

- Sequence planner → coder → reviewer → scribe the way the inline flows do
  today, but one dispatch per turn — the thread is the queue.
- Post an **ack** on first mention before any long work, so the channel shows
  the request was taken up.
- Ambiguity mirrors today's clarification behaviour, posted as a channel reply
  rather than an `AskUserQuestion` call — and then the turn ends, like any
  other.
- Use the **`thread` session-scope policy** so concurrent tasks do not
  interleave in a single ACP session. The flag is now **confirmed** (§20 item 4,
  from `crates/buzz-acp/src/config.rs:353-364` and `src/scope.rs:30-42`):

  ```
  --session-policy <channel|thread>   env BUZZ_ACP_SESSION_POLICY   default: channel
  ```

  `thread` gives each canonical channel thread its own provider session; DMs
  stay conversation-scoped either way. One caveat to carry into the live gate:
  the source comment says it "ships as `channel` so thread scoping can be
  canaried and rolled back without code changes" — **implemented but shipped
  dark**, so verify it on the real relay before treating it as load-bearing, and
  make the orchestrator correct (not merely tidy) under `channel` too.
- **Settled: the orchestrator runs with `--heartbeat-interval`.** It is the only
  unattended wake, and R14.3's rate-limit policy now depends on there being one
  — a thread deferred to a window reset has nothing else to restart it if the
  humans have gone home. Set it no tighter than the ≥10s floor allows and well
  above it in practice (minutes, not seconds), with a heartbeat prompt that
  means "sweep deferred and stalled threads", and make the sweep cheap: read
  thread state, skip everything not yet due, and dispatch at most one thread per
  heartbeat.

  **Say plainly what it does not give you.** A heartbeat is dropped when busy
  and never queued, and at most one is in flight globally — so it makes
  resumption *likely*, never guaranteed. The guarantee is the channel message
  R14.3 posts, which tells a human when to poke it. Do not word that message as
  a promise of automatic resumption unless the heartbeat is actually configured
  for that identity, and surface it in `golem buzz status` so the two cannot
  silently disagree.

## Must not

- Do not hold a turn open waiting for a persona reply.
- Do not keep sequence state in process memory between turns.
- Do not remove or bypass the synchronous `Agent`-tool dispatch path for
  non-Buzz sessions — this is an additional entry point.
- Do not proceed silently when the request cannot be resolved.
- Do not let the orchestrator dispatch to a persona outside the project's
  provisioned roster from R14.2.
- Do not wait out a usage window inside a turn, and do not post a second status
  message for a deferral already recorded.
- Do not promise automatic resumption in a channel message when no heartbeat is
  configured for that identity.
