## The defect

Found by dogfooding 2026-08-06. The proxy was running (pid 63900, port 4930, full
pipeline) while `.claude/settings.json` had no `env.ANTHROPIC_BASE_URL` at all —
so Claude Code was talking **straight to `api.anthropic.com`**, with no redaction,
no compression, no telemetry. Every status surface reported success:

- `golem proxy status` → `golem proxy: running (pid 63900) on port 4930 -> https://api.anthropic.com`
- the statusline → green `⬢ Golem`, level 3, brevity full
- `golem status` → `Proxy: http://localhost:4930 — reachable`

None of them is wrong about the daemon. All of them are wrong about *Golem*.
"Running" was being reported as a property of a process when the thing the user
needs to know is whether their traffic goes through it.

R8.31 established that a live wiring pointing at a dead port is a defect and
warned about it ([proxy.ts:379-384](../../../src/cli/commands/proxy.ts#L379-L384)).
This is the mirror image — a live port with no wiring pointing at it — and it is
strictly worse, because the dead-port case fails loudly on the next request
whereas this one silently succeeds while bypassing the entire product.

## Why it is cheap to fix

`readWiringState(dir, proxyBaseUrl(port))` already returns exactly the needed
`"golem" | "foreign" | "none"` ([proxy-wiring.ts:106](../../../src/cli/proxy-wiring.ts#L106)),
is already unit-tested, and is already imported by the one surface that half-handles
this. The work is calling it on the other paths and deciding the wording — not new
mechanism.

## Surfaces

| surface | today | required |
|---|---|---|
| `golem proxy status` | warns only on `!running` | also warn on `running && owner !== "golem"` |
| `golem status` | `[--] .claude/settings.json -> proxy base URL` as a flat init checkbox, independent of the `Proxy: … reachable` line two lines below | the two must be reconciled — an unwired-but-running proxy is a contradiction the reader should not have to spot |
| statusline | `proxyRunning` from the pid file only ([statusline.ts:417-428](../../../src/cli/statusline.ts#L417-L428)); no wiring input exists | needs a wiring signal; unwired must not render as active green |
| VS Code | `runtimeControlGroup` calls `proxyStatus` only ([control-surface.ts:373](../../../src/config/control-surface.ts#L373)) | same signal, same distinction |

Three states must be distinguishable, not two: **in the path** · **running but
bypassed by the client** · **not running**. `foreign` is a fourth and already has
prior art — R8.31's rule is that another gateway's base URL is reported, never
touched, and that holds here.

## Constraints

- **Read-only.** No surface may auto-wire as a side effect of being asked for
  status. R8.31 deliberately kept `start`/`stop` out of `.claude/settings.json`;
  a status command that edits it is a worse version of the same mistake.
- **Remedy must be `golem proxy wire`, not `golem init`.** `golem status` today
  routes every unchecked box to "run `golem init`", which is a much heavier act
  than restoring one env key.
- Do not report a foreign `ANTHROPIC_BASE_URL` as Golem being off — it is a
  different situation with a different remedy, and the ownership rule already
  distinguishes them.
- The statusline runs on a 2s `refreshInterval`. Whatever signal it gains must be
  a cheap local file read on the same footing as the existing pid-file check —
  no network, no proxy round-trip.

## Out of scope

- Auto-repairing the wiring, on start or anywhere else. R8.31 settled that
  `start`/`stop` do not touch the file; this task only makes the state visible.
- Making `env` hot-reload — Claude Code owns that (§112b), unchanged here.
- Any new lifecycle state. `bypass` (R8.31) is about what the *listener* does;
  this is about whether the *client* is pointed at it. They compose; neither
  replaces the other.

## Open question

How did the wiring come to be removed? Only `golem uninit`
([init.ts:953](../../../src/cli/init.ts#L953)) and `golem proxy unwire` remove
those keys, and the user ran neither knowingly — the working tree simply showed
the `env` block deleted against HEAD. Worth a look for a third caller or a VS Code
path that unwires without saying so; if one exists it is a separate defect and
should get its own task rather than being folded in here.

## Verification

Standing bar (`npx tsc --noEmit`, `npm run lint`, `npm run format:check`,
`npx vitest run`) plus:

- A test per surface for the running-but-unwired state, asserting the output names

- A test that `owner: "foreign"` renders differently from `owner: "none"`.
- A test that no status path writes `.claude/settings.json` — pin the read-only

- Live dogfooding: `golem proxy unwire` with the daemon up, then confirm all four
  surfaces disagree with the pid file and say so.
