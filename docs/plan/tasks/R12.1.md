## Why this is the whole task

Remote permission approval is **remote authorization of code execution**. It is the
exact capability the autonomy gate (ADR-0002) exists to constrain, reached from a
device that is easier to steal than the laptop. R6.3 has sat blocked since
2026-07-30 for one reason: it is the highest-severity item on the roadmap and it
needs a threat model, not a feature memo.

So: **no code in this task.** The deliverable is prose that a later agent can build
against, and that the user can refuse.

## What the ADR must contain

Follow ADR-0002's shape — assets, adversaries, trust boundaries, failure modes —
and answer these specifically:

1. **Assets.** The developer's machine and everything the agent can reach on it:
   the working tree, credentials in the OS store (ADR-0003), the upstream account,
   the LAN. Not "a session" — name what is actually at risk.
2. **Adversaries.** (a) someone on the same LAN; (b) someone holding the unlocked
   phone; (c) someone holding a locked/stolen phone; (d) a malicious app on the
   phone; (e) the relay operator, if one ever exists.
3. **What a paired device may authorize.** The standing rule from R6.3: the
   autonomy gate stays the authority and remote approval is an **input** to it,
   never a bypass. Write down what that means concretely — can a phone approve a
   `Bash(rm -rf …)`? A `git push`? Is there a class of tool call that is
   *never* remotely approvable, and if so what defines the class?
4. **Link loss is default-deny.** A dropped connection must never mean "approve".
   State the mechanism, not the intention: the hook's own timeout, and what the
   user sees locally when it fires.
5. **Pairing, and revocation.** How a device is enrolled, what proves it, and how
   a lost phone is cut off from a laptop that may be asleep. Revocation that only
   works while both devices are online is not revocation.
6. **Audit.** Every remote decision recorded locally — who, what, when, and which
   exact request it answered. R11.7 established the standard: the proxy's own
   records must be able to answer "did Golem do this?".
7. **~~No Golem-operated service in the path. Self-hosted relay only.~~
   SUPERSEDED 2026-08-21 (USER DECISION):** the app must work over the internet,
   via a relay that requires an account. The ADR carries this as Revision 2 (§3b,
   §3c) and the constraints there — blind relay, local-only enrolment, an account
   that buys rendezvous and nothing else — are what make it safe. The build is
   R12.8 (client half) and R12.9 (the service). A capability that *cannot* be
   delivered without a third party is still named rather than quietly admitted
   (notably push, R12.6).
8. **The honest "no mitigation" rows.** At minimum: a compromised paired device is
   RCE on the developer's machine, and no property of the seam prevents that. Say
   it in the words a user would use, the way ADR-0005 said loading a plugin is
   exactly as dangerous as importing a dependency.

## Verified groundwork it should build on, not re-derive

- **The blocked-state half already exists.** `src/hooks/session-hooks.ts`
  (`runNotificationHook`) writes `.golem/state/session.json` via
  `src/hooks/session-state.ts`, and `src/dashboard/server.ts` already serves it at
  `/api/state`, bound to `127.0.0.1` with no auth. That file's header calls the
  network surface "21b's later, guarded step" — this is that step.
- **Golem is already its own CA.** `src/proxy/loopback-cert.ts` (R9.12, §121→§124)
  hand-encodes X.509 over `node:crypto` — CA + leaf, `nameConstraints`,
  `pathlen:0`, round-tripped through `X509Certificate` in tests. mTLS needs a
  client-cert issuer, and this is one. Do not propose a new crypto dependency
  without saying why that module cannot do it; the project pins five runtime deps.
- **Actuation is limited by Decision 37, not by effort.** A proxy has no reverse
  channel into Claude Code's interactive TUI. Any ADR sentence implying a phone can
  "type into" a running session is wrong. See R12.7.

## Out of scope

Building anything. A hosted relay. Choosing the client framework. Push transport
(R12.6 answers that, gated on this). Native-vs-web (R12.5).

## Gate detail

The ADR lands in `docs/decisions/ADR-0006-*.md`, gets a spec Decisions Log entry,
and the user accepts it. **"Do not build this" is an acceptable outcome** — the
same way §100 and §108 were acceptable outcomes. If the answer is no, R12.3–R12.7
get cancelled with the ADR as the record, and that is a successful task.
