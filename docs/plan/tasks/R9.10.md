## Goal

R9.3 made `coder` dispatch to any declared target and R9.4 added
`inference.worker_targets` so each worker picks its own. The capability is
target-agnostic; **the naming never followed**. Every user-facing surface still
says the worker is local, and after R9.3/R9.4 that is simply false.

Reported by the user 2026-08-09 while pointing `coder` at an Anthropic target:

> this is no longer a "local" coder, all workers should be able to use any target

## What is actually wrong

Wiring `coder` to a `claude-sonnet-5` target and asking Golem what it will do
produces a self-contradiction in one object:

```json
"local_model": {
  "reachable": true,
  "coder_enabled": true,
  "coder_model": "qwen2.5-coder:7b",
  "workers": [{ "worker": "coder", "target": "sonnet-5", "model": "claude-sonnet-5" }]
}
```

`local_model.workers[0].model` is a hosted vendor model. `coder_model` still
names the Ollama model, which is now the *fallback* for workers with no target,
not "the coder model". A reader cannot tell from this which model a `coder` call
will actually reach.

The same conflation runs through:

- **`inference.local_coder_enabled`** — a settings leaf named for *where the
  model runs*, gating a tool that no longer has to run there. The switch is
  "is the `coder` tool offered", so the name should say that.
- **`golem local enable|disable|status`** — the command a user runs to turn the
  `coder` tool on is called `local`. `golem local status` prints "Local model:
  ACTIVE" above a worker table pointing at a vendor API.
- **`local_model` in `golem status --json`**, plus the statusline and VS Code
  renderings derived from it.
- **`.claude/rules/golem-local-coder.md`** — tells the agent to draft with
  "a local model" and justifies it as leaving "the paid model's tokens" for
  judgment. With a vendor target wired, the *reason* stated in the rule is
  inverted: drafting now spends paid tokens.
- **`golem devices`** — reports the local hardware tier and local models, which
  is still correct for the local path but is presented as the coder's identity.

## What to check

- **The registry is already right.** `KNOWN_WORKERS` and `workerTarget()` are
  target-agnostic, and `target-dispatcher.ts` resolves per call: explicit
  `targetId` → the worker's `worker_targets` entry → local tiered inference.
  This task is naming, defaults and reporting — **not** a dispatch rewrite.
- **Renaming a settings leaf is a migration, not an edit.** `SETTINGS_LEAVES`
  feeds env mapping, the UI model, the control surface and the VS Code panel.
  R9.6 (config migrations — a renamed setting silently stops working) is the
  mechanism this needs; sequence the two, or the rename is exactly the silent
  breakage R9.6 exists to prevent. Keep the old key accepted with a deprecation
  warning for at least one release.
- **Decide what `golem local` becomes.** Options: keep it for the genuinely
  local concerns (Ollama endpoint, hardware tier, pulled models) and move the
  `coder` on/off switch to a worker-shaped command; or alias it. Do not leave one
  command owning both meanings.
- **The status shape is the user-visible part.** `local_model` wants splitting
  into the local runtime (endpoint, tier, pulled models — genuinely local) and
  the worker table (per worker: target, model, trust, and whether that resolves
  to local). Optional-field the additions so an older renderer degrades rather
  than breaks, per the R9.4 precedent.
- **Rewrite the guidance rule's rationale, not just its nouns.** "Draft locally
  to save paid tokens" is only true on a local target. State the actual rule —
  draft with `coder` first — and let the cost argument follow the configured
  target.

## Out of scope

Changing dispatch behaviour or the fail-closed rules (an unknown target id is
still an error, never a silent fall back to local — R9.3). Adding new workers.
Touching the redaction floor applied to non-local dispatch.
