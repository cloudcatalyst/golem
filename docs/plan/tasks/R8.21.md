## Problem

The autonomy classification patterns are evaluated as byte-level regex matches across the entire command string:

```ts
const OUTWARD_BASH = [
  /\bgit\s+push\b/,  // matches inside `ls 'git push.sh'`
  // ...
];
const DESTRUCTIVE_BASH = [
  /\brm\s+-[a-z]*[rf]/,  // matches inside `ls 'rm -rf flag.sh'`
  // ...
];
```

A quoted filename argument containing a danger pattern (e.g., `ls 'git push.sh'`, `ls 'rm -rf flag.sh'`) would be falsely classified as outward/destructive, forcing an unnecessary human approval prompt. Very low probability in practice (bizarre filenames), but technically a false escalation.

## Fix

Two options:

**Option A (minimal):** Document the false-positive risk on the pattern variables and accept it as a safe-by-default trade-off (false positive ≪ false negative for destructive commands).

**Option B (better):** Strip quoted strings from the command before pattern matching. Use a simple lexer that removes single-quoted and double-quoted strings, then match patterns against the remaining (unquoted) command tokens.

## Out of scope

- Full shell parsing (AST or tokenizer) — the quoted-string heuristic handles the common case
- Changing the approve/deny semantics of the autonomy gate

## Verification

- `npm run typecheck`, `npm run lint`, `npm run test`
- New test asserting `ls 'git push.sh'` is classified as safe (not outward)
- New test asserting `rm -rf /some/path` is still classified as destructive (the real pattern still works)
