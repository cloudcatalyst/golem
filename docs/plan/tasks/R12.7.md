## The trap this task exists to avoid

A companion app makes "send continue" look like an obvious button. It is not
buildable as it appears. Decision 37 settled this on the auto-resume half and the
reasoning transfers whole: the proxy sits *below* Claude Code as a request relay,
there is **no reverse channel into an interactive TUI**, `/resume` is a client-side
slash command the proxy never sees, and the only techniques that reach a live TUI
are `tmux send-keys` and keystroke injection — which Golem rejected on purpose.

An approve/deny button is different in kind: it answers a request the *hook* is
already holding open, so the channel exists. "Continue" invents a new user turn,
and there is nowhere to put it.

## What to decide, and write down

- **What a phone CAN do with an idle session:** nothing, in the running session.
  Confirm that is still true against the current client — this was measured in
  2026-07 and Anthropic has open feature requests in the area, so re-verify before
  restating it.
- **The honest substitute: enqueue, do not inject.** A phone can add a durable
  task (R5.1) that a headless run or the human's next local turn picks up. Decide
  whether that is worth surfacing, and if so what it must NOT look like — it must
  never be labelled "continue", because the work does not start until something
  local picks it up.
- **What the UI says instead.** If the answer is "no continue button", R12.5 needs
  a sentence in its place that tells the truth about why.

## Out of scope

`tmux send-keys`, keystroke injection, PTY wrapping, or any screen-scraping
actuator — Decision 37 rejected these as a matter of discipline, not capability,
and this task does not reopen it. Building a headless orchestration surface.

## Gate

A written answer, re-verified against the current Claude Code rather than quoted
from Decision 37, plus whichever of "enqueue a task" or "nothing" the user
accepts. "A phone cannot resume a session, and here is the sentence the UI shows
instead" is a complete and successful outcome.

## Outcome

Re-verified against Claude Code 2.1.235: Decision 37's architectural half holds, its product half does not — channels (an MCP server pushing notifications/claude/channel), Remote Control and cross-session SendMessage are supported reverse channels into a running session. Outcome unchanged: no continue button, better reasons; ADR-0006 capability-3 row and spec Decision 59(g) superseded on their reason with dated pointers (59(g) amendment left to the user). R12.5 sentence: 'There is no prompt box — this screen can answer what the agent is already asking, but nothing here can start a turn.' Enqueue kept out of R12.5. Notes §136, follow-up R12.10.
