## What happened

Claude Code showed `API Error: Connection lost mid-response. The response above
may be incomplete.` Golem was the proxy in the path. Answering "was it Golem?"
took the client's transcript, the process table and the settings — because
Golem's own records could not answer it.

## The three gaps

**1. `proxy.log` has no timestamps.** 11,655 lines of `golem proxy: routed to
"anthropic" — inference.default_target` and nothing to correlate them with. A log
whose entries cannot be placed in time cannot be used in an investigation, which
is the only reason to keep one.

**2. Nothing is logged when a request ENDS.** Only the routing decision, taken
before forwarding. No status, no duration, no bytes, no error. A request that
dies is indistinguishable from one that succeeded.

**3. Telemetry records savings, not outcomes.** `events.jsonl` carries `kind:
"usage"` rows — model, level, stageSavings. A failed request writes nothing at
all, so the store that exists to make Golem honest about its effect is silent
about its failures.

## The one Golem is uniquely placed to catch

A native Anthropic SSE stream that ends **without `message_stop`** was truncated.
The proxy is holding both sockets and can see exactly that, then say so — naming
which side closed and after how many bytes and how long. R10.23 did this for a
*translated* stream carrying an explicit `error` frame; this is the other case,
where there is no frame at all and the socket simply ends.

That turns "connection lost, cause unknown" into a line the user can read.

## Out of scope

- Retrying or repairing a truncated stream. Report it; do not invent tokens.
- Logging request or response BODIES. Redaction exists precisely so prompt text
  is not lying around; this is metadata only.
- A log-rotation scheme, unless the added lines make the file grow fast enough to
  need one (measure before deciding).

## Evidence from the incident

- One occurrence in 130 sessions, at `2026-08-21T02:21:12.680Z`, error
  `server_error`, on `req_011CeF6Ta2NPRVm23T6MTkTr`.
- The last delta landed at `02:21:04.843Z` — a ~7.8s gap before the client gave
  up — and reported `output_tokens: 3` for 151 characters of text, so the usage
  frame was not the final one: the stream ended before its `message_delta`.
- `cache_read_input_tokens: 355932` — a large-context request.
- The proxy did not crash: same pid since 10:34:25, no restart, zero error lines.
- `proxy.connect_timeout_ms` 10000, `proxy.request_timeout_ms` 600000, so
  undici's idle timeout cannot have fired on a 7.8s gap — Golem's timeouts are
  ruled out.
- Effective compression was 1 (lossless) on a caching upstream and the upstream
  is Anthropic-native, so no response-body transform was in play.

Conclusion: an upstream or network drop of the SSE socket, transient, not
attributable to Golem — but note how much of that came from OUTSIDE Golem.

## Gate

Standing verification bar, plus: a recorded-shape test where the upstream stream
ends without `message_stop` and the proxy logs the truncation (and still relays
byte-faithfully what it did receive — the client's own error path must not
change).

## Outcome

shipped. Three things, in the order they matter:

**Every proxy line carries an ISO-8601 UTC timestamp**, from one sink
(`src/shared/proxy-log.ts`) that all nine daemon-side writers now go through —
the routing decision, the pipeline-hold warning, the startup banner, the
sidecar/local-answer/loopback lines and the target warnings. UTC because the
daemon outlives DST and because the client transcripts it has to be correlated
against are UTC — which is how the incident above was reconstructed. It lives in
`src/shared/` so `src/pipeline/` and `src/proxy/` can use it without inverting
the layering.

**One outcome line per request**, after it ends:

```
2026-08-21T03:45:46.755Z golem proxy: POST /v1/messages → anthropic 200 — OK in 3.9s, 1.3 KB, 36 SSE events
2026-08-21T03:45:48.588Z golem proxy: GET / → anthropic 404 — UPSTREAM_ERROR in 268ms
```

`ProxyRequestOutcome` distinguishes `ok`, `truncated`, `upstream_error`,
`proxy_error`, `client_gone` and `answered_locally`, reported exactly once from
every terminal path — including the ones that previously returned in silence (a
client that hung up, a translated stream that broke mid-flight). Metadata only:
no bodies, no prompt text, and the query string is stripped from the path
because a query can carry identifiers.

**A truncated stream is now named as truncated.** An Anthropic Messages stream
ends with `message_stop`; one that stops without it and without an `error` event
was cut short, and the proxy is the only party holding both sockets when that
happens:

```
POST /v1/messages → anthropic 200 — TRUNCATED in 41.2s, 88.1 KB, 400 SSE events
  (last event: content_block_delta): the SSE stream ended with no message_stop
  and no error event — the response reaching the client is incomplete
```

That is the line that was missing when the incident above had to be diagnosed
from outside Golem.

### How it was built

The termination signal lives on the existing `UsageSniffer` rather than in a new
`Transform`. That scan already reads the SSE event names to route `usage`, so the
answer was one boolean away — and adding a second stream hop would have cost
every streaming response a copy to learn something the first hop already knew.
The sniffer is now constructed when EITHER consumer is listening.

### Measured, so the rotation question has an answer

181 bytes per request (87 routing + 94 outcome) against 65 before: **2.8×**, or
about 2.0 MB per 11,655 requests. No rotation needed; revisit if a single
project's log passes ~50 MB.

Both lines are kept on purpose. The routing line is the "started" record, so a
request that never finishes still leaves a trace — which is precisely the case
the outcome line cannot cover.
