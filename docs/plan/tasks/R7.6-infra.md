> static files. The portal is a Next.js app on Vercel, which has no nginx, so the
> User-Agent branching moved into `next.config.ts`. The *behaviour* this task
> verifies is unchanged; the artifact it verifies is not. Evidence and the three
> implementation gotchas: `docs/plan/verification-notes.md` §149 item 1.

## Goal

Serve the onboarding one-liner from `golem.run` and confirm the user-agent
routing actually reaches the three clients correctly — live, against the
deployed app.

## State of play

`deploy/nginx/golem-run.conf` shipped with R7 (Decision 41b/41c) and is now a
**reference implementation**: it records what the routes must do, and is what the
portal's rules were derived from. Nothing about it is deployed.

`deploy/nginx/landing.html` is superseded by the portal's
`app/(marketing)/install/page.tsx`. Decide whether it stays as a documented
fallback or is retired — do not leave two landing pages with no stated winner.

## What to confirm

- `curl -fsSL https://golem.run | sh` gets the shell installer.
- `irm https://golem.run | iex` gets the PowerShell installer, not the shell one
  and not the HTML page.
- **A Windows `curl` gets the PowerShell installer**, because there `curl` is an
  alias for `Invoke-WebRequest`. This case did not exist in the nginx framing and
  is the one most likely to be got wrong.
- A browser gets the docs page.
- `/install.sh`, `/install.ps1` and `/bin/<asset>` each resolve to real release
  assets rather than a GitHub 404.

## Why this is the user's

Domains, DNS and a deploy are credentialed, outward acts.

## Out of scope

Building the docs site. Changing the installer ladder (npm → binary → Node
bootstrap).
