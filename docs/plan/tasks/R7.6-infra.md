> **Re-pointed 2026-09-04.** This task was written against an nginx box serving
> static files. The portal is a Next.js app on Vercel, which has no nginx, so the
> User-Agent branching moved into `next.config.ts`. The *behaviour* this task
> verifies is unchanged; the artifact it verifies is not. Evidence and the three
> implementation gotchas: `docs/plan/verification-notes.md` §149 item 1.

## Goal

Serve the onboarding one-liner from `golem.run` and confirm the user-agent
routing actually reaches the three clients correctly — live, against the
deployed app.

## State of play

`deploy/nginx/golem-run.conf` shipped with R7 (Decision 41b/41c), was demoted to
a reference implementation when the portal turned out to be on Vercel, and was
**removed on 2026-09-04**: it described a box nobody stood up, and a second
dialect of the routing rules is a second place for them to drift. Git history
keeps it. The behaviour it recorded now lives in
`docs/wiki/concepts/Portal Install Contract.md`, which is what the portal's
rules are derived from.

`deploy/nginx/landing.html` went with it — the portal's
`app/(marketing)/install/page.tsx` is the winner, which is the "do not leave two
landing pages with no stated winner" question answered rather than deferred.

So this task no longer has an artifact in this repo at all. What is left is
purely the live check below.

## What to confirm

- `curl -fsSL https://golem.run | sh` gets the shell installer.
- `irm https://golem.run | iex` gets the PowerShell installer, not the shell one
  and not the HTML page.
- **A Windows `curl` gets the PowerShell installer**, because there `curl` is an
  alias for `Invoke-WebRequest`. This case did not exist in the nginx framing and
  is the one most likely to be got wrong.
- A browser gets the docs page.
- `/install.sh`, `/install.ps1` and `/bin/<asset>` each resolve to real release
  assets rather than a GitHub 404.

## Why this is the user's

Domains, DNS and a deploy are credentialed, outward acts.

## Out of scope

Building the docs site. Changing the installer ladder (npm → binary → Node
bootstrap).

## Partly cleared 2026-09-06

Two of the three blockers are gone:

- **`golem.run` resolves** (`216.198.79.1`) and the portal is deployed there,
  with Stripe, Nango, Clerk and the release webhook all reaching it.
- **`release-portal-assets` is PROVEN** by v0.53.0, so the assets the routes
  redirect to exist. `/install.sh` and `/install.ps1` both answer **307** to
  `releases/latest/download/…`.

**Still unverified is the part the gate is actually about:** that curl,
PowerShell and a browser each get the *right* thing — in particular that a
Windows `curl` gets `install.ps1`, since there it is an alias for
`Invoke-WebRequest`. That needs a browser and a real Windows shell against the
deployed app, which is why this stays `owner: user`.
