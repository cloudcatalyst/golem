## Why this exists

R13.11 made `coder` decline honestly when nothing routes it, and the user's
follow-up question was the right one: *if the harness can already run a subagent
on a different model, why would Golem spawn a second CLI to do it?*

It shouldn't. The proposal reached that conclusion before either mechanism was
built:

> "for a *capable* target there is no reason to build an agent loop inside Golem:
> a sub-agent whose definition names `golem/<target>` already gets a full agentic
> loop, its own context, and correct routing, with **zero new Golem machinery**."

What is missing is not capability — it is the **wiring**: nothing turns a
configured coder model into an agent definition, so the user has to hand-author
one and keep it in step with their Golem config.

## The three pieces

### 1. `inference.default_coder` — a model, not just a target id

Accepts either:

- a **model id** (`claude-sonnet-5`, `sonnet`) — delegate through the harness,
  on that model;
- a **target id** from the registry (`openrouter:qwen/qwen3.7-flash`) — the
  existing `worker_targets.coder` dispatch path, unchanged;
- **unset** — decline, and the work stays in the current session (R13.11).

Resolution order must stay explicit and fail-closed, exactly as R10.8's chain is:
a value that is neither a known model shape nor a declared target id raises and
names both sets, rather than guessing which was meant.

`inference.worker_targets.coder` stays as the low-level key. `default_coder` is
the one users are told about.

### 2. `golem init` generates `.claude/agents/golem-coder.md`

Golem already owns `.claude/` wiring — skills (`init-skills.ts`), hooks, settings,
`.mcp.json`. There is no `agents/` directory today; this adds one file to what
init writes and uninit removes.

Frontmatter uses the documented subagent shape (verification-notes §114 quotes
the table verbatim: *"`model` — … `sonnet`, `opus`, `haiku`, `fable`, a full
model ID (for example, `claude-opus-5`), or `inherit`"*), body carries the coder
prompt from §3.

**Use a plain model id, not `golem/<target>`.** Both work in principle and R9.2
shipped the virtual-id proxy half, but §114 **caveat 5 is still open** — the
slash in `golem/<id>` was never confirmed Claude Code-side, and R9.2 closed with
that check outstanding. A plain id sidesteps it entirely. Reach for the virtual
id only when `default_coder` names a *target* that has no plain model id of its
own, and if it is used, resolve caveat 5 first (the recorded fallback is a flat
`golem-coder`).

Why this is strictly better than what it replaces: a subagent's traffic goes
through `ANTHROPIC_BASE_URL` — Golem's own proxy — so redaction, compression and
telemetry all still apply, and it gets real tool use instead of a blind
one-shot.

### 3. `inference.coder_prompt` — one prompt, two consumers

Today the drafter framing is hardcoded as `DRAFTER_SYSTEM_LINE` in
`src/mcp/coder-tools.ts` (added by R13.11). Make it configurable, and make the
SAME text feed:

- the `system` field of a `coder` MCP dispatch, and
- the body of the generated agent definition.

**Not a skill.** The user asked; R9.11's recorded rule answers it — *"skills
orchestrate, tools execute. A skill never reimplements a tool."* A system prompt
is neither: it is configuration data, and a skill is the wrong home for three
concrete reasons.

1. **Direction.** A skill's body is injected into the *invoking* session's
   context. The coder prompt has to reach the *drafter* — a `system` field on an
   HTTP request, or a subagent's definition body. A skill would load it into the
   wrong context.
2. **Portability.** `SKILL.md` is one client's file format, and R9.11's first
   argument for keeping tools as tools is that R6.1 extends this pipeline past
   Claude Code. The MCP server must read this prompt in a process that may have
   no Claude Code at all.
3. **Semantics.** Skill frontmatter's `description` drives *when to invoke*. That
   has no meaning for a system prompt, and leaving it to rot is how a file
   becomes misleading.

So: a plain prompt file Golem owns (e.g. `.golem/coder-prompt.md`, or inline in
settings for a short one), read directly by the MCP server and copied into the
agent body at `init` time.

**There is a legitimate skill here, and it is a different artifact:** a
`/golem/coder` skill about *when* to delegate rather than do it inline, which
route to prefer, and how to frame the task. That is precisely R9.11's converse
test — *"rare, procedural, and needs prose about when"*. Worth doing; not this
setting.

**Design constraint, stated up front:** the same prompt must work for a
qwen2.5-coder:7b local drafter and for Sonnet 5. The proposal's whole argument
for `coder` existing is that a small model needs "three tools and a tight
prompt". Anything elaborate degrades the small-model path, so concise is a
requirement, not a preference.

## Retire path B — the `claude-cli` provider

R9.15 shipped drafting by spawning the official client headlessly. It was the
honest answer to "spend the subscription" at the time, and the subagent route now
does the same job better. Its own module header says why it loses:

> "`ANTHROPIC_*` goes, so the child talks direct to Anthropic on its own OAuth
> rather than looping back through Golem's own proxy via `ANTHROPIC_BASE_URL`"

That is deliberate and correct for a spawn — and it means **Golem sees none of
that traffic**: no redaction stage, no compression, no telemetry. Add a blind
text call (`--disallowed-tools` covers every file and exec tool,
`--strict-mcp-config`, a temp cwd so no `CLAUDE.md` or project state), a full CLI
cold start per draft, and a 180s timeout, and there is nothing left that the
subagent route does not do better.

Removal touches: the `UPSTREAM_PROVIDERS` member, `isSpawnProvider`, the
`dispatchSpawned` branch and `spawnDrafter` option, `createClaudeCliDrafter`'s
wiring in `mcp-serve.ts`, `src/inference/claude-cli.ts` and its tests, and the
`claude-cli` cases in `defaultAuthScheme` / `originationAuthScheme` /
`PROXY_PROVIDERS`.

**Fail closed on migration.** A user with a `claude-cli` gateway already in
settings must get a clear error naming `default_coder` as the replacement — not a
silently ignored gateway, and not a target that resolves to nothing. Same
discipline as every other unresolvable reference in the registry.

## Decide while doing it

- **Does `default_coder` replace `worker_targets.coder`, or layer over it?**
  Layering keeps one generic map for N workers (R9.4's whole argument) and adds a
  friendlier alias for the one worker that exists. Replacing it would undo that.
  Weigh it; do not collapse the map by reflex.
- **Should `coder` (the MCP tool) say anything when `default_coder` names a
  harness model?** It cannot spawn a subagent — MCP servers expose tools to the
  client and cannot invoke client tools — so the honest options are (a) silence,
  the agent definition is simply there to be used, or (b) a directive result in
  R13.11's non-error decline shape, telling the caller to delegate. (b) risks
  nagging; (a) risks the definition never being noticed. Pick one deliberately.
- **Does the generated agent need a tool allowlist?** A coder subagent with
  `Write`/`Edit` is a different autonomy proposition from one that only reads and
  returns a diff. ADR-0002's class line applies; do not grant write access by
  default without saying so.

## Out of scope

- Any change to R13.11's decline behaviour when nothing is configured. That is
  the settled default and this task must not alter it.
- The `golem/<target>` virtual-id path beyond noting it exists — using it means
  closing §114 caveat 5 first, which is its own piece of work.
- The `/golem/coder` when-to-delegate skill described above. Worth filing
  separately once this lands and there is something to describe.

  through the proxy rather than around it.

  `coder` MCP dispatch's `system` field.
