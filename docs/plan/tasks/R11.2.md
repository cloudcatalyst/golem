## What was wrong

Keeping the KB fresh costs **GPU time, at session start, on the user's machine**.
Measured on this repo (`bge-m3` via Ollama, `FileVectorDriver`): ~42 s for 8
changed files, ~10 minutes for 114. That job started unannounced on every new
session, and three separate faults made it pay far more often than the work
required.

**1. Nothing bounded it.** A branch switch rewrites mtimes wholesale, so an
ordinary `git checkout` was enough to queue hundreds of files. The automatic
caller — `golem mcp serve`, which fires on every session start — had no way to
say "this is more than I should do without being asked".

**2. Progress was not persisted until the end.** The manifest was written once,
after the last file. Any session shorter than the sync recorded **nothing**, so
the next session repeated the identical work: a GPU spike on every session start
with no file actually changing.

**3. One project could become several collections.** `canonicalProjectId` folded
drive-letter case only, so `d:/repo`, `D:\repo` and `D:\repo\` hashed three
different ways. Each spelling re-embedded the tree independently — this repo had
**three collections, 231 MB, two of them unreachable**.

## The three rules

- **A cap on the automatic path.** `knowledge.auto_index_max_files` (default
  `50`, `0` disables the cap). Past it the sync embeds nothing, leaves the
  manifest alone, and says how to run it: `golem index`. The routine
  edit-a-few-files case — the point of auto-index — stays automatic.
- **Checkpoint every `INDEX_CHECKPOINT_FILES` (20) files.** Progress is persisted
  as it is earned, starting from the last completed run's states, so the manifest
  never claims a file whose chunks are not in the store. Deletions checkpoint
  first: they cost no embedding.
- **One canonical project id.** For Windows paths only (the one shape where the
  spellings mean the same location): uppercase the drive, fold `/` to `\`, drop
  trailing separators but never past the root. POSIX paths and bare ids are left
  alone — `\` is a legal filename character there.

## Out of scope

- The cap is **not** applied to the first-run or embedder-change full build. A
  project with no index has no search at all, and that build is announced.
- `golem index` passes no cap. It IS the explicit ask the session-start sync
  defers to, so it must never defer.
- Not a scheduler. No queue, no partial-priority ordering, no background
  resumption daemon — the deferred work simply waits for the next `golem index`.
- Migrating or merging the duplicate collections already on disk. The fix stops
  new ones being created; reclaiming the 231 MB is a `golem index` away.

## Gate

Standing verification bar (`npx tsc --noEmit`, `npm run lint`,
`npm run format:check`, `npm run verify:deps`, `npx vitest run`, `golem wiki
check`) plus the batch close-out in `CLAUDE.md`. Check EXIT CODES, not tailed
output.

Behavioural gate: with 8 changed files the sync still runs automatically; with
the cap exceeded the session start logs the deferral and embeds nothing; a sync
killed mid-run resumes at its last checkpoint rather than from zero.

## Outcome

shipped — `knowledge.auto_index_max_files` (default 50) bounds the automatic
session-start sync, which now checkpoints every 20 files, and
`canonicalProjectId` collapses every Windows spelling of a project path to one
collection. `golem index` is uncapped. The cost that motivated all three is
recorded in `docs/wiki/concepts/Auto-Index Cost.md`.
