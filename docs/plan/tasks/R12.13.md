## Why this is `owner: user`, not `owner: agent`

Not because it needs a credential an agent lacks — running a local, throwaway
test channel needed no organization feature enablement (this dev machine's
personal account connected one live, R12.11, verification-notes §141: "Pro/Max
individual, no org, skips the check entirely"). It's `owner: user` because the
test itself needs a **real interactive terminal**, and an agent in this repo has
no way to drive one: `grep -rl "node-pty\|pty.spawn" tests/ src/ package.json`
turns up nothing, and building that harness is a new capability this spike's
budget didn't extend to (R12.11) — plus `node-pty` is exactly the kind of native
dependency CLAUDE.md's hard rules ask to keep out, even scoped to `devDependencies`
only for one test. A human at a keyboard is the cheaper, correct way to run this
once, rather than building permanent infrastructure to avoid asking.

## What to do

1. Make sure `R12.12` has shipped (the `PermissionRequest`-level `deny` for
   `destructive`/`outward`).
2. Build or reuse a minimal channel (the throwaway one from R12.11,
   `.tmp-r12.11/channel-server.mjs`, was deleted before commit per the spike's
   own instructions — recreate it from `docs/plan/verification-notes.md` §141's
   description if useful, or write a fresh one against
   `code.claude.com/docs/en/channels-reference`'s webhook-receiver example).
   Declare `claude/channel` + `claude/channel/permission` under `experimental`
   capabilities, and log every `notifications/claude/channel/permission_request`
   it receives.
3. In a project directory with that channel wired into `.mcp.json`, start a
   **genuinely interactive** `claude` session (not `-p`) with
   `--dangerously-load-development-channels server:<name>` (or `--channels`,
   whichever applies to the org/account in use — see verification-notes §136/§141
   for the preview's opt-in and org-enablement constraints).
4. Trigger a `destructive` or `outward` Bash call (e.g. `rm -rf` against a
   throwaway directory, or `git push` against a disposable remote) and watch
   both: whether the channel's log shows a `permission_request` notification,
   and whether the local terminal shows a dialog at all.
5. Record the result — either way is useful:
   - **No dialog, no notification**: R12.12's fix works as the documentation
     implied. Update ADR-0006's R12.11 block to say the class line is confirmed
     safe against the relay, and update verification-notes with the observation
     (dated, client version noted).
   - **A dialog opens and/or the channel is notified anyway**: the fix as
     designed does not close the gap. This is safety-critical — do not treat it
     as a minor finding. Reopen the question of whether Golem needs its own
     transport after all (the from-scratch stack R12.11 recommended cancelling)
     and flag it loudly to the user before doing anything else.

## Out of scope

Building a permanent, repo-owned PTY test harness — this is a one-time manual
confirmation, not new infrastructure. Enabling the channels preview on any
shared/production org account. Anything that changes this machine's or any
shared account's persistent Claude Code auth or settings beyond the single test
session.

## Gate

A dated entry in `docs/plan/verification-notes.md` recording which of the two
outcomes above occurred, with the client version, and — if the fix failed — an
immediate, loud flag rather than a quiet note, since it bears directly on
whether ADR-0006's class-line guarantee holds in production.
