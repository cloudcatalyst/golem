## Goal

Introduce `proxy.targets` — **one registry for every model Golem can reach**,
local or upstream. This is the shared spine both R9.2 (proxy routing) and R9.3
(`coder` on any target) build on, and it is deliberately split out so those two
can then proceed in either order.

The pivot: **a local model becomes an ordinary target whose provider is
`ollama`.** "Optional local coder" stops being a special case.

## The one structural idea

Split two concerns that are currently fused in `proxy.accounts`:

| registry | answers | holds secrets? |
|---|---|---|
| `proxy.accounts` (exists, unchanged) | *whose credential* — id → provider + OS-keychain reference | reference only |
| `proxy.targets` (new) | *which endpoint + model* — id → provider, base_url, model, `account` ref, `trust` | **none** |

Several targets may reference one account (one Anthropic key backing both an
`opus` and a `haiku` target). Because targets hold no secrets, **the entire
ADR-0003 threat model carries over untouched** — this is the property that keeps
the task small, and it must not be traded away for convenience.

See the proposal for the TOML shape and the `trust` levels.

## Scope

- `proxy.targets` in `src/config/schema.ts`, zod-validated at the boundary.
- `src/providers/targets.ts` — resolution, **fail-closed** on an unknown id in
  the same spirit as `resolveActiveUpstream`: never silently substitute a
  different target.
- `trust` as an enumerated field (`vendor | local | lan | third-party`) whose
  only job in this task is to be *stored and surfaced*. It is consumed in R9.3.
- Generalize the spawn-time credential preflight from the single active account
  to every account referenced by a target. `perAccountEnvVar` already exists and
  was designed per-account (Decision 47) — **no new secret mechanism.**
- Startup warnings per misconfigured target, not just the active one: missing
  credential, translating provider with no `model`, and `doubledVersionSegment`
  (which already exists for exactly this).
- `golem target list | show | add | test` — `test` reuses the existing
  credential-probe path.
- Migration: `active_account` → `default_target` with a shim, so an existing
  config keeps working untouched.

## Real migration input (as of 2026-08-08)

This is not a greenfield registry — `proxy.accounts` in
`.golem/settings.local.json` already holds **six** entries, and they are exactly
the shape `proxy.targets` must express:

| id | provider | model |
|---|---|---|
| `moonshotai-kimi-k2.7-code` | openai | `moonshotai/kimi-k2.7-code` |
| `openrouter-gpt-oss` | openrouter | `openai/gpt-oss-20b:free` |
| `openrouter-laguna` | openrouter | `poolside/laguna-s-2.1:free` |
| `openrouter-qwen3` | openrouter | `qwen/qwen3-14b` |
| `openrouter-gemma4` | openrouter | `google/gemma-4-26b-a4b-it` |
| `openrouter-deepseek-v4` | openrouter | `qwen/qwen3-14b` → see live config |

`proxy.active_account` is currently **undefined** (the top-level Anthropic
config is in force). Note the shape these prove out: five of the six share one
OpenRouter credential but name different models — precisely the
many-targets-one-account case the split exists for, and the thing a
one-target-per-account design would have got wrong.

**Use these as the migration fixture.** The `active_account` → `default_target`
shim must leave this working config untouched, and `golem target list` should
show all six without the user editing anything.

## Out of scope

- **Any proxy behaviour change.** The proxy still serves one upstream after this
  task; the registry is inert configuration until R9.2 consumes it. This is what
  makes the task safe to land on its own.
- Changing `coder` (R9.3).
- Anything in `src/interfaces/` — nothing here touches a frozen contract.
- Route-on-exhaustion / failover. Out per the ADR-0003 line and the user's
  2026-08-08 scope decision; **do not add a fallback field to a target.**

## Watch for

- **Do not put a secret in a target.** The whole design rests on targets being
  non-secret. A `key`/`api_key` field on a target would silently reintroduce
  plaintext-secrets-as-settings, which ADR-0003 invariant 1 forbids outright.
- The daemon's environment now carries N credentials instead of 1. That is
  accepted (the CLI still owns resolution and injects at spawn), but the wider
  blast radius should be noted in the ADR amendment, not discovered later.
