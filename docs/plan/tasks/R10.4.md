## The defect

Every retrieval-shaped request through the proxy logs:

```
golem: local-answer stage failed, falling through to upstream
(query embedding is 768-dim but the index was built with 1024-dim vectors —
 the index was built with a different embedder. Rebuild it with `golem index`)
```

It fails open, so nothing breaks — but the local-answer feature (Decision 33) is
silently dead weight, doing an embed call and throwing it away on every query,
while `golem status` reports knowledge as enabled.

## Mechanism (traced)

The embedder is chosen by detected hardware tier
(`embedModelFor(tier, "text")`, src/inference/catalog.ts):

| tier | text embedder | width |
|---|---|---|
| 1 (CPU) | `nomic-embed-text` | 768 |
| 2, 3, 4 | `bge-m3` | 1024 |

So the model — and therefore the **vector width** — is a function of a
*runtime probe*, not of what the index was built with. The index here was built
at a higher tier (bge-m3, 1024-dim); the proxy later started at tier 1 and
queried with nomic-embed-text (768-dim).

`detectCapability` is documented as never throwing and **degrading to the CPU
tier** on any probe failure. That is right for chat, and wrong here: a transient
probe hiccup, Ollama being briefly down, or a machine under load can silently
change which embedder is used against an index that cannot accept it.

**The existing guard checks the wrong property.** src/cli/commands/proxy.ts
(~L179-192) suppresses local-answer when the current tier's embed model is not
available:

```ts
const model = embedModelFor(facts.tier, "text");
if (await ollamaHasModel(settings.inference.ollama_base_url, model)) { … }
```

That asks "can I run *an* embedder?" It never asks "is this the *same* embedder
the index was built with?" — so when the tier drops, the tier-1 model IS
available, the guard passes, and every query then fails on width.

## What to build

Make the index's embedder a recorded fact and compare against it:

- Persist the embedder identity (model name, and ideally vector width) with the
  index when it is built, and read it back at query time.
- Compare identity, not availability. On mismatch, either query with the
  embedder the index was built with (if available), or disable local-answer once
  at startup with a message naming BOTH models — not an error per query.
- Consider whether a tier downgrade should be allowed to change the embedder at
  all for an existing index. Pinning the embedder to the index is the property
  that actually matters; the tier is an implementation detail of choosing one.

The existing `resolvePersistedEmbedMode` (src/cli/auto-index.ts) already persists
semantic-vs-lexical, so there is a precedent and probably a home for this.

## Verification

Reproducible without special hardware: build an index at one tier, force the
other embedder, and confirm the proxy either queries correctly or disables
local-answer with a clear message — and that `.golem/proxy.log` shows no
per-query failure either way.

## Out of scope

- Changing the tier catalog's model choices, or adding an embedder.
- The 768/1024 widths themselves — the bug is that the pair can drift apart,
  not which numbers they are.
- The `knowledge.vector_db_url` Qdrant driver (still `NotImplementedYetError`).

## Outcome

shipped: query embedder pinned to the index's recorded one, not the detected tier. manifest.embedder + readCollectionDim + planQueryEmbedder; back-compat resolves pre-R10.4 indexes from signature/meta.json without assuming. All three branches proven against a real proxy, including a counterfactual reproducing the original error.
