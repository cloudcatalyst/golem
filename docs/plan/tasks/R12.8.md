## The job

Make a paired device reach its laptop from anywhere, **without the relay being
able to read, forge, or enrol anything**. ADR-0006 §3b is the contract; this task
is its implementation, and the properties are the deliverable rather than the
feature.

Three pieces:

1. **The protocol**, documented well enough to reimplement: how a laptop offers a
   session, how a device finds it, what the opaque session id is, and what the
   relay is allowed to see. Documented because §3b's "the endpoint is
   configurable and self-hosting is a real path" is only true if someone else can
   write a server against it.
2. **Both client halves** — the laptop offering, the device connecting — with the
   relay endpoint a setting and `none` a valid value.
3. **A reference relay server that is genuinely self-hostable**, in this repo, run
   by the tests. Not a sketch: the thing R12.9 deploys, and the thing that keeps
   Alternative 4 in the ADR "adopted" rather than "rejected".

## The properties that are the actual gate

- **The relay terminates no TLS and holds no key.** The mTLS session from R12.4
  runs end-to-end *through* it. Prove it the way this repo proves things: a test
  where the relay logs everything it sees, and the assertion is that no plaintext
  request, tool argument, or decision appears in that log.
- **The relay cannot approve.** No code path on the server produces a decision;
  it has no certificate from any user's CA.
- **The relay cannot enrol.** Pairing over the relay must be structurally absent,
  not merely disallowed — there should be no message type for it. This is what
  keeps account takeover at "DoS and metadata" (§3c-1), so it needs its own test:
  a client that *tries* to pair through the relay gets a protocol error, and the
  laptop never presents a pairing prompt.
- **Relayed mode is a separate opt-in from LAN exposure**, off by default, and
  `golem status` says which transports are live.
- **A relay outage is silence, and silence denies** (§5). No queueing a decision
  for later delivery, no falling back to direct exposure. Test the outage.

## What the relay unavoidably learns

Write it down in the wiki page, not just the code: account, timing, device count,
traffic volume. §3b concedes this and a "blind relay" claim that omits it would be
dishonest. If the implementation can reduce any of it cheaply (padding, constant
heartbeat), say what it cost and whether it was worth it.

## Out of scope

Operating a public relay, the account system, 2FA, billing, ToS, abuse handling —
all R12.9, and all `owner: user`. Push (R12.6). NAT-traversal cleverness: a relay
exists precisely so there is no STUN/TURN/hole-punching problem to solve.

## Gate

A phone on a mobile network reaches a laptop behind NAT, approves a `write`, and
the relay's own full log contains no plaintext. A pairing attempt through the
relay is impossible rather than refused. Relay set to `none` leaves LAN behaviour
identical, and no paired device at all leaves the hook path unchanged (R12.3's
property, re-asserted here).
