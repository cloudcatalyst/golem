## Why this exists

A write surface needs authentication in a way a read surface does not. ADR-0006
shipped the observe tier with no pairing at all and that stays true — an unpaired
browser on the LAN is still a dashboard. Pairing is what a **send** button
requires.

Two things make this bigger than the draft ADR proposed, both by user decision
(ADR-0007 Revision 1):

- **mTLS is revived.** Golem is already a CA, so mutual TLS costs no dependency,
  and §7c gives the second reason: the device certificate issued here is what a
  future internet relay carries end to end. Building something smaller now would
  mean building this later anyway.
- **A user factor is added.** A certificate proves a *device*; devices are lost,
  borrowed and stolen. The person is a separate claim and this task establishes it.

## What to build

1. **Local-only enrolment.** A code or QR shown by a command on the developer's
   own machine, short-lived, single-use. There is no remote enrolment path and no
   message type for one — invariant 8, inherited verbatim from ADR-0006 §3c-1 and
   worth restating in the code comment, because it is the property that makes a
   stolen phone and (later) a compromised relay survivable.
2. **Client certificates from the existing CA.** Issue, store, verify on every
   write endpoint. Label each device; record last-seen. `golem device list` /
   `golem device revoke <id>`, with revocation effective on the next request
   rather than at some cache expiry.
3. **The user factor — measured first, then chosen.** A passkey/WebAuthn
   credential is the goal; a passcode is the universal fallback. **Before
   promising the passkey path, establish what a browser will actually do on a LAN
   origin served with a private CA's certificate** — secure-context and
   `publicKey` availability rules are the risk, and they must be measured on a
   real device and recorded in a dated verification-notes section. If passkeys
   are unavailable in that context, the passcode is the mechanism and the note
   says so.
4. **Bounded unlock.** The factor unlocks sending for a bounded window,
   re-prompts after idle, and is re-required for gate-map item 5's high-risk acts
   (originating a session). The window length is configurable with an honest
   default.
5. **Failure is denial.** No certificate, no factor, expired either — refused,
   with a message saying which. Never a degraded "read-only but pretend it sent".
6. **Status legibility.** `golem status` says where the write surface is
   reachable from and how many devices are paired. If the developer has put it on
   a VPN, Golem neither prevents that nor pretends it has not happened
   (invariant 9).

## Out of scope

The relay, the account and internet reach — phase 2, R13.10. Multi-user or team
access: every device here belongs to the same developer (ADR-0007 §10). Push
notification (R12.6). The gate-map controls themselves (R13.9) — this task
provides the identity those controls key off, not the policy.

## Gate detail

Tests: pairing succeeds once and the code cannot be reused; a write request with
no client certificate is refused while read endpoints still serve; a valid
certificate with no user factor is refused; a revoked device is refused on the
next request; nothing accepts a pairing attempt that did not originate locally.
Plus the real-device run in the gate line, and the dated verification note on
what the user factor can be on this platform — that note is part of the gate,
because the alternative is a promise made from an API's shape rather than from a
measurement. Wiki page: how to pair, how to revoke, what a paired device may do.
