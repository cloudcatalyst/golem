## Why this exists, and why it is not R12.4

R12.4 (mTLS device pairing over the LAN) was **cancelled** by R12.11, together
with the relay and hosted account it existed to serve. This task is not its
revival and must not quietly become it: ADR-0007 §7 re-decides a strictly
smaller mechanism for a strictly smaller purpose — authenticating a *write*
surface on the local network, with no relay, no account, and no internet reach
(invariant 9).

The observe tier does not need this. ADR-0006 shipped a read-only dashboard with
no pairing at all, and that stays true: an unpaired browser on the LAN is still a
dashboard. Pairing is what a **send** button requires.

## What to build

1. **Pairing initiated locally, always.** A code (or QR) displayed by a command
   on the developer's machine, short-lived, single-use. There is no remote
   enrolment path and no message type for one — ADR-0006 §3c-1, inherited
   verbatim and worth restating in the code comment, because it is the property
   that makes a stolen phone survivable.
2. **Credentials minted from the existing CA.** `loopback-cert.ts` is already
   the authority; use it rather than adding a crypto dependency. Store the
   device's own secret material through `src/credentials/` on the device side of
   what Golem controls, and store only what is needed to verify on the host side.
3. **Enumerate and revoke.** `golem device list` / `golem device revoke <id>`,
   with last-seen so a stale device is visible. Revocation takes effect for the
   next request, not at some cache expiry.
4. **Refuse by default.** Every write endpoint (R13.5's message POST, R13.8's
   start/branch) requires a valid device credential. Unauthenticated means
   refused, not degraded — and a refusal says what to do about it.
5. **LAN-only, verifiably.** Bind and check accordingly, and make it plain in
   `golem status` where the surface is reachable from. If the developer puts it
   on Tailscale or WireGuard that is their network decision (invariant 9); Golem
   neither prevents it nor pretends it is not happening.

## Out of scope

Any relay, rendezvous or hosted account (R12.8/R12.9, cancelled — do not
resurrect). Internet reach. Multi-user or team access: every device here belongs
to the same developer, and anything that implies otherwise is a different ADR.
Push notification (R12.6). mTLS as such, if a simpler credential meets the gate
— the ADR asks for the smallest thing that authenticates a write, not for the
most sophisticated.

## Gate detail

Tests for: pairing succeeds once and the code cannot be reused; an unpaired
request is refused on every write endpoint while the read endpoints still serve;
a revoked device is refused immediately; nothing accepts a pairing attempt that
did not originate locally. Plus a real device on the real LAN completing the flow
once, recorded in the verification note. A wiki page for how to pair, how to
revoke, and what a paired device may and may not do — the capability table from
ADR-0007 §4, restated for a human.
