## The complaint

`npm test` on every batch of tasks takes many minutes and maxes all 16 logical
cores, so the machine is unusable while it runs.

## The measurement

Vitest parallelises across **files**, never within one. No file here uses
`.concurrent`. So the suite can never finish faster than its single slowest
file, and at the tail one worker grinds alone while fifteen sit idle.

| file | tests | per-file time |
|---|---|---|
| `tests/integration/checkpoint-ledger.test.ts` | 12 | ~125s |
| `tests/integration/cli-init.test.ts` | 44 | ~98s |
| `tests/integration/cli-status.test.ts` | 39 | heavy |
| `tests/integration/mcp-server.test.ts` | 57 | heavy |

**This is why every pool experiment in R10.1 came back worse.** Worker counts
cannot subdivide a single file. The floor is a *partitioning* problem, and it
was never attacked.

## Already settled — do NOT re-derive

- **Pool/worker tuning is a dead end.** R10.1, 2026-08-12: threads+cap → 141s;
  two-project split → 195s + 6 failures + include-routing breakage; simple
  threads → 209s; baseline ~125–133s. `vitest.config.ts` stays at baseline.
- **Do not thin the integration tests.** They carry documented regressions
  (R8.32, R9.4, R9.22) and are the highest-value coverage in the suite.
- **Do not raise `testTimeout` globally** (R10.2). The two init-heaviest files
  already carry a justified local 90s ceiling.
- **Do not regress the CI sharding** (PR #97).

## The work

### 1. Stop running the full suite on every batch

The close-out checklist mandates a full `vitest run` per batch; most batches
touch a handful of modules. Add to `package.json`:

- `test:changed` — `vitest run --changed HEAD` (the inner loop)
- `test:unit` — `vitest run tests/unit` (no daemons, no git spawns)
- `test:full` — the existing full run, unchanged

The full suite still runs, once, at close-out — which is where the gate
actually lives. This removes the per-batch cost without removing any coverage.

### 2. Split the wall-time floor files

Pure re-partition along existing `describe` seams: same tests, same assertions,
more files for vitest to spread across the 16 workers. Shared fixtures move to
`tests/integration/helpers/`.

**Safe to split now** (untouched by the in-flight R13.16 branch):

- `checkpoint-ledger.test.ts` — 12 tests, one describe, each doing a real
  `git init` + commit
- `mcp-server.test.ts` — 57 tests across 13 describes

**Deferred — see the conflict note below:**

- `cli-init.test.ts`, `cli-status.test.ts`

## Out of scope

- **Windows Defender exclusions.** Real-time protection is on, and this suite
  spawns real git/proxy daemons and writes ~20 files per `golemInit` across
  hundreds of temp trees under `%TEMP%`. `vitest.config.ts` already blames a
  virus scanner for the 5s→20s timeout bump, but nobody has measured it.
  Requires admin, so `owner: user` — captured separately, not done here.
- **Capping `maxWorkers` to keep the machine usable.** Measured at ~6% wall cost
  (141s vs 133s). Defensible as an opt-in env flag if "maxes the CPU" turns out
  to mean "unusable while running" rather than "slow"; not a default, and not
  this task.
- Any `vitest.config.ts` pool/worker change (see above).
