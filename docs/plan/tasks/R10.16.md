## The defect

Found 2026-08-14 alongside R10.14, while explaining why sessions on a translating
upstream "seem to stall" rather than fail.

Two gaps compound:

**1. `message_start` is lazy.** `#ensureStarted()` only runs when the first
content arrives, or at `_flush`:

```ts
#ensureStarted(): void {
  if (this.#started) return;
  ...
}
```

Anthropic's own API emits `message_start` immediately on accepting the request.
Golem's translated stream emits nothing until the upstream produces its first
token — so a client has an open socket carrying zero bytes for the whole prefill.

**2. Nothing ever emits `ping`.** `grep -rn "ping" src/proxy src/providers`
finds no emitter. Anthropic's streams ping throughout; the OpenAI chat-completions
schema has no ping, and the translator does not synthesise one.

Measured on a real 468k-token request against
`openrouter:deepseek/deepseek-v4-flash-0731`: **124–152 s** per attempt with no
bytes to the client until the end. Repeated three times, consistently.

The second gap has teeth beyond appearances. `bodyTimeoutMs` is the max idle time
between upstream body chunks, and its own comment explains the budget by assuming
a cadence the OpenAI path never has:

```ts
/**
 * Max idle time between upstream body chunks, ms. Default 300_000.
 * (Anthropic SSE streams emit `ping` events well within this.)
 */
```

On a translating upstream there are no pings to rely on, so a long enough prefill
trips an idle timeout that was sized against a different protocol's behaviour.

## What to build

- Emit `message_start` as soon as the response is known to be a stream, using the
  configured target id/model as the fallback — which is what the translator
  already carries for exactly this purpose. Keep the later upstream-reported
  `id`/`model` for the rest of the stream.
- Synthesise periodic `ping` events while the upstream is silent, stopping at the
  first real content and on end. This is a timer inside the Transform, so it must
  not `push` after end and must not keep the event loop alive (`unref`).
- Revisit the `bodyTimeoutMs` comment so it states the real basis for the number
  on each path, rather than an Anthropic-only assumption.

## Watch for

- **Honesty of the eagerly-reported model.** `message_start` currently reports
  whatever the upstream said; emitting early means reporting the configured target
  before the upstream confirms it. That is the routed target, so it is true — but
  if the upstream later reports a different id, the stream has already claimed
  one. Decide and document which wins (cf. Decision 25, the "real serving model"
  rail, and `src/proxy/served-model.ts`).
- Ping cadence must stay well inside `bodyTimeoutMs` on both sides — the client's
  idle timeout and the proxy's.
- **This is not the empty-response bug.** R10.14 is why answers came back blank;
  this task is why a working request looks dead while it is in flight. Fixing this
  one alone would have made that failure *more* confusing, not less: a stream that
  pings for two minutes and then returns nothing.
- Recorded-shape tests cover the streaming path — a new leading event changes
  those fixtures, and the pipeline hard rule means the change has to be
  deliberate and asserted, not absorbed.

## Out of scope

- The non-streaming path, which has nothing to keep alive.
- Gemini's SSE translator, which needs the same treatment on its own task.
