## Goal

Golem has **no config migration machinery at all**. The only thing resembling one
is `migrateSliderLevel` — a read-time zod transform clamping legacy 4/5 onto 3 —
which is a value coercion, not a key migration.

## Why this is a real risk rather than a tidiness itch

Verified live (2026-08-09), a settings file naming a key that no longer exists:

```
Warnings:
  - …/.golem/settings.json: unknown setting "inference.coder_target" ignored
  - …/.golem/settings.json: unknown setting "inference.bogus_key" ignored
  - …/.golem/settings.json: unknown settings section "nosuchsection" ignored
```

Exit 0. **That is the good news and the bad news.** Good: a rename cannot break
config loading, so nobody is locked out by an upgrade. Bad: the setting *silently
stops taking effect*, the warning appears only in `golem status` (which nobody
runs after an upgrade that appears to work), and the user's deliberate choice is
now inert while every surface reports success.

That is precisely the failure class this project keeps rediscovering — R8.32's
running-but-unwired proxy, R9.4's status line naming a model that could never
run. A silent no-op is worse than an error.

## The worked example already in the tree

R9.1 renamed `proxy.active_account` → `proxy.default_target` and handled it with
a **bespoke read-time fallback** inside `resolveDefaultTargetId`: read the new
key, fall back to the old one. It works, it is well-commented, and it is
completely unreusable — the next rename will hand-roll the same idea somewhere
else, or forget to.

R9.4 then removed `inference.coder_target` outright, which was only safe because
it had never been released.

## Scope

- One declarative place to say "`a.b` was renamed to `c.d`" (and ideally "`x` was
  removed in version N"), consulted by the loader.
- A renamed key keeps working from an existing file, with its provenance
  reported honestly — `golem status` should not claim the value came from the new
  key when the file says the old one.
- The warning must reach the user **when it matters**, not only in `golem status`.
  Decide where: a one-time notice, a `golem update` step, or the init report.
- Migrate the R9.1 `active_account` fallback onto the new mechanism, so there is
  exactly one implementation and the example is the test.
- `golem config set` on a renamed key should do the sensible thing rather than
  writing a key the loader will then warn about.

## Out of scope

- Rewriting the user's settings file in place. Golem does not silently edit
  user-authored config, and a migration that mutates the file on read would be a
  worse precedent than the problem. Reading the old key is enough; *offering* a
  rewrite behind an explicit command is acceptable, doing it automatically is not.
- Versioning the settings file format (a `version:` field). Possible later; not
  needed for key renames and it adds a migration path of its own.
- Managed-file refresh for skills and guidance — R9.5, different mechanism.
- `migrateSliderLevel`, which is a value coercion and already works.

## Watch for

- **Precedence.** The layered config (`default < user < project < local < env`)
  means an old key in one layer and a new key in another can both be present. The
  new key must win at the same layer; across layers, normal precedence applies —
  and whichever wins, provenance must name the file and key the value actually
  came from.
- The env mapping splits `GOLEM_<SECTION>_<KEY>` on the first underscore after the
  prefix (CLAUDE.md), so a rename that changes a section name is a different and
  harder case than one that changes a leaf. Decide whether section renames are in
  scope or explicitly refused.
- Unknown-key warnings are currently emitted per settings file; a migration must
  not double-report (once as "unknown", once as "migrated").

## Outcome

shipped — declarative migration table, active_account retired onto it, warnings at proxy startup
