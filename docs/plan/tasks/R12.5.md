## Start from web, and say why

The dashboard is already a self-rendered, dependency-free HTML page served from
`127.0.0.1`. Made responsive and installable to a home screen, that is a companion
app on every phone platform with no store, no signing, no second toolchain, and no
new dependency — which is the same discipline that kept ink and React out
(Decision 51) and keeps the runtime at five deps.

**A native shell earns its place only if it buys something the web cannot**, and
there is exactly one candidate: a notification that arrives when the app is
closed. That is R12.6's question, deliberately separated so this task is not held
hostage to it. Do not build a native app in this task; if R12.6 concludes a native
shell is required, that is its own task with its own ADR paragraph.

## What the screen has to get right

- **The block, legibly.** Project, what is being asked, the exact argument, how
  long it has been waiting — from R12.2's read model. A phone screen that says
  "waiting on your input" is a notification, not a control.
- **Approve / Deny, and nothing that looks like them.** No swipe-to-approve, no
  action reachable from a lock screen preview, no default-focused button.
- **A visible deadline.** The human must see the hook's window closing (R12.3), so
  a timeout is understood rather than experienced as a failure.
- **Connection state, never optimism.** A dropped link shows "not connected" —
  never a stale "approved", never a queued decision that might land later. Default
  deny on link loss is the ADR's rule and it has to be legible on the screen.
- **Read-only until paired**, so an unpaired browser can still be a dashboard.

## Out of scope

A native app or an app store. Push (R12.6). "Continue" or any prompt entry
(R12.7). The relay and the account (R12.8 / R12.9). Reworking the desktop
dashboard's own layout beyond making it responsive.

**The UI must not know which transport it is on.** ADR-0006 §3b makes relayed mode
carry the same end-to-end mTLS session as the LAN, so the client sees one kind of
connection. Build against the LAN, and the relay works for free later — if it
does not, that is a bug in R12.8, not a case to special-case here. The one thing
worth surfacing is the *fact* of relaying, so a user can tell when their traffic
is transiting someone else's server.

## What R12.7 settled, so you do not re-derive it (2026-08-22)

**Ship no prompt box, no "continue", no send field.** Not because nothing could
reach the session — that changed, and R12.7 found it — but for five reasons that
each survive contact with the current client. Full evidence:
`docs/plan/verification-notes.md` §136.

The short version: Claude Code `2.1.235` does have a supported reverse channel now
(**channels** — an MCP server emitting `notifications/claude/channel`; plus Remote
Control and cross-session `SendMessage`). Golem still does not use it, because it
is opt-in per session by launch flag, off the Anthropic-curated allowlist, gives
**no delivery acknowledgement** (a button that cannot know whether its message
landed can only lie), rides an explicitly unstable contract, and — decisively —
*authoring a turn is a larger authority than answering one*, which is a new USER
decision (**R12.10**), not a UI affordance this task may add.

**Put this sentence where the button is not** (same register as R12.6's
"Alerts are off — this screen only updates while it is open."):

> **There is no prompt box — this screen can answer what the agent is already
> asking, but nothing here can start a turn.**

Keep it scoped to *this screen*. "No phone can steer a session" would be false
now, so do not write it.

**If someone later asks for the enqueue affordance** (R5.1's durable queue is real
and could back it), it is R12.10's call, not yours — and it arrives under three
rules: labelled **"Add a task for later"** with the sub-line **"Nothing runs until
your laptop picks it up."**, never grouped with Approve/Deny, and with no spinner
or progress state, because the only thing that happened is that a file was
written.

## Gate

From a phone on the LAN, over mTLS: the current block is legible, approve and deny
both work end-to-end through R12.3's gate, the deadline is visible, and pulling the
network shows a disconnected state with no decision in flight. Installable to a
home screen on at least one platform, verified on a real device.
