## Goal

Reported live, 2026-08-09: the VS Code status bar showed the coder drafting on
`qwen2.5-coder:7b` while the CLI correctly showed `claude-sonnet-5`.

The config was right and the CLI was right. The **deployed** extension's
`render.js` was three releases behind: it read the worker list only from
`st.local_model.workers`, while the CLI emits `workers` at top level. Finding
none, it fell back to the implicit coder row and filled it with
`localCoderModel` — a surface confidently naming a model that was not being
used, which is the R8.32/R9.4 failure class this project keeps closing.

The repo copy had been correct the whole time. It had simply never been
deployed, because:

```ts
if (await pathExists(target)) {
  return { kind: "skip", path: …, detail: "already installed" };
}
```

`installVscodeExtension` keys on the **directory existing**, and the directory
is named for the extension version. Ship a fix without bumping that version and
every subsequent `golem init` is a silent no-op. This is exactly R9.5's
seed-once bug — *an improved file never reaches an existing install* — one level
up, in the one place R9.5 did not look.

## What the work is

- **`src/cli/vscode-extension.ts`** — one place that knows where the extension
  ships from, where it deploys to, and which files constitute it. `init.ts`
  currently owns all three; `status.ts` needs two of them, and duplicating the
  file list is how the two copies would drift.
- **`inspectVscodeExtension()`** → `current` | `stale` | `absent` | `unknown`,
  plus the names of the files that differ. Hash comparison per file, not mtime:
  a redeploy that copies identical bytes must not read as a change.
- **`golem init` refreshes a stale deployment** rather than skipping it, and
  reports `modify` with the files it replaced. An identical copy is still a
  skip, so the common case stays quiet.
- **`golem status` names a stale deployment** before anyone has to notice a
  wrong model on their status bar. It does not fix it — status is read-only
  (R9.13 drew that line) — it names the fix.

## Why no ownership check, unlike R9.5

R9.5 refuses to overwrite a managed file that differs from what Golem last
wrote, because `.claude/rules/*.md` and `SKILL.md` are documents a user may
legitimately edit. The deployed extension is not a document: it is a build
artifact in VS Code's own extensions directory, and nobody hand-edits
`render.js` there. So "differs from what we ship" means "stale", and refreshing
it loses nothing. Recording that reasoning matters more than the code — the next
reader will otherwise wonder why the two managed-file mechanisms disagree.

## The test that should have caught it

`vscode-extension/render.test.js` passed throughout, because it tests the
**repo** copy. A test that only ever sees the source cannot detect a stale
deployment — the gap is not coverage, it is *which artifact* is under test. The
new tests therefore assert on a fake extensions directory: shipped-vs-deployed
drift, not renderer behaviour.

## Out of scope

- Removing orphaned version directories (`golem-vscode-0.1.1`, `0.5.0`, `0.7.0`
  are on this machine). `uninit` already matches `golem-vscode-*`; deleting
  another version's install during `init` is a different decision, and VS Code
  loads the highest version anyway.
- Detecting whether the extension **host** has reloaded. It cannot be observed
  from outside, so both surfaces say "reload the window" rather than implying
  the refresh took effect immediately.
- Bumping the extension version to force redeployment. That would fix this
  instance and leave the mechanism broken for the next one.
- Any change to `vscode-extension/deploy-local.mjs`, which already copies
  unconditionally and was how the live fix was applied.
