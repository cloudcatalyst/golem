## The defect

Every proxy start spawns up to two Headroom sidecars (`HeadroomSidecar` for
semantic compression, `HeadroomMemorySidecar` for MEMORY-scope search), launched
as `uv run` python children. **They are not reaped when the proxy stops.**

Measured on the dev machine, 2026-08-13:

```
24 python.exe processes, in 12 launcher+worker pairs
oldest pair:  pids 45388 / 48204, started 8 Aug 19:29 — FIVE DAYS earlier
CPU burned:   127.3s (pid 50360), 92.0s (38916), 55.8s (45388)
RSS:          82 MB each for the newest pair
```

All are `"…\uv\cache\builds-v0\…\python.exe"` with a cwd inside
this project's own checkout, so they are this project's. Only three node
proxies were alive at the time (started 10, 12 and 13 Aug) — and those are three
*different* projects, which is the per-project-proxy model working correctly. So
the sidecars from 8 and 9 Aug had outlived their parent daemons by days.

They surfaced as background CPU load that slowed a full test run from ~125s to
214s, which is how they were noticed at all.

## Mechanism (traced, not guessed)

1. `runProxyForeground` installs a `shutdown` handler on SIGINT/SIGTERM which
   calls `semantic?.stop()` (src/cli/commands/proxy.ts).
2. `stopProxy` kills the daemon with `process.kill(info.pid)`
   (src/cli/proxy-daemon.ts).
3. **On Windows, `process.kill` maps to `TerminateProcess`** — abrupt, and Node's
   emulated SIGTERM handler in the target is NOT invoked by an external kill. So
   `shutdown` never runs, `stop()` is never called, and the python child is
   orphaned.

Two further gaps visible in the same code, worth fixing while there:

- `shutdown` stops only `semantic`. The **memory sidecar is never stopped at
  all**, so it leaks even on a clean POSIX shutdown.
- The child is spawned without `detached`, but nothing kills the process group
  either, so a hard parent death orphans it on any platform.

## What to build

Make orphaning structurally impossible rather than relying on a shutdown path
that may not run:

- Track every spawned sidecar so ONE teardown reaps all of them (both classes),
  not just the semantic one.
- Do not depend on a signal handler for correctness on Windows. Options to weigh:
  have the daemon record its sidecar pids alongside `proxy.pid` so `stopProxy`
  can reap them directly; or use a job object / process-group kill; or have the
  worker exit on stdin EOF, which it gets for free when the parent dies.
- Reap pre-existing orphans on start, so a machine that already has 24 of them
  recovers without manual cleanup.

## Verification

The leak is Windows-reproducible and cheap to measure: count `python.exe`
processes, `golem proxy restart`, count again. The number must not grow. A
`golem proxy stop` must return the count to its pre-start value.

## Out of scope

- Disabling the sidecars, or changing when they spawn. They are opt-in already
  (`compression.headroom_sidecar`, slider ≥3) and this is a lifecycle bug, not a
  feature question.
- The Headroom pin or the adapter's isolation rule (`tests/contract/headroom-isolation.contract.test.ts` guards that).

## Cleanup for the current machine

The 24 existing orphans predate any fix and will not be reaped by it unless the
start-time sweep above is built. They can be killed by hand; nothing depends on
them.

## Outcome

shipped: worker exits on stdin EOF (structural — nothing in the dying parent has to run), LIVE_WORKERS registry reaps every sidecar class, taskkill /T on Windows, POSIX group kill, plus start-time reaping of pre-existing orphans. Measured 6 -> 0 of this project's workers, no growth across restarts.
