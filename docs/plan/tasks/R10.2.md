## The defect

On a clean tree with nothing else running, `npx vitest run` fails 0–3 tests per
invocation. Every failure is `Error: Test timed out in 20000ms.` — **never an
assertion failure.** The same tests pass in 0.4–2s when run in isolation.

Measured 2026-08-12, four consecutive full runs of the same commit:

| run | machine state | result |
|---|---|---|
| 1 | 5 subagents also running | 5 failed / 2536 passed — all timeouts |
| 2 | idle | **0 failed** / 2541 passed |
| 3 | idle | 3 failed / 2548 passed — all timeouts |
| 4 | idle | **0 failed** / 2551 passed |

The three that failed in run 3, and the times they take alone:

- `tests/e2e/golem-init-smoke.test.ts` — "pins slider level 1 and is idempotent"
- `tests/integration/cli-init.test.ts` — "never clobbers a NODE_EXTRA_CA_CERTS that someone else owns (§121-C)"
- `tests/integration/cli-slider.test.ts` — "does not re-run activation on an already-initialized project"

Run together in isolation: **42 tests, 23s, all green.** One of them
(`cli-slider` "activates a not-yet-initialized project") was measured at **409ms
alone** in a run where it had timed out at 20 000ms — a 50× blowout.

## Why it matters

- A developer running `npm test` locally sees red on an unmodified tree, which
  trains people to re-run and ignore failures — the exact habit that hides a
  real regression.
- It is invisible in CI: the 10× sharding from #97 means each shard carries a
  fraction of the spawn load, so the contention never builds. The gate that
  should catch this is the one place it cannot happen.

## What to investigate

The failing tests all spawn real subprocesses (git, proxy daemons, the CLI).
The hypothesis to test first is **process-spawn starvation**: when vitest's
worker pool saturates the CPU, `spawn()` latency for a *new* OS process balloons,
so a test whose work is 0.4s of compute but which waits on three spawns blows a
20s budget. If that is right, the fix is to reduce the number of real spawns —
not to wait longer for them.

The brief for R10.1 already lists the consolidation that would do it:
**consolidate the ~26 proxy-spawning integration files around the shared
fixtures in `tests/integration/helpers/`**, so setup is paid once per file
instead of once per test. That is a testability win first and a contention fix
second.

## Out of scope

- **Any `vitest.config.ts` pool/worker tuning.** Measured and rejected during
  R10.1 (threads pool + cap → 141s; two-project serialisation → 195s + 6
  failures + include-routing breakage; simple threads → 209s; baseline 125-133s).
  Do not re-derive this.
- **Raising `testTimeout`.** The margin being blown is 10–50×, so a bigger
  number hides the cause rather than fixing it. If a timeout change turns out to
  be the right answer, it needs a recorded measurement saying why.
- **Deleting or thinning the integration tests.** They carry documented
  regressions (R8.32, R9.4, R9.22) and are the highest-value coverage in the
  suite.
