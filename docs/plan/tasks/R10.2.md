## The defect

On a clean tree with nothing else running, `npx vitest run` fails 0–3 tests per
invocation. The same tests pass in 0.4–2s when run in isolation.

Measured 2026-08-12/13, five consecutive full runs:

| run | machine state | result |
|---|---|---|
| 1 | 5 subagents also running | 5 failed / 2536 passed — all timeouts |
| 2 | idle | **0 failed** / 2541 passed |
| 3 | idle | 3 failed / 2548 passed — all timeouts |
| 4 | idle | **0 failed** / 2551 passed |
| 5 | idle | 3 failed / 2548 passed — 2 timeouts **+ 1 assertion** |

### Two failure modes, not one — do not rely on "timeouts are flake"

Most failures are `Error: Test timed out in 20000ms`, which is easy to
recognise. But run 5 produced an **`AssertionError: expected true to be false`**
from a flake, in
`tests/integration/headroom-adapter.test.ts` → "backs off on unexpected worker
death and does not respawn immediately (R8.30)". It passes in isolation in
1.4s.

The cause is a wall-clock margin, not a wrong expectation: the test waits 400ms
for a fake worker that dies at 300ms, then asserts `isRunning()` is false
(headroom-adapter.test.ts:132-133). Under load the child's exit event has not
been processed inside that 100ms margin, so the flag is still true.

**So error kind alone cannot classify a failure here.** Any timing-margin
assertion over a real subprocess can fail the same way. The reliable check is
still: re-run the failing file in isolation.

The three that failed in run 3, and the times they take alone:

- `tests/e2e/golem-init-smoke.test.ts` — "pins slider level 1 and is idempotent"
- `tests/integration/cli-init.test.ts` — "never clobbers a NODE_EXTRA_CA_CERTS that someone else owns (§121-C)"
- `tests/integration/cli-slider.test.ts` — "does not re-run activation on an already-initialized project"

Run together in isolation: **42 tests, 23s, all green.** One of them
(`cli-slider` "activates a not-yet-initialized project") was measured at **409ms
alone** in a run where it had timed out at 20 000ms — a 50× blowout.

## Why it matters

- A developer running `npm test` locally sees red on an unmodified tree, which
  trains people to re-run and ignore failures — the exact habit that hides a
  real regression.
- It is invisible in CI: the 10× sharding from #97 means each shard carries a
  fraction of the temp-tree churn, so the contention never builds. The gate that
  should catch this is the one place it cannot happen.

## Diagnosis — the first hypothesis was WRONG

This task originally guessed **process-spawn starvation**. That was wrong, and
the correction matters because it points at a different fix.

Checked and ruled out:
- **Not spawn count.** Only 7 test files spawn a subprocess at all. Two of the
  three usual failures (`cli-init`, `cli-slider`) spawn nothing.
- **Not key generation.** `ensureLoopbackCert` looked expensive but uses EC
  (`prime256v1`), not RSA — about a millisecond.

The actual cost is **temp-directory churn, and specifically the deletes.**
`tests/helpers/tmp.ts` already documented the mechanism without anyone
connecting it to the timeouts: on Windows a recursive delete of a just-written
tree races the indexer and the virus scanner, so `rmTemp` carries
`maxRetries: 5, retryDelay: 50`. A delete that loses the race **sleeps and
retries while holding the test open.**

**82 test files did `mkdtemp` in `beforeEach` and a recursive delete in
`afterEach`** — one create-and-delete cycle per TEST, thousands per run, every
one retry-prone. `tests/integration/cli-init.test.ts` alone makes 36
`golemInit()` calls, each writing ~20 files into its own temp tree, each tree
then recursively deleted.

Corroborating evidence that this was known but never linked to the timeouts:
the 20s `testTimeout` in `vitest.config.ts` carries a comment describing these
exact symptoms ("tests timing out intermittently, on a different one each run",
§86c), and `rmTemp`'s own comment describes the same load-dependent race causing
`afterEach` failures. The timeout was raised 5s -> 20s to paper over it. It came
back.

## The fix — three parts, in order of how much they mattered

**1. One temp-tree delete per FILE, not per test.** `tests/helpers/tmp.ts` gained
`useTempDirs(prefix)`: one temp root per file, a fresh `mkdtemp` subdirectory per
test, one recursive delete when the file finishes. Per-test isolation is
unchanged — every test still gets a directory nobody else can see. Only the
reclaim point moved. **67 files converted**, including all four chronic
offenders.

**2. Atomic settings writes — this fixed a real defect, not just a flake.** Under
load, `golem init` began failing with "settings.json is not valid JSON" against a
file it had written itself, seconds earlier, in a fresh temp dir.
`cli/json-file.ts` wrote with a plain `writeFile`, which leaves a window where
the file exists holding a *prefix* of the new content — and
`.claude/settings.json` is read back several times during a single init. It now
writes temp-file-then-rename, the same durability `config/file-io.ts` already
gave `.golem/settings*.json`. The same window would corrupt a user's real
settings if the process died mid-write. The corruption has not recurred in ten
runs.

That defect lived in a FOURTH copy of `readJsonObject`/`writeJsonObject`, in
`hooks/settings-extras.ts`, differing from the others only in an error message.
It now shares the one module.

**3. A local, measured ceiling on the two init-heaviest files.** What remained
after 1 and 2 was pure contention. The measurement the "out of scope" section
demanded: **`golemInit` costs 298ms on an idle machine** (10 calls in 2981ms,
2026-08-13). A test doing one or two of them, tripping a 20s budget, is a **66×
slowdown of work that is small and real** — not a hung test and not a slow code
path. The cause is environmental: ~15 vitest workers doing filesystem work on
Windows, where every file creation is a virus-scanner event.

`cli-init.test.ts` and `golem-init-smoke.test.ts` therefore set
`testTimeout: 90_000` locally, with that measurement recorded in the file. The
20s default still guards the other 202 files, which is what keeps this from
being the blanket increase the task ruled out — and it matches the precedent
`checkpoint-ledger.test.ts` already set.

## Outcome — gate met

Ten consecutive `npx vitest run` invocations on an unloaded machine, all green:

**2554 passed / 2 skipped / 204 files, zero failures, ten times running.**

Before: 3–4 failures per run, with the corruption appearing under load.

## Out of scope

- **Any `vitest.config.ts` pool/worker tuning.** Measured and rejected during
  R10.1 (threads pool + cap → 141s; two-project serialisation → 195s + 6
  failures + include-routing breakage; simple threads → 209s; baseline 125-133s).
  Do not re-derive this.
- **Raising `testTimeout`.** The margin being blown is 10–50×, so a bigger
  number hides the cause rather than fixing it. If a timeout change turns out to
  be the right answer, it needs a recorded measurement saying why.
- **Deleting or thinning the integration tests.** They carry documented
  regressions (R8.32, R9.4, R9.22) and are the highest-value coverage in the
  suite.

## Outcome

shipped: useTempDirs (one delete per file, 67 files), atomic .claude/settings.json writes (fixed a real corruption bug), measured local timeout on the two init-heaviest files. Ten consecutive full-suite runs green.
