## Goal

Golem writes two kinds of file into a user's project and treats them **inversely
wrong**:

| file | on re-init | consequence |
|---|---|---|
| `.claude/skills/golem/<cmd>/SKILL.md` | full-content compare → **overwrite** | a hand-edited skill is silently destroyed |
| `.claude/rules/golem-<name>.md` | **seed-once**, sentinel-gated | an improved rule never reaches an existing project |

Neither is a small bug. The first loses the user's work with no warning; the
second means every guidance fix Golem ships is invisible to everyone who already
ran `golem init`.

## How it stands today (verified 2026-08-09, not inferred)

- **Skills** — `init.ts` reads the installed `SKILL.md`, compares it to
  `P0_SKILLS[name]`, and rewrites on any difference. It reports `modify`, but
  only in the action list; nothing tells the user their edit was the thing being
  replaced. Observed live: `golem init` silently regenerated
  `.claude/skills/golem/ship/SKILL.md`, which had drifted.
- **Guidance** — `seedDefaultGuidance` returns early when
  `.golem/state/guidance.json` holds `{ "seeded": true }`. The rationale is
  sound and must be preserved: a user's `golem guidance disable` has to survive
  a re-init. But "don't undo the user's choice" and "never refresh the text" are
  currently the same mechanism, and only the first is intended.
- R8.33 got lucky: it changed the `slider` and `bypass` skills (which do
  refresh) and no guidance rule mentions level 0, so nothing was stranded. The
  next guidance change will not be so lucky.

## The one structural idea

Separate **"has the user taken ownership of this file?"** from **"is this file
stale?"** — they are different questions and each managed file currently answers
only one of them.

A workable shape (not prescriptive — the task is the outcome, not this design):
record the hash of what Golem last wrote. Then on re-init a file is
*unmodified-and-stale* (safe to refresh silently), *modified-and-stale* (the
only case needing the user), or *unmodified-and-current* (skip). The user's
`disable` decision stays where it is, in the presence/absence of the rule file
plus the sentinel.

## Scope

- Skills: never discard a user edit without saying so. At minimum report it
  distinctly from a routine refresh; better, leave it and tell the user how to
  take the update.
- Guidance: a mechanism by which improved rule text reaches an existing project,
  **without** resurrecting a rule the user disabled.
- `golem init --dry-run` must make the difference legible — "refreshing stale
  text" and "replacing your edit" cannot both render as `modify`.
- Whatever records provenance lives under `.golem/state/`, gitignored, like the
  existing guidance sentinel.

## Out of scope

- Changing which skills or guidance rules exist, or their content.
- Making guidance rules non-user-owned. Decision 2026-07-16 stands: presence of
  the file is the toggle and the user owns it.
- Config-file migrations — that is R9.6, a different mechanism for a different
  class of file.
- The VS Code extension's install path (versioned dir + `deploy:local`), which
  has its own separate staleness story.

## Watch for

- **The sentinel must keep doing its real job.** A refresh that re-creates a
  rule the user ran `golem guidance disable` on is a worse bug than the one being
  fixed — it overrides an explicit choice rather than an implicit one.
- `.claude/skills/` is git-tracked in this repo, so a clobber is recoverable
  *here* and silent-but-permanent in a user's project that does not commit it.
  Do not let this repo's own safety net set the standard.
- `golem uninit` removes what init added; anything new recorded here needs the
  matching removal, and the existing uninit test asserts exactly that.

## Outcome

shipped — hash-provenance mechanism; skills keep edits, guidance refreshes, disable still sticks
