## Why this exists

The user's words (ADR-0007 Revision 1): *"I don't want to put any limits on
remote authorship, maybe we can have some user controls applied once we define
where possible gates could be."* §3d is that definition. This task turns the
enumeration into switches the user can actually reach, which is the deal —
authorship is unrestricted, and the controls are theirs to choose, not Golem's to
impose silently.

Read §3d's table before writing any code; it carries the defaults and they are
not all "on".

## What to build

One coherent policy surface, not nine scattered flags:

1. **Session visibility** (item 1) — which sessions and projects a device may see
   and address. Default: all, for an authenticated device.
2. **Origination scope** (item 2) — which project roots a device may start a
   session in. Default: all known roots.
3. **Remote answer to `destructive`/`outward`** (item 3) — see the section below;
   default **off**.
4. **Approval routing when nobody is local** (item 4) — for `read`/`write`/
   `unknown` always; for `destructive`/`outward` only when item 3 is on. Default:
   route to the device.
5. **Re-authentication for high-risk acts** (item 5) — on for origination, on for
   every item-3 answer, off for ordinary messages. Keys off R13.4's user factor.
6. **Rate and size limits per device** (item 6) — on, generous, and the refusal
   states the limit rather than dropping quietly.
7. **Kill switch** (item 7) — one command and one tap that suspends all remote
   authorship immediately, always available, loud in `golem status`, and
   overriding item 3 instantly. This is the control that matters in an incident:
   build it first and test it hardest.
8. **Quiet hours / presence** (item 8) — offered, default off.
9. **Per-session pause** (item 9) — suspend remote authorship for one
   conversation without unpairing.

## Item 3 — the one that carries real authority

Decision 61 amended 59(a) at the user's explicit request, so this ships as a
setting. Five properties are the safety margin, and none is negotiable (61(c)):

- **Off by default**, and it cannot be enabled implicitly — not by an autonomy
  level, not as a side effect of another setting, not by an env var alone
  without the same deliberate act. Its own summary text states the consequence
  in plain words, because the config panel is where a user will meet it.
- **Fresh re-authentication per answer** (item 5). A valid device certificate is
  not sufficient; the user factor must have been re-presented for *this* answer.
- **Loud logging** — device, user, class, tool, exact argument, surfaced locally
  and not only appended to a file (ADR-0007 invariant 4).
- **Kill switch overrides it instantly**, mid-flight.
- **Silence still denies** — timeout, dropped link or an ambiguous request-id
  match produces no `allow`, ever (ADR-0007 invariant 3).

And the line that must survive in the code comment: **Golem still never emits
`allow` for `destructive`/`outward` itself** (ADR-0002 invariant 5). This setting
changes *who counts as the human answering the prompt*, not what Golem decides.
If an implementation finds itself making the gate emit `allow` for those classes,
it has gone wrong.

## Constraints worth stating

- **A control may narrow, never widen — with item 3 as the single, decided
  exception**, which is why it carries five conditions instead of a default.
- **No control gates *sending*.** ADR-0007 §3c removed that; a policy that makes
  the send box conditional reintroduces exactly what Revision 1 rejected. These
  gate what happens *after* a message.
- **Defaults are documented where the user reads them**, not only in code — the
  config panel's summary strings are user-facing prose and the
  retired-identifier check scans them.

## Out of scope

Anything about the relay or accounts (R13.10). Per-tool allowlists — ADR-0002
owns classification and this task does not fork it. Multi-user policy: one
developer, one set of devices. Changing what `classifyAction` classifies.

## Gate detail

A test per control: the default is what §3d says, enforcement happens at the
point the map names, and flipping it changes behaviour observably. For item 3,
five separate tests, one per property above — including one that asserts it
cannot be switched on implicitly, in the spirit of ADR-0004's no-dial-disables-
redaction rule, and one that asserts the gate still never emits `allow` for those
classes even with the setting on. Plus a kill-switch test proving in-flight
authorship stops rather than finishing. Wiki page laying out the map as a user
sees it, with two sentences carried verbatim in substance: authorship itself is
never gated, and item 3 is the one setting that lets a device authorize something
irreversible.
