## Why this exists

The user's words (ADR-0007 Revision 1): *"I don't want to put any limits on
remote authorship, maybe we can have some user controls applied once we define
where possible gates could be."* §3d is that definition. This task turns the
enumeration into switches the user can actually reach, which is the deal —
authorship is unrestricted, and the controls are theirs to choose, not Golem's to
impose silently.

Read §3d's table before writing any code; it carries the defaults and they are
not all "on".

## What to build

One coherent policy surface, not nine scattered flags:

1. **Session visibility** (item 1) — which sessions and projects a device may see
   and address. Default: all, for a paired device.
2. **Origination scope** (item 2) — which project roots a device may start a
   session in. Default: all known roots.
3. **Approval routing when nobody is local** (item 4) — for `read`/`write`/
   `unknown` only, per Decision 59(a). Default: route to the device.
4. **Re-authentication for high-risk acts** (item 5) — on for origination, off
   for ordinary messages. Keys off R13.4's user factor.
5. **Rate and size limits per device** (item 6) — on, generous, and the refusal
   says the limit rather than dropping quietly.
6. **Kill switch** (item 7) — one command and one tap that suspends all remote
   authorship immediately, always available, and loud in `golem status`. This is
   the control that matters most in an incident; build it first and test it
   hardest.
7. **Quiet hours / presence** (item 8) — offered, default off.
8. **Per-session pause** (item 9) — suspend remote authorship for one
   conversation without unpairing. Default available.

**Item 3 is not on this list and must not appear on it.** Decision 59(a) says
`destructive` and `outward` are never remotely approvable "with no setting to
change it". Unlocking that is an amendment to a user decision, not a feature —
so this task ships a **test asserting no such control exists**, in the spirit of
ADR-0004's "no dial value can disable redaction". If the user later amends 59(a),
that amendment carries its own task.

## Constraints worth stating

- **A control may narrow, never widen.** Every switch here can restrict what a
  device may do; none may grant a device something ADR-0002 or Decision 59(a)
  withholds.
- **No control gates *sending*.** ADR-0007 §3c removed that; a policy that makes
  the send box conditional reintroduces exactly what Revision 1 rejected. These
  gate what happens *after* a message, not whether it may be typed.
- **Defaults are documented where the user reads them**, not only in code — the
  config panel's summary strings are user-facing prose and the
  retired-identifier check scans them.

## Out of scope

Unlocking item 3. Anything about the relay or accounts (R13.10). Per-tool
allowlists — ADR-0002 owns classification and this task does not fork it.
Multi-user policy: one developer, one set of devices.

## Gate detail

A test per shippable control: the default is what §3d says, the enforcement
happens at the point the map names, and flipping it changes behaviour observably.
Plus the negative test for item 3, and a kill-switch test that proves in-flight
authorship stops rather than finishing. Wiki page laying out the map as a user
sees it, with the sentence that authorship itself is never gated — because a user
who cannot find the "block sending" switch should learn from the docs that it
does not exist by design.
