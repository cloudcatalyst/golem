## What R10.4 left

R10.4 pinned the QUERY embedder to the index's recorded one, so a hardware-tier
downgrade can no longer produce a width mismatch at query time.

`buildKnowledgeStack` (`src/cli/build-knowledge.ts`) — the BUILD side used by
`golem index` and `golem mcp serve` — still selects the embedder purely by
detected tier.

## Why it is lower severity, and still real

A degraded probe there does not produce bad queries: the embedder change alters
the manifest signature, which triggers a full rebuild, and the result is
self-consistent. So nothing breaks.

But it means **a transient probe hiccup silently re-embeds the entire index at
the degraded width** — expensive, invisible, and it quietly downgrades retrieval
quality (nomic-embed-text/768 in place of bge-m3/1024) until something rebuilds
it again. The user is never told that the index they just built is not the one
they had.

## Approach

`planQueryEmbedder` and the `embedder: {mode, model, dim}` manifest record from
R10.4 already exist; the build side should use the same vocabulary rather than
growing a second one. The question to settle is what a build SHOULD do when the
detected tier disagrees with an existing index: rebuild at the new width (today's
silent behaviour), refuse and explain, or keep the index's embedder when it is
still available — the last being what R10.4 chose for queries.

## Out of scope

The tier catalog's model choices. The query path (done in R10.4).

## Outcome

shipped: a build never NARROWS an existing index's vectors while the embedder that built it is available. Widening still allowed, so lexical->semantic and CPU->GPU upgrades survive — R10.4's rule applied verbatim would have frozen the index forever. One retry on a false ollamaHasModel.
