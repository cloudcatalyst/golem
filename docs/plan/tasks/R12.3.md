## The job

A remote "Approve" must become a `permissionDecision` that the hook applies — and
must be incapable of becoming anything else. Four properties decide whether this
is safe, and all four are testable:

1. **Exact match.** A decision applies to *one* pending request, identified by
   session + tool + a digest of the exact input + a nonce Golem generated. A
   decision that arrives for a request that already resolved, or whose input
   differs by a byte, is discarded and recorded as discarded. This is what stops a
   replayed "yes" from approving the *next* command.
2. **Bounded wait, and the timeout denies.** The hook cannot block indefinitely
   (Decision 21b's open edge 1). Past the window it falls back to the local
   prompt — which is a *deny* from the hook's perspective, never an allow. Measure
   the real ceiling before choosing the number: `golem hook post-tool-use` is
   ~126ms today and the CLI's hot-path latency is a standing constraint
   (Decision 51), so an added wait must be conditional on there being a paired
   device at all.
3. **The gate stays the authority.** Remote input is one more voice into
   `src/autonomy/`, subject to every rule already there. If the autonomy level
   forbids a class of action locally, a phone cannot raise it. Prove this with a
   test whose remote approval is *ignored* because the local policy said no.
4. **Audited.** Every decision — applied, timed out, or discarded — leaves a
   record naming which request it answered. R11.7's standard: the log answers
   "did Golem do this?" without inference.

## The property that matters most

**With no paired device, behaviour is byte-for-byte unchanged.** No added latency,
no new file, no new code path taken. The feature is invisible until someone opts
in, and `golem status` says plainly when it is on.

## Out of scope

The transport (R12.4) — this task consumes decisions from a local store and does
not care how they arrived. The UI (R12.5). Any notion of "continue" (R12.7);
this is approve/deny only.

## Gate

A pending request can be approved from a second local process before its deadline,
is denied when nothing answers, and cannot be approved by a stale, replayed or
mismatched decision. Plus: the unpaired path is unchanged, demonstrated rather than
asserted.
