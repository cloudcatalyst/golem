## Goal

Make "use a big local MoE instead of upstream tokens" a command rather than a
weekend. R8.15 made llama.cpp *addressable*; nothing yet makes it *present*.

## The selection is the feature, not the catalog (user, 2026-08-01)

> "The model choice should be fit for purpose, and fit for hardware. […] we're building
> a tool that's not just for me, but for any developer to have an efficient sub-harness
> interface to be able to scale up or down compression, brevity, and model choices based
> on what they have access to, the tokens they want to consume, and the expectations of
> the task."

So **there is no default model.** A 64 GB workstation and a 16 GB laptop want different
weights for the same request, and a throwaway classification wants different weights
from an agent that will run for an hour. The catalog is a ladder; `selectModel(role,
usableRam, contextTokens, prefer)` is the entry point; `FLOOR_GGUF_MODEL_ID` is named a
floor precisely so nobody reads it as a recommendation. Returning **`undefined` — "no
local model is appropriate on this machine right now" — is a valid and required
answer**, because loading something that swaps is worse than not loading it.

This also retires the earlier "default local coder with a defined model" framing: the
direction is **several tools in one conversation, local and upstream, with agents
commanding the same set** (R8.19).

## Why now

R8.15 shipped the provider table, so Golem can already talk to a llama.cpp server —
if one exists. Standing one up by hand today means: pick the right release asset for
your GPU, get the matching CUDA runtime, pick a quant that fits, find the MoE offload
flags, and hand-write the provider entry. That is the gap between "supported" and
"usable", and it is the whole reason the user asked.

The prize is specific and measured: on 8 GB of laptop VRAM, `-ngl 99 --n-cpu-moe 999`
keeps a 35B-A3B MoE's experts in RAM and its attention on the GPU, so ~3B parameters
are active per token. That is what makes a 20 GB model usable on this class of machine
— and what makes local work a real substitute for upstream tokens rather than a
consolation prize.

## Verified upstream facts (2026-08-01, verification-notes §113)

- **llama.cpp release `b10216`** (published 2026-07-31). Windows assets include
  `llama-b10216-bin-win-cuda-13.3-x64.zip` (139 MB) with a separate
  `cudart-llama-bin-win-cuda-13.3-x64.zip` (372 MB), a CUDA 12.4 pair, and
  `llama-b10216-bin-win-vulkan-x64.zip` (32 MB, no runtime bundle needed). The GitHub
  release API reports a **`sha256:` digest per asset** — so verification is available
  and must be used.
- **`ggml-org/Qwen3.6-35B-A3B-GGUF`** carries `Qwen3.6-35B-A3B-Q4_K_M.gguf` (19.02 GB),
  `Q8_0` (34.37 GB), `mtp-Qwen3.6-35B-A3B-Q4_0.gguf` (0.99 GB, multi-token prediction
  draft for speculative decoding) and `mmproj-…-Q8_0.gguf` (0.57 GB, vision).
- There is **no official `Qwen/Qwen3.6-*-Coder`**. The stable coder line is
  `Qwen3-Coder-Next`, and it is large: `unsloth/Qwen3-Coder-Next-GGUF` Q4_K_M is
  **45.20 GB**, with UD-IQ2_M at 23.25 GB. See "The coder-model finding" below.

## What to do

**A curated GGUF catalog** (`src/inference/gguf-catalog.ts`) — data, in the style of
`catalog.ts`: repo, files, bytes, quant, whether it is MoE, active-parameter count,
minimum RAM, and the roles it suits. Curated and small on purpose: community fine-tunes
get re-uploaded and vanish, so the shipped table names only stable publishers
(`ggml-org`, `Qwen`, `unsloth`) and anything else is the user's own entry — the same
argument little-coder makes for keeping its `models.json` short.

**Hardware-aware planning, pure and testable.** Given detected RAM/VRAM and a catalog
entry, produce the `llama-server` argument array: `-ngl`, `--n-cpu-moe` for MoE models,
`-c` sized to what is actually free, `--jinja`, and the speculative-decoding flags when
an MTP draft is present. Pure function in, argument array out — no shell strings
(CLAUDE.md cross-platform rule).

**Install, with consent and pinned.** Mirror `golem ollama setup` (Decision 26): this is
the second module allowed to install software, it is never invoked automatically, and
`golem init` must not import it. Golem ships none of llama.cpp's bytes — it fetches the
pinned upstream release asset, **verifies the sha256 the release API publishes**, and
extracts it. A checksum mismatch aborts; it never runs an unverified binary.

**Downloads must be resumable and backgroundable.** A 20 GB GGUF is not a foreground
tool call. HTTP range requests, a partial file that survives an interrupt, and progress
that is readable from another process. This is the design constraint that shapes the
whole command; do not build a blocking download and bolt resumption on later.

**Model files go where there is room.** Default under the Golem data dir via `env-paths`,
but the target must be configurable, and the command must **check free space on the
target volume before starting** — the machine that motivated this has 23.8 GB free on
`C:` and 2.5 TB on `D:`.

**Then wire it.** On success, write the `inference.providers` entry (R8.15) so the model
is immediately resolvable, and verify by reading `/props` back.

**Lifecycle.** `golem llamacpp status|start|stop` — a llama-server is a long-running
process Golem did not previously manage. Reuse the proxy's daemon discipline (pid file,
`status` reports a real pid) rather than inventing a second one.

## The coder-model finding — do not silently pick a bad quant

The user asked for separate coder and general models. On 64 GB of RAM that does not fit
as hoped: `Qwen3-Coder-Next` Q4_K_M (45.20 GB) alongside Qwen3.6-35B-A3B Q4_K_M
(19.02 GB) is 64 GB against a 64 GB machine. Every alternative is a trade — UD-IQ2_M
(23.25 GB) is a real quality loss on code; official `Qwen2.5-Coder-32B` (~20 GB) is
**dense**, so all 32B stream from RAM and it is *slower* than the 35B MoE, not faster;
`Qwen3.6-27B-A3B-Coder` (~16 GB) is A3B and fast but a community repo.

The catalog must make this a one-line choice and the planner must **refuse a
combination that does not fit measured RAM**, reporting the arithmetic rather than
letting the OS discover it by swapping. Default to the single A3B model serving both
roles until a two-model set is shown to beat it.

## Out of scope

- **Building llama.cpp from source.** Prebuilt pinned release assets only. A CUDA
  toolchain build is not something Golem should drive.
- **Vendoring or mirroring any binary or GGUF.** Decision 53: a binary is a spawn
  target, never cargo.
- **Auto-install on first use.** Explicit command, explicit consent, always — the
  Decision 26 rule, and a 20 GB download makes it more important, not less.
- **Fine-tuning, quantizing, or converting models.**
- **The routing fabric** — that is R8.19 and must not be pre-empted here.

## Gate detail

Live, on the machine, recorded in `verification-notes.md` with the release tag, asset
digest, model file, server command line, and measured tokens/sec. **A slower-than-hoped
number is a result, not a failure** (§89/§100 precedent) — record it either way.
