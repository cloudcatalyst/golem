## Problem

`_transform` in `OpenAIChatSSETranslator` accumulates SSE data into `#buf` without any size bound:

```ts
override _transform(chunk: Buffer, _enc: BufferEncoding, cb: TransformCallback): void {
  this.#buf += chunk.toString("utf8");
  // ... find first \n, process line ...
  cb();
}
```

If an upstream sends an SSE line > available RAM (or a streaming bomb with `data:` lines that never contain a newline), `#buf` grows until OOM. This affects the OpenAI→Anthropic streaming translation path — the non-default provider path (R6.1 case (b)) — so risk in practice is low. But memory-safety guards should not depend on the upstream being well-behaved.

## Fix

Add a cap on `#buf` length — e.g. 1MB. If `#buf` exceeds it, either:
- Drop the overlong line and continue (best-effort stream recovery), or
- Emit an error on the transform (propagates as a stream error)

Simple approach: check `this.#buf.length` in `_transform` before concatenating. If it would exceed `MAX_BUF_SIZE`, flush `#buf` + truncate the chunk to the last complete line, dropping the oversized remainder.

## Out of scope

- The Anthropic→Anthropic passthrough path (uses undici pipeline, no SSE transform)
- Adding a size cap to usage-sniffer's `#lineTail` (that's accepting the same risk for a trusted upstream)

- `npm run typecheck`, `npm run lint`, `npm run test`
- New test asserting the translator handles a >1MB SSE line without memory growth
