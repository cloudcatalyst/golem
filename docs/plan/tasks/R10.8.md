## The defect

`createTargetDispatcher(...).dispatch()` resolves a target in this order
(`src/inference/target-dispatcher.ts:377-397`):

1. an explicit `targetId` on the call,
2. this worker's `inference.worker_targets` entry,
3. **local tiered inference** — `options.inference.chat(...)`, audited as
   `"no target named — local tiered inference"`.

`inference.default_target` is **never consulted**. So the local Ollama model is
the implicit default for every worker that has no explicit mapping, and the
setting that exists precisely to name a default is skipped.

That is backwards. Local should be one target among many — reachable because you
named it, not because nothing else was named.

## What it should be

```
explicit targetId
  -> inference.worker_targets[worker]
    -> inference.default_target
      -> the harness's own default upstream (proxy.upstream_*)
```

A local backend (Ollama, llama.cpp) is then reachable exactly like any other:
declare a gateway, declare a target that points at it, and name that target —
via `worker_targets`, `default_target`, or per call.

## What already exists (do not rebuild it)

- `ollama` is ALREADY a gateway/target provider (`UPSTREAM_PROVIDERS`,
  `src/providers/index.ts:93`), and llama.cpp is reachable today through the
  OpenAI-shaped provider — `probeInferenceEndpoint` is OpenAI-aware (`/v1/models`)
  specifically so a llama.cpp server with a loaded GGUF answers rather than 404s
  (R8.15).
- `proxy.targets` already carries `{ gateway, model }`, so naming a specific
  model on a specific local endpoint is already expressible.
- `inference.default_target` already exists and is optional; unset already means
  "use the top-level upstream config".

So this is a ROUTING change, not new capability. The pieces are there; step 3 of
the chain is wrong.

## Decide while doing it

- **Is a first-class `llamacpp` provider type worth adding?** It works today as
  `openai` + a base_url. A distinct type buys a clearer `golem gateway add` and
  better probe/error messages; it costs another enum member and another branch
  everywhere `provider` is switched on. Weigh it; do not add it by reflex.
- **What happens when `default_target` names something unreachable?** The rest of
  the codebase is fail-closed on unknown target ids (`worker_targets` explicitly
  refuses to "silently fall back to the local model — that would send the work
  somewhere the user did not choose while reporting success"). The new step 3
  must be fail-closed the same way, NOT a silent slide to local.
- **What does `coder` do when there is no local model AND no default_target?**
  Today local-unavailable is a soft failure. After this change the harness
  default is the last resort, which is a better answer — make sure the message
  says which one it used.

## Out of scope

- Removing the local model as a capability. It stays; it stops being implicit.
- The redaction floor: every non-local dispatch is already redacted at its
  target's trust floor (R9.3), and this change routes MORE traffic to non-local
  targets, so that path must not be weakened — it is what makes the change safe.

## Verification

A project with no `worker_targets` and no `default_target` must send a `coder`
draft to the harness's default upstream, not to Ollama — provable from the audit
record and `golem status`, without a local model installed at all.
