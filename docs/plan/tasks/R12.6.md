## The question

A companion app whose owner must remember to open it is not a companion app — the
whole value is *not sitting at the laptop*. So: how does a phone find out that a
permission prompt is waiting?

And the constraint that makes this hard: **Web Push requires a push service.** On
Android that is Google's infrastructure; on iOS, Apple's. Both are third parties in
the path, which collides head-on with R6.3's "self-hosted relay only, no
Golem-operated service". A self-hosted push server does not remove them — it only
removes *Golem* from the list.

> **Reopened 2026-08-21 by ADR-0006 Revision 2.** The user's relay decision changes
> this spike's shape: a relay that is already holding a connection for a paired
> device is the obvious place for a push to *originate*, so **relay-originated push
> is now option 1** and must be evaluated before the alternatives below. Two new
> sub-questions come with it: what a push payload may contain (the answer is
> "something is waiting", never the command or the project), and whether the relay
> can originate a push without learning more than §3b already concedes.

## What to establish, with dates

1. **What Web Push actually leaks to the push service.** VAPID, payload
   encryption, and what an endpoint reveals even when the body is opaque. If an
   encrypted "something is waiting" with no detail is genuinely opaque to Google
   and Apple, that changes the answer — verify it, do not assume it.
2. **Whether iOS delivers Web Push to an installed PWA** in the current OS
   version, and under what conditions. This has changed more than once; check the
   live docs.
3. **The LAN-only alternatives, honestly costed.** A foregrounded PWA holding a
   connection. A self-hosted ntfy or Matrix target the user already runs. A
   local-network wake. Each one's failure mode when the phone is locked and off
   Wi-Fi is the interesting part, not its happy path.
4. **The fallback that always works:** the laptop is right there and Claude Code
   already prompts locally. State plainly what the user loses if the answer to
   this spike is "nothing reliable" — they lose remote *unblocking*, and keep
   remote *observation*.

## The acceptable outcomes

Three, all fine:

- **A self-hosted-enough path exists** → propose it, with the ADR paragraph naming
  every third party that remains in the path.
- **Only a degraded path exists** (foreground-only, or LAN-only) → say so, and
  R12.5 ships with polling while open and nothing more.
- **No path meets the bar** → recorded as a reproducible negative, the way §100
  and §108 were. The companion app is then an observation-and-approve surface the
  user opens deliberately, which is still worth having.

## Out of scope

Building any of it. Any Golem-operated push service. A native app (that decision
follows from this answer, it does not precede it).

## Gate

A dated verification-notes section that answers all four questions from live
sources, and a recommendation the ADR can absorb. "No reliable path" is a passing
answer; an unverified assumption in either direction is not.
