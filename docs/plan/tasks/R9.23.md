## The defect

Hit live on 2026-08-10 while working R9.22. The session reached the usage limit, and
enforcement (Decision 45) denied every tool except `mcp__golem__snooze` — correct. But
`snooze` is a deferred tool, so calling it first requires `ToolSearch` to load its schema,
and **every** such call came back elided:

```
[Golem: duplicate content elided (lossless dedup, ~152 tokens); identical content appears
earlier in this conversation. Retrieve original: hash=2725829de20d080cb1c0ab8dd1b7396ce769f1e2ec96156ffc62993039c68646]
```

Four different query spellings, all elided to the same hash:

- `select:mcp__golem__snooze`
- `snooze park usage limit until note`
- `+snooze`
- `select:mcp__golem__snooze` (repeat)

That is a **deadlock**. The only permitted tool cannot be called, because the only way to
learn its parameters returns a reference instead of the schema — and `expand`, which would
retrieve the reference, is itself a deferred tool needing a schema, and is denied by
enforcement anyway. The agent cannot park, so the note that survives the session is never
written.

**Workaround that unblocked it:** ask for several tools in one call
(`select:mcp__golem__snooze,mcp__golem__stats,mcp__golem__level`) so the response payload
differs from the cached hash. That should not be knowledge an agent is required to have.

## Why it is wrong beyond the deadlock

A tool schema is not prose. It is the *executable contract* for a call the model is about
to make, and unlike a file excerpt it cannot be re-derived, narrowed, or grepped for. CCR's
bargain — replace bulk with a reference the agent can expand on demand — assumes expansion
is always available. For tool schemas under enforcement it is not.

The elision also looks incorrect on its own terms: the first `select:mcp__golem__snooze`
call was elided as a duplicate although no prior response in that conversation contained
the snooze schema. Worth confirming what the hash actually keys on before fixing the
symptom — the dedup may be matching on something other than the emitted content.

## Options

- **Exempt tool-schema responses from CCR entirely** — narrowest and almost certainly
  right. `ToolSearch` results are small, bounded, and never worth the round trip.
- Exempt them only while enforcement is active — cheaper, but leaves a confusing elision in
  every other session for no gain.
- Make the enforcement gate permit `ToolSearch` *and* `expand` as a general escape hatch —
  a good companion regardless, since any deferred tool needed for parking has this shape.

## Watch for

- Whatever lands must be provable *at the gate*, not just in a unit test: the failure only
  appears when enforcement and a dedup hit coincide.
- Check the same reasoning for any other response class the agent cannot re-derive
  (permission prompts, hook feedback), not just tool schemas.
