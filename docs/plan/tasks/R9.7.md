## The report

> *"a webfetch which is serviced by golem works, but shows a red dot in claude code"*

Accurate, and it is the mechanism rather than a defect. `runWebFetchPre` serves a cached
or self-fetched page with `permissionDecision: "deny"`, putting the content in
`permissionDecisionReason` (the only PreToolUse field Claude actually reads). Claude Code
renders a denied tool call as an error. So Golem's **best** path — content served, network
fetch skipped, summarizer call avoided — is the one that looks broken.

Reproduced live 2026-08-09: a `WebFetch` of the hooks doc came back inside an `<error>`
wrapper whose first line was `✓ Golem served this URL from the knowledge base`. A tick
inside an error box is the whole problem in one line.

## Why the obvious fix does not exist

§44 concluded there is no way to substitute a tool's output at PreToolUse. That note
predates several hook changes, so §115 **re-verified it against live docs** rather than
trusting it: PreToolUse decision control still has exactly `permissionDecision`,
`permissionDecisionReason`, `updatedInput`, `additionalContext`. No `updatedToolOutput`
(PostToolUse only), no synthetic-result field. `deny` + reason remains the only way to
return content without running the tool.

Do not re-derive this. If you think you have found a fifth field, check the date on the
docs first.

## The candidate: loopback serve + proxy-side short-circuit (user, 2026-08-09)

`updatedInput` + `permissionDecision: "allow"`: rewrite `tool_input.url` to a loopback URL
that Golem serves the page from, so WebFetch runs normally, succeeds, and renders green.

Taken alone this **re-introduces what Decision 42 Option A removed** — WebFetch runs,
including its internal summarization model call, an LLM round trip per fetch. That is the
cost that made this look like a bad trade for a UI colour.

**The user's two-part refinement removes most of that objection, and it is the design to
build to:**

### (a) Do the cache check at the loopback endpoint, not in the hook

Stop branching in the hook. **Always** rewrite to
`http://127.0.0.1:<port>/…?u=<url>` and **always** `allow`. The endpoint then does
hit → serve from cache, miss → fetch + redact + cache + ingest + serve.

This is strictly better than the current shape beyond the rendering fix:

- one code path instead of the hook's four (hit / stale / revalidate / raw-miss), and the
  cache-serve and self-fetch paths stop being separately reachable;
- the hook stops needing `WebCache`, `fetchRawPage`, CCR and the KB — it becomes a URL
  rewrite, which is the only thing PreToolUse is actually good at;
- `MAX_SERVED_CHARS` truncation and the CCR-ref dance **disappear**. Today an 8k cap
  exists because the content has to fit in a deny *reason*; over HTTP there is no cap, so
  large pages stop being truncated-and-re-expanded.

### (b) Short-circuit the summarization call at the proxy

The hook cannot tell WebFetch to skip summarizing. But **Golem is already in the path of
that call** — verification-notes records it as a single-turn, tool-free request carrying
the fetched page, *observed in the wild* transiting the proxy (it once matched the
project's README above the confidence floor, which is why
`MAX_LOCAL_ANSWER_QUERY_CHARS = 1000` exists to exclude it).

So: have the loopback response carry a **sentinel**, and have the proxy recognize a
summarization request whose embedded content contains that sentinel and answer it directly
via the existing `respondDirectly` seam (Decision 33) — no upstream call, no tokens.

That flips the length gate's role. It excludes these requests today *because* they carry a
page; here the page is one **Golem itself planted**, so it can be recognized precisely
rather than guessed at.

## Scope

- Verify the premise first: **does WebFetch actually honour a rewritten `url` via
  `updatedInput`?** Everything else depends on it and it is currently unverified. If it
  does not, stop and record that.
- The loopback endpoint, with (a) above.
- The proxy-side sentinel recognition + `respondDirectly` short-circuit, with (b).
- Measure what is left: with (b) working the LLM cost should be ~0; without it, the
  summarizer round trip per fetch is the number that decides whether (a) alone is worth
  shipping.
- Cheaper half-measures, if the above is refused — say why they are or are not enough:
  wording that reads correctly *inside an error box* (the intro already opens with `✓`),
  or `additionalContext` on an `allow` where the fetch is cheap anyway.
- Whatever is decided, write it down. An accepted red dot with a recorded reason is a fine
  outcome; an unexplained one gets re-reported every few weeks.

## Out of scope

- Removing the cache-serve behaviour. It works, it is fast, and it avoids both a network
  fetch and an LLM call — the rendering is the only complaint.
- Anything requiring a Claude Code change.
- The proxy-side local-answer path (§ the two-interception-points note) — a different
  mechanism that happens to touch the same tool.

## Watch for

- **The short-circuit (b) inverts the context economics, and this is the trap.** With (a)
  alone, WebFetch summarizes the page and only the *summary* enters context — good. Add
  (b) and the raw page enters context **whole**. The hooks doc measured in this session is
  **248,890 chars**; the current deny path caps inline content at `MAX_SERVED_CHARS`
  (8,000) precisely to stop that. So "the 8k cap disappears" is a benefit for *fidelity*
  and a hazard for *context* — this is a context-economy project, and a 249k page landing
  in one tool result is a far worse regression than a red dot. The short-circuit must stay
  bounded: keep the head + `hash=` CCR-ref treatment, or let genuinely large pages fall
  through and actually summarize. Decide the threshold deliberately and measure it.
- **The sentinel must not be forgeable.** A hostile page that contains the sentinel string
  would steer the proxy into short-circuiting a summarization it should not touch — a
  prompt-injection-shaped hole in the one component that exists to be trustworthy. Use a
  per-run unguessable nonce held in `.golem/state/`, not a constant baked into the source
  (which ships in the npm package and is readable by anyone).
- **What the caller receives changes.** WebFetch's contract is "answers `prompt` against
  the page"; a short-circuit returns content rather than an answer to that prompt.
  Decision 42 Option A already made exactly that trade on purpose (prompt-independent raw
  text, which is why it is cacheable), so this is consistent — but re-affirm it rather
  than inheriting it silently.
- **Do not "fix" this by allowing the fetch and caching afterwards.** That is the legacy
  pre-Decision-42 behaviour, and it caches WebFetch's *prompt-specific answer* rather than
  the raw page — the exact bug Decision 42 exists to fix.
- A loopback URL served to WebFetch must not become an unauthenticated local endpoint that
  serves arbitrary cache entries to anything that can reach the port. It is reachable by
  any process on the machine, so it needs the same nonce as the sentinel.
- The proxy already binds loopback-only and its request bodies are uncapped by design
  (`readBody`'s comment says so, on the assumption of local bounded JSON) — a new endpoint
  that serves cache entries should re-read that assumption rather than inherit it.
