## Bug 1 — `key MISSING` for a keyless provider

`src/cli/targets.ts:322-327`:

```ts
const key = t.key_set
  ? `key set — ${t.key_location ?? "stored"}`
  : t.account === null
    ? "no stored key (inherits the client's auth)"
    : "key MISSING";
```

The **warning** logic thirty lines above gets this right — it exempts keyless
providers explicitly, with a comment saying why:

> "R10.8: so is a model server the user runs themselves (`ollama`, `llamacpp`).
> It is not that a missing key is tolerable there — it is that a key is not part
> of how you reach it … Keyless is the CORRECT state for these, not a degraded
> one."

The **display** branch never learned that. So a correctly configured `ollama`,
`llamacpp` or `claude-cli` gateway target reads as broken:

```
    claudecli:claude-sonnet-5    claude-cli https://api.anthropic.com model=claude-sonnet-5
        trust=third-party account=claudecli key MISSING (from gateway)
```

Nothing is missing. `isKeylessProvider` already exists and is already imported in
that file for the warning; the display branch needs the same question asked.

Note the two branches disagree on *which* fact they key off — the warning asks
about the provider, the display asks whether an account id is present. Fixing one
line is enough, but check whether the honest rendering is "keyless" rather than
either existing string.

## Bug 2 — "model will be IGNORED" on a provider that pins the model

`src/cli/gateways.ts:204`:

```ts
if (models !== undefined && models.length > 0 && !isTranslatingProvider(input.provider)) {
```

fires:

> `warning: provider "claude-cli" is byte-faithful (it forwards the client's own model id unchanged), so model(s) "claude-sonnet-5" will be IGNORED on the wire — they are recorded for display only.`

Both halves are false for a spawn provider. `claude-cli` forwards nothing — it
spawns a process — and `claudeCliArgs` pins the model as an explicit argument:

```ts
return ["--print", "--model", model, "--output-format", "text", …];
```

The model is not display-only there; it is the most load-bearing field on the
target. It is also what the dispatcher's same-model guard compares against, so a
user who believes this warning and omits the model gets a target that cannot
dispatch at all.

The condition wants `&& !isSpawnProvider(input.provider)` as well. The predicate
already exists in `src/providers/index.ts`.

This one actively misled a real user, who asked whether the spawn route could
target a different model *because the warning said it could not*.

## Ordering note

R13.12 removes the `claude-cli` provider. These two bugs are **not** made moot by
that:

- bug 1 still affects `ollama` and `llamacpp`, which are staying;
- bug 2's condition is still wrong in principle, and leaving a
  `!isTranslatingProvider` check as the sole test re-creates the same defect the
  next time a non-translating, non-forwarding provider is added.

Ship this independently of R13.12 — it is small, it touches different files, and
neither blocks the other. If R13.12 lands first, drop the `claude-cli` mentions
and keep both fixes.
