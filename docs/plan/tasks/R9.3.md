## Goal

Let `coder` run on **any** target from the R9.1 registry, not only the local
Ollama. This is the mechanism that delivers *"divert to a different model when
there is a good reason"*, and it is **out-of-band by design**: the diversion is
a tool call whose result appends to the transcript, so the conversation's cache
prefix is never touched.

It is a sibling of R9.2, not a successor — both depend only on R9.1 and may land
in either order.

## Why `coder` is not replaced by a sub-agent

Both mechanisms stay; they serve different model capability classes. `coder`
gives a *weak* model a narrow tool surface and a small prompt — which is exactly
why it works where a sub-agent would not. A sub-agent carries Claude Code's full
system prompt and tool schema, which a 3B–14B local model cannot handle. For a
*capable* target, use a sub-agent and build nothing.

Full reasoning and the comparison table are in the proposal; do not re-derive.

## The redaction blocker — the reason this task exists

**`src/mcp/` contains no redaction calls at all.** `coder` reaches the model via
`InferenceService` → Ollama directly, never crossing the proxy's redaction
stage.

That is *sound today*, because the only reachable target is local: nothing
leaves the machine. **The moment `coder` can name a remote target it becomes an
egress path that bypasses redaction** — carrying exactly the material most worth
redacting (KB/wiki grounding from `gatherGrounding`, and in `edit` mode, project
source). That violates the CLAUDE.md hard rule *"redaction must never be
weakened or reordered"*.

This is a risk **introduced by this change**, not a pre-existing bug — and it
must land in the same slice as the target parameter. Shipping the parameter
first and the redaction after is not an acceptable ordering.

Required behaviour:

- `trust = "local"` → today's direct path is permitted unchanged.
- Any non-local target → **redact before dispatch**, at that target's `trust`
  floor. A target may raise the floor, never lower it.
- The placeholder table must **round-trip**, so the returned draft is
  de-redacted before it reaches the caller. A draft full of `[REDACTED_1]` is
  useless — this deserves its own test, not a corner of another one.

The fix is cheap: `redactRequestBody` and `redactStandaloneText` are already
standalone exports in `src/pipeline/redaction.ts` (:206 / :149). No proxy hop,
no refactor.

## The frozen-contract constraint

`src/interfaces/inference.ts` is a **FROZEN CONTRACT** whose stated doctrine is
*"callers never name concrete models"* — role-based dispatch through the tier
catalog. A `coder` that names a target contradicts that head-on.

**Do not amend the frozen contract.** Introduce a `TargetDispatcher` *above* it:

- `InferenceService` keeps its exact present meaning (local, tiered,
  role-based). Untouched — no tests to update, no dependent workstream to flag.
- `TargetDispatcher` resolves a target id, then either delegates to
  `InferenceService` (local target, mapping the requested role through the
  existing catalog) or dispatches to a remote target reusing the R6.1
  translators — **after redaction**.

## Scope

- `TargetDispatcher` over the frozen `InferenceService`.
- Optional `target` param on `coder`; **omitted → behaves exactly as today.**
- Redaction-before-dispatch with placeholder round-trip.
- The `target` enum exposes only targets config marks **agent-selectable** (see
  open question below).
- Audit: every `coder` dispatch records `(target, provider, model, reason)` on
  the existing ADR-0003 invariant-5 audit log.

## Out of scope

- Proxy-side routing (R9.2).
- Giving `coder` model-driven tool use (letting the model decide to read a file
  or grep). That is a real feature but a different one — and the argument above
  says a capable model should use a sub-agent instead.
- Amending `src/interfaces/inference.ts`.
- Failover between targets.

## Who chooses the target — SETTLED (USER, 2026-08-08)

**The triggering conversation chooses, bounded to the range config declares.**
No further ruling needed; build to this.

The earlier framing ("is an agent selecting?") was the wrong axis. `coder` is a
narrow tool, not an agent, and the model in the conversation is what decides
either way — so agent-vs-tool draws no security line. The control that carries
the weight is: **can the selection reach anything the user did not declare?**
Here it cannot, and that is the whole guardrail.

ADR-0003 invariant 4 forbids a tool selecting an **account** or reading a
**secret**. `coder(target: …)` does neither — a target is not an account, and no
credential is exposed. The letter holds and the spirit is satisfied by the bound.

**Precedent this is measured against.** The `level` MCP tool already lets a
conversation change proxy behaviour, including **level 0, which disables
redaction entirely** ("secrets reach the upstream raw"), guarded by a warning
string. Choosing among declared targets — each of which *keeps* redaction on at
its trust floor — is strictly safer than a capability that already ships.

### What this means for the schema

- The `target` enum lists declared targets, **selectable by default**.
  Declaring a target is already a deliberate act; requiring a second opt-in flag
  on each one is ceremony without safety.
- `agent_selectable = false` opts a single target **out**. This exists for the
  case that actually matters: an expensive target (your main Anthropic account)
  that you want reachable by an explicit route but never picked for a draft.
- **Never** accept an ad-hoc URL, an undeclared id, or an account name. An
  unknown id is a clean tool error, never a fallback to another target.
- The trust-floor redaction above is what makes a *wrong* selection bounded
  rather than harmful — it is the second layer, and it is why this is safe.
- Every dispatch is audited with the resolved target and reason.
