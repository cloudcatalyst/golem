## The defect

`golem proxy restart` intermittently prints

```
golem: proxy did not come up on port 4930
```

while the proxy is in fact running and serving — `golem proxy status` immediately
afterwards reports `running (pid …) on port 4930`, and the session it is carrying never
notices. Observed roughly 1 run in 3 during R9.12, with every run taking ~15–16s.

## What has been ruled out

R9.12's loopback endpoint is **not** the cause, though it was the first suspect. The
daemon binds its port and writes its pid file *before* any loopback code runs, confirmed
by the log ordering:

```
golem proxy listening on http://localhost:4930 -> https://api.anthropic.com (slider level 3)
golem proxy: loopback serve on https://127.0.0.1:55785 — …
```

`generateKeyPairSync` blocking the event loop was also suspected and was fixed anyway
(keygen is async now), but the kernel completes the TCP handshake from the listen backlog
regardless, so `portInUse` would have succeeded during a blocked loop.

## The cause, measured (the guess above was wrong twice)

Two hypotheses were written down and both were killed by measurement. *"`proxy.close()`
waits for keep-alive sockets"* — it does not; `ProxyServer.close()` already calls
`closeAllConnections()`. *"The port is slow to release"* — it is not:

```
process dead after : 4ms
port free after    : 4ms
```

The actual cause is on the **start** side. Timing every step the daemon performs before
`listen()`:

```
     7ms  migrateOnVersionChange
    11ms  loadConfig
  6668ms  credentialEnvForProxy      <- 98% of pre-listen time
   118ms  detectCapability
    22ms  resolvePersistedEmbedMode
    59ms  ollamaHasModel
```

`waitForPort`'s budget was **8000ms**. Startup sat right beneath it, and the restart path
pays credential resolution twice (parent builds the child's env, child resolves again), so
ordinary jitter pushed time-to-listen over the line — a working daemon reported as failed,
about one run in three. On the runs that "succeeded", `waitForPort` was sometimes seeing
the *old* listener, which is worse: a false success.

## The fix

- `waitForPort` budget 8s → **30s**. Being slow to declare failure costs seconds on a
  genuinely broken start; being quick to declare it sends people debugging a healthy daemon.
- `restartProxyDetached` **honours `waitForPortFree`** instead of discarding it. When the
  port is still held, spawning a daemon that will immediately exit with "already running"
  cannot succeed, so it now reports what is actually true.
- Credential resolution stays **sequential**. Making it concurrent was tried and reverted:
  it bought nothing on Windows (concurrent PowerShell startups contend rather than overlap)
  and the burst of processes destabilised the test suite. The fix that actually removes the
  cost — one batched decrypt — is R9.20.

Verified: **10 consecutive `golem proxy restart` runs, 10 successes**, each with a distinct
new pid.

## Outcome

shipped: waitForPort budget 8s->30s, restartProxyDetached honours waitForPortFree. Root latency (DPAPI spawn per stored account) filed as R9.20. Verified 10/10 restarts.
