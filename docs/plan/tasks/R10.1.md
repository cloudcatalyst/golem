## The method (read this first)

"The first pancake" — the first release of a project is expected to be the
throwaway pancake: the **ingredients** (stack, deps, data model, architecture) and
the **method** (the approach, the invariants) are good and proven, but the
**execution** is what's burnt. Nobody ships the first pancake. So: keep the
recipe, scrap the scaffolding that was written to *prove the method works*, clean
the pan, and build pancake #2 — the first real release — right.

The `/golem/first-pancake` skill (added this session) is the review playbook for
exactly this: **Pass 1** settle the keep-list (recipe + ingredients), **Pass 2**
eat the first pancake critically (scrap list: dead code, scaffolding,
proof-of-concept residue, half-integrated seams), **Pass 3** clean the pan and
reset for pancake #2 (delete / consolidate / harden). It writes nothing — it
decides, then `/golem/develop` acts.

## Priorities (user decision, this session)

1. **Testability + readability first.** Perf only where a measurement shows a real
   hot spot. (The slow tests are I/O-bound, not CPU-bound — no CPU rewrite will fix
   them.)
2. **Interfaces are ON THE TABLE.** CLAUDE.md's "frozen contracts" rule is not a
   blocker — if clean code demands a frozen-contract change, propose it (with test
   updates + flagged dependent workstreams). But keep it surgical: every interface
   change is a deliberate, reviewable act, not a side-effect of cleanup.
3. **Keep all 2541 tests green.** "Simplify the tests" means consolidate/remove
   only where a test is *proven* redundant or dead — never delete load-bearing
   integration coverage to cut runtime.

## What the rewrite must not do

- **Never weaken redaction, never reorder it after compression** (CLAUDE.md hard rule).
- **Never break byte-fidelity** at slider ≤1 — pipeline changes need recorded-shape tests.
- **No new heavyweight native deps** in default install.
- **Do not touch `src/interfaces/` blindly** — see priorities; any change is gated.
- **Do not regress the CI sharding** (#97) or the `/golem/first-pancake` skill
  (unmerged branch `feat/first-pancake-skill`, commit b2d19a6 — land it with this
  or separately).
- **Keep changes isolated from in-flight workstreams.** At the time of writing, 7
  files are dirty from another workstream (`.golem/settings.json`,
  `src/cli/commands/proxy.ts`, `src/cli/proxy-runtime.ts`, `src/cli/status.ts`,
  `src/providers/gateways.ts`, `src/providers/openai-stream.ts`,
  `src/providers/openai-translate.ts`). Do not commit, rebase, or fold those in.

## Suggested sequencing (each its own commit / reviewable chunk)

1. **Survey + classify the big files** with the first-pancake lens — label every
   region KEEP / SCRAP / REFACTOR before editing anything. This is the "review"
   deliverable; act on it via `/golem/develop`.
2. **Extract + split the largest monoliths** (init.ts, status.ts, schema.ts,
   control-surface.ts, web-fetch.ts, gateways/accounts, skills.ts) into cohesive
   modules — the biggest readability win for the least behavioral risk.
3. **Consolidate the ~26 proxy-spawning test files** around the shared fixtures
   (tests/integration/helpers/) so setup is written once — a testability win that
   *incidentally* cuts spawn cost. Consolidate, don't delete coverage.
4. **Harden what pancake #2 needs** — error paths, edge cases, docs that describe
   what actually exists.
