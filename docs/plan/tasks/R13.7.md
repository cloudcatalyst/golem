## Why this exists

This is the harness-agnostic half of ADR-0007, and the reason the proxy is a
better seam than a channel: it needs no launch flag, no allowlist, no client
cooperation, and it works for anything pointed at Golem. It is also strictly
second-class, and the brief must stay honest about why — the proxy speaks only
when the harness speaks to it, so a message reaches a *looping* session in
seconds and an *idle* one never.

## What to build

1. **A queue per conversation.** A message from a device waits, keyed to a
   conversation identity that agrees with `session-tree.ts` and R8.13's fix. If
   the conversation cannot be identified unambiguously, refuse — invariant 3,
   and §99's collision case is exactly why this is not a guess.
2. **Delivery on the next request**, as an injected block, clearly framed as a
   message from the developer's other device rather than as system text. The
   model must be able to tell who is speaking.
3. **Enforcement gate, checked at send time.** Per §3c: if R12.12's
   `PermissionRequest`-level `deny` is not registered and active for that
   project, the send path is **disabled with a reason**. Do not deliver and hope.
4. **Visible locally before it lands** (invariant 5). The developer at the
   keyboard can see what their phone said into their session — dashboard entry,
   action log, and, where the harness gives us a surface, a visible note. Golem
   does not deliver silent instructions even from the same person.
5. **Byte-faithfulness when idle** (invariant 7). Injection is opt-in, off by
   default, and a request with nothing queued must be byte-identical at
   compression ≤ 1. This is a CLAUDE.md hard rule and it needs recorded-shape
   tests, not an argument.
6. **Honest UI semantics.** Queued-and-not-yet-delivered is a state the device
   shows as such, with the delivery condition named ("this session is idle;
   nothing will be delivered until it runs again") and the alternative offered:
   start a hosted session instead (R13.3/R13.8).
7. **Optional: the channels adapter.** Where a channel is available and
   configured, delivery MAY go that route instead — but as an adapter behind the
   same queue, never as the foundation, and never as the only path. §136's five
   objections all still stand; re-read them before deciding to build this part
   at all, and it is acceptable for this task to conclude "not yet".

## Out of scope

Hosted sessions (R13.3). Any attempt to mirror or drive the harness's TUI —
`send-keys` and keystroke injection stay rejected (ADR-0007 §8). Making
injection default-on. Widening the pipeline's injection surface beyond a single
framed block. Reviving the relay.

## Gate detail

Recorded-shape tests proving byte-identity with nothing queued, and the exact
injected shape with something queued. An integration test that a queued message
is delivered exactly once on the next request and not twice on a retry. A
demonstration against a real second harness (any client pointed at the proxy) to
prove the harness-agnostic claim rather than asserting it — that demonstration is
part of the gate. Plus a wiki page stating the idle-session limitation in the
words a user needs, because "sent" meaning "queued" is the misunderstanding this
feature will generate.
