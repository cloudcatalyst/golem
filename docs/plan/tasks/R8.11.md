## Goal

Let a third party add a **pipeline stage**, an **MCP tool**, or a **redaction rule**
without forking Golem. `golem plugin` — deliberately separate from `golem ext`.

## Why redaction rules are the real driver

Every org has private key formats. Today extending redaction means editing Golem. This
is an adoption feature more than a token feature, and redaction is the seam with the
most demand and the least acceptable workaround.

## Why `plugin` is not `ext` (Decision 53)

An **ext** runs *beside* Golem (spawned or detected; Headroom, Ollama, RTK). A
**plugin** runs *inside* Golem — and specifically inside the redaction path. That is a
different trust model, which is why Decision 53 named them separately rather than
merging the surfaces.

## Hard constraints — these are the whole task

- **Never weaken the redaction stage, and never reorder it after compression** (CLAUDE.md
  hard rule). A plugin that can register a redaction rule must not be able to *remove*
  or *reorder* one.
- **`src/interfaces/` is frozen.** A plugin seam is exactly the kind of change that
  needs its contract tests updated and every dependent workstream flagged in the PR.
- Resolved from the user's own install; Golem ships no third-party bytes. A registry, if
  one ever exists, is **a list of names and pins, not a store**.
- Absence or failure of a plugin is a no-op, never an error path.
- A plugin runs inside the process that sees unredacted prompt content. Write the threat
  model (an ADR, like ADR-0002 for autonomy) **before** the seam.

## Out of scope

A plugin marketplace or registry service. Auto-download. Sandboxing as a solved
problem — if it needs a sandbox to be safe, say so in the ADR rather than shipping.
