## The symptom

The VS Code status bar shows Golem going offline and back at random while the
proxy is running normally, and the whole surface feels slower than it used to.

## The mechanism (measured, not inferred)

`vscode-extension/extension.js`:

- polls every `golem.pollSeconds` (default **15**, floor 5),
- each refresh runs **four CLI invocations in parallel** — `stats --json`,
  `status --json`, the gateway list, and the control surface,
- each is `execFile("golem", …, { timeout: 8000, shell: true })` and
  **resolves to `null` on error OR timeout**,
- `null` renders as offline.

So the bar goes offline whenever a CLI call crosses 8s, and comes back on the
next poll that does not. That is the flapping, exactly.

And the calls are nowhere near free. Measured on the affected project, warm:

| | ms |
|---|---|
| bare `node -e 1` | **177** |
| `node dist/cli/main.js --version` | **1429** |
| `golem --version` (npm shim) | **1894 – 3486** |
| `golem status --json` | ~2500 |
| `golem stats --json` | 2900 – 4009 |

Three things fall out of that:

1. **Golem's module graph costs ~1.25s** before any work happens
   (1429 − 177). `--version` pays it in full.
2. **The npm shim plus `shell: true` adds another 0.5–2s**, and it is the
   VARIABLE part (1894 → 3486 on identical work). That variance is what carries
   a call over the 8s line.
3. **Four of these run at once**, so they contend with each other on top of
   whatever else the machine is doing.

## Why the existing fast path does not help

`src/cli/fast-path.ts` exists precisely to dodge this cost, but `fastPathFor`
returns non-null only for `statusline` and `hook <event>` — the per-prompt Claude
Code paths. `status`, `stats`, `gateway list` and `config schema` all take the
long way through `program.ts`, which statically imports 21 modules and registers
36 command groups just to answer one JSON query.

## Options

- **Put the extension's read-only commands on the fast path.** Biggest win,
  same trick that already works for `statusline`. `status --json` and
  `stats --json` are pure reads; they do not need the command registry.
- **Collapse four invocations into one.** A single `golem panel --json` (or
  equivalent) returning all four payloads pays startup ONCE instead of four
  times, and removes the contention entirely. Larger change, biggest structural
  win.
- **Drop `shell: true`.** `execFile` with a controlled argv does not need a
  shell; on Windows it spawns cmd.exe per call. The comment says it is there
  because `execFile` ENOENTs on the shim — verify whether that is still true
  before removing it, and prefer resolving the shim path over keeping a shell.
- **Raise the timeout** — the weakest option alone, since it hides the cost
  rather than removing it, but reasonable as a floor once the others land.

## Out of scope

- The proxy itself. It is healthy throughout; this is entirely a reporting-path
  problem, and the bar is lying about the proxy rather than reflecting it.
- Whether R10 changed the startup cost. NOT measured against a pre-R10 build, so
  do not claim it either way without one. The 4-spawn fan-out and the 8s timeout
  both predate R10.

## Immediate mitigation for a user hitting this

Raise `golem.pollSeconds` in VS Code settings. It reduces how often the race is
run, though it does not remove it.
