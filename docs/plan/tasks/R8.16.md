## Problem

`LocalDirBlobStore.put` has a destructive race under concurrent writes:

1. Thread A creates temp file, `rename(tmp → target)` succeeds
2. Thread B creates temp file, `rename(tmp → target)` fails (target exists)
3. Thread B's catch clause **deletes** Thread A's data, then writes Thread B's version

Content-addressed (same hash = same content), so bytes are identical in practice and this has never caused data loss. But the assumption that "same key = same content" is entirely undocumented. A SHA-256 collision or a routing bug (different content → same key) would silently destroy data.

## Fix

Two options, pick one:

**Option A (minimal):** Document the content-addressed assumption on the `put` method, skip the write when the target already exists after a failed rename (don't delete and re-create).

**Option B (robust):** Use a per-key lock (`Map<string, Promise>`) so concurrent `put` to the same key serializes — only the first write proceeds, subsequent ones become no-ops.
