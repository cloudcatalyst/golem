## The defect

Found while deploying R9.23 (2026-08-14), the hard way.

`proxyStatus` decides staleness by comparing version strings:

```ts
// No stamp => started before the stamp existed => older than this build.
stale: info.version !== currentVersion,
```

That is correct across a release and **blind within one**. Every local
`npm run build` leaves `VERSION` untouched, so a daemon started before the build
keeps serving its old code while `golem status` reports it as current — no `stale`
flag, no warning, nothing to notice.

The live sequence that produced this:

| time | event |
|---|---|
| 22:48 | proxy daemon starts (pid from `.golem/proxy.pid`) |
| 00:40 | `npm run build` — R9.23's dedup exemption lands in `dist/` |
| 00:52 | `golem status` → `running_version 0.20.0`, installed `0.20.0`, **`stale` not flagged** |

The daemon was two hours behind the build and reported healthy. The dedup half of
R9.23 was not running, and no surface said so; it was diagnosed by comparing the
pidfile's mtime against `dist/`'s by hand.

This matters more than a stale label usually would, because the proxy is where the
compression pipeline runs. A rebuilt pipeline stage that is not live looks exactly
like a pipeline stage that does not work — which is a very expensive hour.

## Why the release path hides it

Merging auto-bumps the minor version (`chore(release): auto-bump minor version
[skip ci]`), so after a merge the version really does differ and the check fires
correctly. The blind spot is precisely the **local dev rebuild loop**, which is
where the check gets leaned on most.

## What to build

Stamp the running daemon with something that changes when the CODE changes, not
only when the version does, and treat a mismatch as stale.

- The child writes its own pid file on listen (see `startDetached`'s comment), so
  it can fingerprint the code it is actually running rather than the code the
  parent had — that ordering is already right and is what makes this honest.
- A cheap fingerprint is enough: `mtimeMs` + `size` of the daemon's entry script,
  or a hash of it. Note `dist/` is many files, so an entry-script stamp will miss
  a rebuild that changed only a leaf module — weigh a cheap-but-partial stamp
  against hashing more of `dist/` on a path `golem status` calls often. Say which
  was chosen and what it does not catch.
- Keep the existing version comparison as well: a daemon from a different release
  is stale regardless of any fingerprint, and the no-stamp case must stay stale
  (it predates the stamp, so it is older by definition).
- The message has to name the fix (`golem proxy restart`), per R9.6 — a warning
  nobody can act on is the same as no warning.

## Watch for

- **No false positives on the common case.** A freshly restarted daemon on an
  unchanged build must never report stale, or the flag becomes noise and gets
  ignored — which is worse than the gap being fixed here.
- The stamp must not make `proxyStatus` expensive. It is on `golem status`, the
  status line, and the VS Code extension's poll (R10.10 measured that path
  carefully); a hash of every file in `dist/` on each call would trade this bug
  for a latency regression.
- A daemon found only by a port probe (no pid file) is already reported stale, and
  should stay that way — "something is listening" was never evidence of what.

## Out of scope

- Auto-restarting a stale daemon. `golem status` is a read-only diagnostic and
  R9.16 settled that a diagnostic which rewrites an install is its own surprise.
- The R10.12 bypass-shim work, even though both touch proxy lifecycle.
